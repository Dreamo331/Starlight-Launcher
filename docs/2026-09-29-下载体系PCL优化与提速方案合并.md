# 第一部分：PCL 下载提速机制参考设计规格（Java 落地方案）

> 范围：对照 PCL 2 的 `ModNet.vb` / `ModDownload.vb` / `ModDownloadLib.vb`，为 Starlight Launcher 的 `com.example.starlight.download.mod` 包产出算法级设计。

## 0. PCL 下载引擎全局架构总览

PCL 的下载引擎由四层组成，自底向上：

1. **Http 原语层**：一个共享的 `HttpClient`（自动 gzip/deflate、跟随重定向）。小请求走带 CacheCow 磁盘缓存的另一个客户端；大文件下载走无缓存客户端。
2. **NetFile（单文件任务）**：持有一组有序下载源（`NetSource`），内部用一条链表组织多个分块下载线程（`NetThread`），每块写自己的临时文件。
3. **LoaderDownload（文件列表任务）**：一批 NetFile 的容器，负责去重、本地已存在文件复用、整体进度。
4. **NetManager（全局单例）**：跨所有 LoaderDownload 的调度中心 -- 全局线程数上限、限速令牌桶、两个“线程播种器”循环（20ms）、一个统计刷新循环（100ms）、按目标路径去重合并并发任务。

关键认知：PCL 不是“每文件开 N 个线程”，而是全应用共享一个总线程池配额，由调度器动态把线程分配给“最值得加速”的文件（正在下且速度慢、且最大碎片足够大的文件）。

## 1. 多线程分段下载

### 1.1 PCL 实现思路（算法级）

- **不分块条件**：文件大小未知，或总大小 < 1MB，则单线程整文件下载，小文件直接写内存 `MemoryStream`，完成时一次性落盘。
- **分块组织**：每个分块是链表节点，记录 `[DownloadStart, DownloadEnd]`、已完成字节数、临时文件路径。最后一块的结束位置 = 文件总大小 - 1；大小未知时视为约 1TB 上限。
- **动态再分裂**：调度器发现某正在下载文件“全局速度不达标”时调用 `TryBeginThread()`：在该文件链表中找剩余量最大的分块，若该分块未完成量 > 256KB，则从其已完成点之后的 60% 处切出一个新分块（即把大块再劈成两块），新分块插入链表。
- **首线程探测**：第一个线程不带 Range 头，直接 GET 全量响应，从 `Content-Length` 确定文件总大小并做大小校验；后续线程一律带 `Range: bytes=start-`。
- **并发写冲突规避**：每个分块写独立的临时文件（文件名含 fileUuid/threadUuid/随机数），没有任何两个线程写同一文件；全部完成后由唯一 Merge 线程按链表顺序串行拼接。天然无锁、无冲突。

### 1.2 关键参数

| 参数 | PCL 默认 | 说明 |
|---|---|---|
| 单文件不分块阈值 | < 1MB 或大小未知 | 现有 Java 引擎是 4MB，建议保留 Java 的 4MB 作为“才值得分块”门槛，PCL 的 1MB 作为“一定单线程”下限 |
| 二次分裂最小碎片 | 256KB（FilePieceLimit） | 小于此碎片不再切分 |
| 分裂点位置 | 大块剩余量的 60% 处 | 即新线程接管该块后 40% 的尾部 |
| 全局线程上限 | 用户设置 + 1（默认约 4 到 16） | 全部文件共享 |
| 读缓冲 | 16KB | 现有 Java 引擎 64KB，建议沿用 64KB |

### 1.3 异常与边界

- 服务器不支持 Range（`start>0` 但返回的 ContentLength >= 总大小，即忽略了 Range），抛 `RangeNotSupportedException`，该源降级为“单线程源”，全文件回到单线程重下。
- 非首线程 ContentLength 与 `FileSize - start` 不符，判该源抽风，切源。
- 文件 >50MB 时下载前校验目标盘 + 临时盘剩余空间（临时盘需约等于文件大小，目标盘需文件大小 + 5MB）。
- 下载中断：线程异常退出后状态置 Canceled，其已下载字节保留在临时文件中；调度器可在剩余区间上另起新线程换源续传（见第 2 节）。

### 1.4 落地方案

- **复用** `HttpDownloadEngine` 的 `sendFollowingRedirects / downloadRange / probeFileSize` 作为“单个 Range 请求”原语；复用其 HTTP/2 到 1.1 降级双客户端。
- **新建** `com.example.starlight.download.mod.DownloadPiece`：字段 `start, end, done, tempFile, sourceIndex, state`；替代 PCL 的链表，用 `List<DownloadPiece>` 即可（Java 无须手写链表）。
- **新建** `DownloadFileTask`（见第 2 节）持有 `List<DownloadPiece>`。
- **不新建** HTTP Range 原语层 -- 直接复用 `HttpDownloadEngine`。

## 2. 多源自动切换链

### 2.1 PCL 实现思路

每个文件持有按优先级排序的 URL 列表（如：官方、BMCLAPI、MCBBS），每个源记录 `FailCount` 与 `IsFailed` 标记。

- **选源规则**：从指定下标开始环形扫描，跳过已 `IsFailed` 的源，取第一个可用源。
- **首源轮转（FirstThreadSource）**：每个文件的第一个线程不固定从源 0 开始，而是按 `FirstThreadSource` 递增轮转选取 -- 这样多个文件不会同时都打第一个源，把压力均匀分散。
- **单线程源（SourcesOnce）**：不支持 Range 的源进入此集合，强制单线程（一个文件只允许一个线程挂在它上面，用 `SingleThread` 字段标记唯一线程）。
- **多线程源黑名单**：PCL 对 `bmclapi / github.com / optifine.net / meloong.com / momot.rs / pcl2-server` 这类源只开一个线程 -- 即便源可用，调度器也不为其追加分裂线程（这些源单连接已够快，多连反而触发风控）。
- **BMCLAPI 限流**：每启动一个打 bmclapi 的线程后 `sleep 100ms`，降低频率。

### 2.2 源被禁用（IsFailed）的触发条件

满足任一即禁用该源（由第一个标记它的线程执行，其余线程静默退出）：

1. `RangeNotSupportedException` 或 HTTP 416；
2. HTTP 502 / 404；
3. DNS 解析失败、连接无返回数据、磁盘空间不足；
4. HTTP 403 / 429（例外：bmclapi 的 403/429 是频率限制，不禁用）；
5. 该源从未拿到任何字节（DownloadDone<1）且 FailCount >= clamp(全局线程数, 5, 30)；
6. FailCount > 全局线程数 + 2。

### 2.3 禁用后的状态机

1. 还有其他多线程可用源，其他线程继续，仅把失败线程换成下一个源重起；
2. 无多线程源、但本文件尚未整体重试过（`Retried=false`），把所有源标记为单线程源，清空已下进度（Reset），单线程整体重下一遍 -- 兼容“某源返回错误文件”和“多线程抽风源”两类问题；
3. 已整体重试过仍失败，该文件最终失败，汇总各源异常上报。

### 2.4 落地方案

- **新建** `DownloadSource`：`url, host, failCount, disabled, singleThreadPiece(可空), lastError`。
- **新建** `DownloadSourceChain`：封装“按序选源 / 标记禁用 / SourcesOnce 单线程集合 / 首源轮转”逻辑。
- **复用** 现有 `DownloadProvider.injectURLWithCandidates` 生成候选 URL 列表喂给 `DownloadSourceChain`；BMCLAPI/Mojang/MCBBS provider 不变。
- **新建** `HostPolicy`（小枚举/配置）：标记“只单线程”的 host 集合（默认含 bmclapi、github、modrinth cdn 等），与 Java 现有的 MCIM 熔断解耦。

## 3. 限速

### 3.1 PCL 实现思路

限速是全局令牌桶，不是线程级：

- 一个全局原子计数 `SpeedLimitLeft`（剩余可下载字节预算）。
- 统计线程每 100ms 向桶里补充 `highLimit / 10` 字节（即按 1 秒预算分 10 次补充）。
- 每个读循环每读完一块：若限速开启，则原子扣减 `RealDataCount`；当 `SpeedLimitLeft <= 0` 时该线程 `sleep 16ms` 自旋等待补充。
- 高限映射（PCL 设置项 0 到 41 的档位）：
  - 档位 0 到 14：`(档位+1) * 0.1 MB/s`（0.1 到 1.5MB/s）
  - 档位 15 到 31：`(档位-11) * 0.5 MB/s`
  - 档位 32 到 41：`(档位-21) * 1 MB/s`
  - 档位 >41：-1 表示不限速
- 低限 256KB/s 不是死限速，而是“加速触发线”：实测近 1 秒平均速度的 85% 若高于 256KB/s，则把低限抬高到该值；当全局速度跌破这条自适应线时，调度器才追加分块线程。

### 3.2 落地方案

- **新建** `GlobalSpeedLimiter`（单例）：`AtomicLong tokens`，后台调度 100ms 滴答补充 `highLimit/10`；提供 `acquire(int bytes)` 阻塞方法（park 16ms 循环）。
- 现有引擎是逐文件回调进度，需要在 `HttpDownloadEngine` 的写循环前插入 `limiter.acquire(n)` -- 以装饰器/钩子方式接入，不改 Range 原语。
- UI 档位直接给“KB/s 数值”即可，不必照搬 PCL 的 0 到 41 档位；内部仍做 `bytes/sec` 令牌桶。
- “低限自适应抬升”可作为二期：先固定 256KB/s 作为“慢速才加线程”的触发线。

## 4. 统一下载任务队列 / 调度

### 4.1 PCL 任务链（LoaderTask 链）

一次“安装某个 Mod/版本”被组织成 `LoaderCombo`（可并行组）、若干 `LoaderTask`（分析类）+ `LoaderDownload`（下载类）：

```
分析缺失文件(ProgressWeight约1)  -->  LoaderDownload(ProgressWeight 15到27)  -->  后处理任务(ProgressWeight 0.1到10)
```

- **分析阶段**：根据版本 JSON / Mod 元数据算出需要的 `NetFile` 列表（URL 候选 + 期望大小 + Hash）。
- **本地复用**：对每个有校验信息的文件，并行（每 40 个文件一个检查线程，最多 8 线程）在 `.minecraft` 各版本文件夹里按“同路径 / 同大小 + SHA1”查找已有文件，命中则直接复制（IsCopy=true，进度权重只算 0.2 而非 1.0），不再走网络。
- **下载阶段**：把全部 NetFile 交给 NetManager；NetManager 按 `LocalPath` 去重 -- 同一文件被多个任务需要时共享一个 NetFile 对象，任一任务完成即算完成。
- **进度聚合**：任务进度 = sum(文件进度 * 权重) / sum权重；网络文件权重 1.0，本地复制文件权重 0.2；各 LoaderCombo 之间再按 `ProgressWeight` 加权。

### 4.2 调度循环（NetManager）

- 两个播种线程（20ms 一轮），按 `fileUuid mod 2` 分管一半文件；
- 对 WaitingToDownload 文件：只要全局线程数 < 上限就 `TryBeginThread()`；
- 对进行中文件：仅当全局速度 < 自适应低限才追加线程，且“准备中线程数 <= 下载中线程数”才追加（避免一窝蜂建立连接）。

### 4.3 落地方案

- **新建** `DownloadCoordinator`（约等于 NetManager 单例）：持有全局 `ExecutorService`（线程数 = 用户设置，如 8 到 16），`ConcurrentMap<Path, DownloadFileTask>` 按目标路径去重；提供 `submit(Collection<DownloadFileTask>)`。
- **新建** `InstallPlan` + `PlanStage`（约等于 LoaderTask/LoaderCombo/ProgressWeight）：把“分析缺失、下载、校验、后处理”显式建模成 DAG 阶段，每阶段带 `weight`；UI 进度 = 加权平均。
- **新建** `LocalFileReuse`：下载前扫描已有 MC 目录，按 size+SHA1 硬/软复制，命中文件不进网络队列。
- 现有 `newui/download/DownloadTaskManager` 是 UI 层任务卡片，与本调度器解耦：调度器只管字节，UI 层订阅进度事件。

## 5. 失败重试 + 熔断

### 5.1 PCL 行为

- **连接超时自适应**：`timeout = min(max(历史平均连接耗时, 15s) * (1 + 源.FailCount), 30s)` -- 失败越多容忍越久但封顶 30s。
- **慢速掐线**：两包间隔 > 5s 且该间隔内只收到不足约 1KB（`gapMs > bytesReceived`）且非单线程源，主动断开重连。
- **无数据超时**：已开始收数据后，若一包间隔超过 connect-timeout，断开。
- **成功即清零**：任一时刻收到有效字节，该源与所属任务的 FailCount 立即归零。
- **合并重试**：拼接文件最多重试 3 次，退避 500ms * 次数；3 次后删除残文件，把当前源标记失败并整体换源重下。
- **加载器级熔断**：整个 LoaderDownload 的累计 FailCount >= `min(10000, max(剩余文件数*8, 全局线程数*8+3))` 时强制判失败（防止网络全挂时空转）。
- 小请求层另有 `Retrier`（基于谓词的重试循环，仅对 FileNotFoundException/IOException 重试，固定 200ms 延迟，最多数轮）。

### 5.2 与现有 MCIM 熔断的合并

现有 `MirrorCircuitBreaker` 是“镜像域名级”熔断器：连续 N 次失败，冷却期内跳过镜像，冷却结束放行一次探测（half-open）。
PCL 的 `NetSource.FailCount/IsFailed` 是“单文件 URL 级”开关。

建议两层并存，不合并：
- `MirrorCircuitBreaker`（域名级）：保留在 `HttpDownloadEngine`，决定“要不要走镜像 host”；
- 新建 `DownloadSource.failed`（文件级）：决定“这个文件的这条候选 URL 还试不试”；
- 判定顺序：请求前先问域名熔断器 `allowMirror()`，再问文件源是否 disabled；任一失败分别上报。文件源级禁用可直接复用 PCL 的触发条件（第 2.2 节）。

### 5.3 落地方案

- **复用** `MirrorCircuitBreaker`，不重写。
- **新建** `RetryPolicy`：连接超时基数 15s、上限 30s、随 FailCount 线性放大；慢速掐线阈值 5s/1KB。
- **新建** `SourceDisabledException` / `RangeNotSupportedException` 异常族。
- 合并重试 3 次、500ms 退避写进 `DownloadFileTask.merge()`。

## 6. 文件校验

### 6.1 PCL 行为

- 校验器 `FileChecker` 三要素：期望大小 `ActualSize`（-1 表示不校验大小）、最小大小 `MinSize`、Hash（自动识别 MD5 32 位 / SHA1 40 位十六进制）、`IsJson`（仅校验是否合法 JSON）。
- 首线程拿到 ContentLength 时先做大小校验（< MinSize 或 != ActualSize 直接抛错切源）。
- 合并完成后再做一次完整 Hash 校验；校验失败，删除成品，当作合并失败处理（第 5.1 节合并重试/换源）。
- 本地复用阶段也用同一个校验器判断候选文件是否真的一致。

### 6.2 落地方案

- **新建** `FileVerifier`：`verify(Path, expectedSize, expectedHash)` 返回 `Optional<String>`（空表示通过）；SHA1/MD5 自动按长度识别。
- 该校验器同时服务：下载后校验、本地复用匹配、UI“文件已损坏”自检。

## 7. 六个特别分析的明确结论

### 1. 多线程分段下载 + 断点续传 + 文件合并如何正确组合

- PCL 不并发写同一目标文件：每个分块写独立 `.tmp`，合并是单线程串行拼接，写 `[0,len)` 顺序、按每块 `done` 字节数精确截断。
- “断点续传”在 PCL 里是单次运行内的：临时目录 `Download\` 在一次会话首次启动时被整体清空，且临时文件名含随机数 -- 即 PCL 并不跨重启恢复分块进度；跨重启的“续传”靠两件事：(a) 已完成文件不再重下（校验命中即跳过/复制）；(b) 未完成文件整个重下。
- Java 落地建议：一期与 PCL 对齐 -- 分块 `.part` 文件落 `{gameDir}/.download-cache/{fileHash}/`，文件名用“块序号”而非随机数；若要真正跨重启续传，把块进度（start/done/sourceIndex）写一个同级 `.meta` JSON，重启时校验 `.part` 大小后继续。这是对 PCL 的增强而非照搬，建议作为可选项（默认开，因为成本低）。
- 合并正确性：合并前必须确认 `sum(piece.done) == fileSize`（未知大小除外）；合并时 `RandomAccessFile` 按 piece.start 定位写，或先顺序拼接再校验后原子 `move` 到目标路径（推荐后者：先写 `dest.tmp`，校验通过后 `Files.move(ATOMIC_MOVE)` 替换，避免半成品目标文件）。

### 2. 多源切换与分块下载如何组合

- 多线程分块场景下，不同分块可以挂在不同源上 -- 但调度器对每个“禁用源”的判定是文件级的：一个源被禁用，挂在它上面的所有分块线程退出，新分裂出来的分块统一选下一个可用源。
- 第一个线程出错即切源的细节：首线程负责探测文件大小；它失败时 `FirstThreadSource` 已推进到下一个源 ID，所以下次重起首线程天然落在第二个 URL 上，而不是反复打第一个挂掉的源。
- 单线程 vs 多线程策略差异：
  - 多线程源：可同时挂 N 个分块线程，每个分块独立选源；
  - 单线程源（SourcesOnce / 黑名单 host）：该文件只允许一个线程，且不分块、不做 Range；
  - 一旦所有多线程源都挂了，整文件 Reset 成单线程模式，用单线程源从头重下（`Retried` 保证只整体重尝试一轮）。

### 3. 限速放在哪一层

- 放在全局总量层，不是线程/文件层：一个 JVM 级令牌桶，所有分块线程共享。
- 实现：后台 100ms 周期任务补充 `bytesPerSecond / 10`；读循环每消费 N 字节就 `tokens.addAndGet(-N)`，耗尽则 `LockSupport.parkNanos(16ms)` 自旋。
- 低限 256KB/s 在 PCL 里不是“最低下载速度”，而是“低于此速度就加线程”的自适应加速阈值；高限可配置 = 令牌桶 refill 速率，-1 = 不 refill（不限速）。
- Java UI 直接暴露“限速 KB/s 输入框”，内部映射为 refill 速率即可。

### 4. 任务链如何映射 / ProgressWeight 如何分配

- 映射：分析缺失，生成 DownloadFileTask 列表，DownloadCoordinator 统一调度，全部完成后 FileVerifier 批量校验，后处理（解压/合并 JSON）。
- ProgressWeight 分配原则：下载是大头（占总权重 60% 到 80%），分析和后处理各占小头；PCL 实例：支持库分析 1 / 下载 15；资源索引分析 0.5 / 索引下载 2 / 列表生成 0.01 / 资源下载 25。
- 单文件内部进度非线性映射：`p' = 1 - (1-p)^0.9`，再线性映射到 5% 到 98%（避免小文件进度跳变感）；连接中 2%、读首包 4%、合并 99%。
- 并发度：全局线程池上限统一控制，不是文件级并发；播种循环 20ms 一轮，慢文件才追加线程。

### 5. 重试 + 熔断与现有 MCIM 熔断合并

- 文件级源失败（第 2.2 节条件），该 URL 标记禁用，切下一个候选 URL；
- 域名级熔断（`MirrorCircuitBreaker`），冷却期内整个 host 不试；
- 两级独立、串联判定：域名熔断优先（快速跳过整 host），文件源禁用兜底；
- 恢复策略：PCL 没有“半开探测恢复源”，因为文件生命周期短；建议域名级沿用现有 half-open（冷却结束放行一次探测），文件级不做恢复（任务结束即销毁）。

### 6. HTTP 缓存（CacheCow）的价值与最小可行实现

- PCL 的 CacheCow 只服务小 JSON 请求（版本列表、Forge/Fabric 元数据），完全不参与大文件下载（下载客户端是另一个无缓存 HttpClient）。磁盘位置 `{temp}/Cache/Http/`，标准 HTTP 缓存头协商（ETag / Cache-Control / Expires）。
- 价值：二次启动时版本列表/Mod 列表秒开，少打网络；对“下载提速”本身帮助为零。
- Java 最小可行实现：
  - 一期不做通用 HTTP 缓存（避免引入缓存协商复杂度）；
  - 对“版本清单 / Mod 元数据 JSON”这类小响应，用现有 `downloadContentFile` 落地后按 URL hash 存 `{gameDir}/.cache/meta/`，下次直接读本地文件，TTL 1 天（PCL 对 asset index 就是“每天更新一次”的同款策略）；
  - 大文件下载、分块 Range 请求一律不加缓存，与断点续传互不干扰。

# 第三部分：PCL 优化后补全速度提升预期

不能给一个统一倍数。按 `pcl_spec.md` 落地后，补全速度提升主要取决于场景：首次全量下载、二次补全、源是否稳定、线程上限是否从默认 4 调到 16、服务器是否支持 Range、磁盘/带宽是否瓶颈。

先给结论：

| 场景 | 预计总补全时间提升 | 主要原因 |
|---|---:|---|
| 首次全量补全，仍用默认 4 线程 | 1.1 到 1.5 倍 | 底层 `HttpDownloadEngine` 已有分块、断点续写、HTTP/2 降级、MCIM 熔断；PCL 主要补全局调度/多源，线程上限没变 |
| 首次全量补全，线程调到 16，源支持 Range | 1.5 到 3 倍，乐观 4 倍 | PCL 全局线程池 + 动态再分裂，可让大文件从 4 线程升到更多线程 |
| 大量小文件：assets / libraries | 2 到 5 倍 | PCL 全局线程池跨文件调度，减少小文件串行和连接等待 |
| 大文件：client.jar / modpack / 大 mod | 1.5 到 3 倍 | 动态再分裂有效，但受服务器单连接限速、总带宽、磁盘合并限制 |
| 源不稳定 / 镜像抽风 / 403/429 | 有效吞吐 2 到 10 倍，或从失败到成功 | `DownloadSourceChain` 多源切换、禁用、首源轮转、重试熔断 |
| 二次补全 / 修复已有游戏 | 5 到 20 倍甚至更高 | `LocalFileReuse` 按 size+SHA1 复制复用，元数据缓存秒开，大量文件不走网络 |
| 开启限速 | 不提速，按限速值 | PCL 限速是全局令牌桶，属于限制器 |
| 只做类搬迁，不接调度/复用 | 接近 0 | 核心提速不在搬包，而在全局调度、源链、本地复用、动态分裂 |

用 Amdahl 定律看更清楚：如果下载占补全总时间的 80%，下载本身加速 2 倍，总时间只提升  
`1 / (0.2 + 0.8/2) = 1.67 倍`；下载加速 3 倍，总提升约 `2.14 倍`。所以总补全提升一定小于下载环节的提升倍数。

为什么不是从零到巨大提升？`inventory.md` 显示现有基础不差：

- `HttpDownloadEngine` 已有分块下载（>=4MB）、断点续写、HTTP/2 到 1.1 降级、MCIM 镜像熔断。
- `DownloadSettings` 默认 4 线程，最大 16。
- `GameResourceCompleter` 已有并发控制、SHA-1 校验、inheritsFrom 解析，但自带独立 `HttpClient`，未复用 `HttpDownloadEngine`。
- `InstallEngine` 自带三套 HTTP 下载；`MultiThreadDownloader` 是旧 `HttpURLConnection` 实现；4 处静态持有 `DownloadProvider`。
- 缺少的是 PCL 那套：全局 `DownloadCoordinator`、文件级多源链、动态再分裂、`HostPolicy`、全局限速、`LocalFileReuse`、`MetaDiskCache`。

`pcl_spec.md` 里对“下载提速”真正有价值的是：

1. 全局线程池 + 动态再分裂：把线程从“每文件固定 4 个”变成“全局配额给最值得加速的慢文件”。
2. 多源自动切换 + 文件级源禁用：减少卡死、反复打坏源。
3. HostPolicy 单线程黑名单：bmclapi、github 等只开单线程，避免风控，提升稳定性。
4. LocalFileReuse：二次补全时按 size+SHA1 复制已有文件，这是提升最大的点之一。
5. MetaDiskCache：版本清单/Mod 元数据秒开，对下载本体帮助小。

而 `pcl_spec.md` 也明确：

- CacheCow 只服务小 JSON，对下载提速本身帮助为零。
- 限速是全局令牌桶，开启后只会限制速度。
- 合并、校验、进度权重不直接提速，只是保证正确性和体验。

所以合理预期是：

- 首次全量补全：常见总体提升 1.5 到 2.5 倍；如果用户把线程调到 16、源支持多连接、且小文件多，可到 3 倍左右；超过 4 倍通常说明原实现有严重串行、源故障或未复用。
- 二次补全/修复：因为本地复用和元数据缓存，可能 5 到 20 倍以上，具体看已有文件命中率。
- 源故障场景：不是简单提速，而是从“频繁失败/卡死”变成“能稳定完成”，有效吞吐可能 2 到 10 倍。
- 默认 4 线程不变：提升最小，约 1.1 到 1.5 倍，主要来自多源切换和调度优化，而不是带宽放大。

一句话总结：按 `pcl_spec.md` 落地，首次全量补全合理预期是 1.5 到 2.5 倍，调优后可到 3 倍左右；二次补全可 5 到 20 倍以上；源差场景提升最大但不可精确量化。不要期待限速、元数据缓存、CacheCow 带来下载峰值提升。

# 第四部分：怎样可以更快

要更快，核心不是继续堆“分块线程”，而是把重复下载、全局调度、源选择、磁盘合并这四个瓶颈打掉。PCL 方案是及格线，不是极限。按优先级排：

## 1. 最大收益：本地复用 + 全局 CAS（P0）

`pcl_spec.md` 的 `LocalFileReuse` 只做到“按 size+SHA1 复制”。可以再进一步：

- 建一个全局内容寻址缓存：`{gameDir}/.download-cache/{sha1}`。
- 下载前先查 CAS，命中则直接硬链接到目标路径（同盘），或复制。
- 多个版本、多个整合包共享同一份 libraries/assets/mod。
- Windows 上用 `Files.createLink` 或 `mklink /H`，避免复制大文件。
- 配合 `FileVerifier` 校验，保证一致性。

预期：二次补全从几分钟降到几秒到几十秒，提升 5 到 20 倍以上。这是最快、最稳的提速点。风险是硬链接被修改会影响其他实例，所以只对只读游戏文件用硬链接，或默认复制、可选硬链接。

## 2. 全局线程池 + 提高默认并发（P0）

现在 `DownloadSettings` 默认 4，最大 16。PCL 的全局线程池可以让线程动态分配给最慢的文件。建议：

- 默认线程从 4 提到 8 到 12，上限开到 32 到 64。
- 单 host 并发限制：bmclapi/github 等 2 到 4，普通 CDN 4 到 8。
- 播种循环 20ms 保留，动态再分裂触发线从 256KB/s 提到 512KB/s 到 1MB/s，让慢文件更早加线程。
- 小文件走 HTTP/2 多路复用，不要每个文件都开新连接。

预期：首次全量补全 1.5 到 2.5 倍，调到 16 线程可到 3 倍左右。注意源风控，单 host 不能无限加。

## 3. 多源从“顺序切换”升级为“测速选源 + 分块级多源”（P0/P1）

PCL 是文件级选源、失败才切。可以更快：

- 维护每个 host 的 EWMA 吞吐、首包时间、失败率。
- 选源时按速度排序，同时保留首源轮转，避免同时打一个源。
- 对支持 Range 的多个源，不同分块挂不同源同时下，突破单源限速。
- 小元数据请求可以多源竞速，谁先返回用谁。
- HostPolicy 保留：bmclapi、github、modrinth cdn 默认单线程或低并发。

预期：源不稳定时有效吞吐 2 到 10 倍，或从失败到成功。风险是不同源文件版本不一致，必须最后整体 SHA1 校验。

## 4. 真正跨重启断点续传（P1）

PCL 不跨重启恢复分块。Java 可以：

- 分块 `.part` 文件放 `{gameDir}/.download-cache/{fileHash}/`。
- 同级写 `.meta` JSON：`start/end/done/sourceIndex`。
- 重启时校验 `.part` 大小，继续未完成分块。
- 合并前确认 `sum(piece.done) == fileSize`。

预期：大文件中断后重来提升明显，尤其 client.jar、整合包、大 mod。

## 5. 磁盘与合并优化（P1/P2）

PCL 每个分块写独立临时文件，最后串行合并。合并可能成为瓶颈。可以：

- 临时文件与目标文件同盘，优先 SSD。
- 预分配目标文件空间。
- 用 `FileChannel.write(ByteBuffer, position)` 多线程写同一文件不同区间，省掉合并阶段。
- 完成后流式算 SHA1，校验通过再 `Files.move(ATOMIC_MOVE)`。
- 小文件（<1MB）内存缓冲，批量落盘，减少磁盘 IO。

预期：大文件合并时间减少 30% 到 70%，SSD 上更明显。风险是崩溃一致性，需要 `.meta` 和最终校验兜底。

## 6. 校验与进度优化（P1）

- 下载时边写边算 SHA1，或合并时同时算，省一次完整读。
- 大量小文件并行校验，复用 `VerifySettings` 的并行开关。
- 本地复用匹配先比 size，再比 hash，避免全量读。
- 进度回调节流到 100ms，UI 事件队列，别让 UI 阻塞下载线程。

## 7. 统一现有重复实现（P0）

`inventory.md` 显示：

- `MultiThreadDownloader` 旧 `HttpURLConnection`，靠 stdout 劫持进度。
- `DownloadService` 和 `UIGeneralControlClass` 两份重复下载实现。
- `InstallEngine` 自带三套 HTTP 下载。
- `GameResourceCompleter` 自带独立 `HttpClient`。
- 4 处静态 `DownloadProvider`。

统一到 `HttpDownloadEngine` + `DownloadCoordinator` 后，连接池、HTTP/2、熔断、多源、限速才能全局生效。否则每个模块各自为战，全局调度无从谈起。

## 8. 系统与配置（P3）

- 关闭限速；必须限速就用全局令牌桶，不要线程级。
- Windows Defender 排除游戏目录和 `.download-cache`。
- 电源计划高性能，有线网络，SSD。
- 关闭不必要的 VPN/代理。
- 调整 JVM：`HttpClient` 用独立 Executor，避免公共 ForkJoinPool 瓶颈。

## 最快配置示例

- 全局线程 16 到 32，单 host 4 到 8，bmclapi 2 到 4。
- 分块阈值 1 到 2MB，最小碎片 128 到 256KB，分裂点 50% 到 60%。
- 慢速触发线 512KB/s 到 1MB/s，播种 20ms。
- 临时文件同盘 SSD，预分配，FileChannel 写不同区间。
- 本地 CAS + 硬链接。
- 分块级多源 + 最终 SHA1 校验。
- 关闭限速，进度 100ms 节流。

## 优先级路线

1. P0：本地 CAS/硬链接、全局线程池、统一下载引擎、多源切换、关闭限速。
2. P1：跨重启续传、源测速、动态再分裂调参、并行校验、进度节流。
3. P2：分块级多源、FileChannel 并发写、预分配、边下边校验。
4. P3：系统优化、HTTP/2 调优、DNS 缓存。

一句话：先复用，再全局调度，再源测速，最后磁盘优化。只调线程数最多 1.5 到 3 倍；加上本地 CAS 和分块级多源，才能把首次全量补全推到 3 倍左右，二次补全推到 5 到 20 倍以上。
