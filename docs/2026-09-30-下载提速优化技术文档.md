# 2026-09-30-下载提速优化技术文档

> 项目：Starlight Launcher（Maven，Java 17，Windows）  
> 基线：`com.example.starlight.download` 体系已建立，`download.mod` 已落地 PCL 提速六机制骨架  
> 目标：在现有重构基础上，进一步降低首次全量补全时间，大幅提升二次补全/修复速度，并在源不稳定场景下提高有效吞吐与成功率  
> 适用范围：`com.example.starlight.download.mod`、`download.task`、`download.engine` 及其调用方

---

## 1. 背景

`2026-09-29` 与 `2026-09-30` 两轮重构后，下载体系已完成以下工作：

- 所有“发起下载”的类收进 `com.example.starlight.download`，按 `engine / source / task / mod` 分模块。
- `download.mod` 已实现：`DownloadCoordinator`、`DownloadFileTask`、`DownloadPiece`、`DownloadSourceChain`、`HostPolicy`、`GlobalSpeedLimiter`、`RetryPolicy`、`FileVerifier`、`InstallPlan`、`PlanStage`、`LocalFileReuse`、`MetaDiskCache` 等提速组件。
- `DownloadService.downloadFileAsync` 已切换为 mod 链路：多源链 → `DownloadFileTask` → `DownloadCoordinator.submit` → 轮询进度。
- `DownloadProviderHolder` 收敛了原先分散的 provider 静态持有。
- `util/UpdateChecker` 已实现官方检查更新 + Gitee 优先、GitHub 备用的安装包下载源切换。

但当前仍有明显瓶颈：

1. **旧链路未全部接入 mod**：`AssetDownloader`、`LibraryDownloader`、`GameResourceCompleter`、`InstallEngine`、`LoaderInstallEngine`、`JavaInstall`、陶瓦下载等仍走旧 `HttpDownloadEngine` 或自带 HTTP 实现。
2. **本地复用仍以复制为主**：`LocalFileReuse` 已按 size+SHA1 复用，但未升级为全局 CAS + 硬链接。
3. **多源仍以“顺序切换”为主**：未做源测速、未做分块级多源。
4. **断点续传未跨重启**：分块 `.part` 文件未配套 `.meta` 恢复。
5. **磁盘合并可能成为瓶颈**：分块独立 `.part` 最后串行合并，大文件合并耗时明显。
6. **`download-mod.json` 仅为骨架**：运行时可调参数未真正接入。
7. **`InstallPlan/PlanStage` 未接入安装流程**：加权进度与本地复用尚未覆盖完整安装链。

本文件给出下一阶段提速优化的技术方案与实施路线。

---

## 2. 提速原则

1. **先复用，再全局调度，再源测速，最后磁盘优化。**
2. **全局资源必须统一**：线程池、限速、熔断、源选择、本地缓存只应有一套。
3. **旧链路不接入 mod，全局调度只能覆盖局部**：优先统一下载入口。
4. **最终校验兜底**：多源、分块级多源、硬链接、跨重启续传都必须以最终 SHA1/MD5 校验为准。
5. **参数可调优于硬编码**：线程数、分块阈值、慢速线、单 host 并发应可由 `download-mod.json` 运行时读取。
6. **不做线程级限速**：限速只做全局令牌桶；默认关闭。

| 类 | 当前下载方式 | 影响 |
|---|---|---|
| `AssetDownloader` | `HttpDownloadEngine` | 不参与全局线程池、多源链、本地复用 |
| `LibraryDownloader` | `HttpDownloadEngine` | 同上 |
| `GameResourceCompleter` | 自带独立 `HttpClient` | 并发、校验、临时文件原子替换均内建，未统一 |
| `InstallEngine` | 自带 `fetchWithMirrors / downloadFileWithProvider / downloadFile` | 三套 HTTP 栈，未统一 |
| `LoaderInstallEngine` | 自带 HTTP + installer jar 下载 | 未统一 |
| `JavaInstall` | `HttpURLConnection` 多源下载 | 未统一 |
| `TerracottaDownloader` / `AbstractTerracottaProvider` | `TerracottaBundleStub` | 未统一 |
| `ContentDownloader` / `OverlayDownloader` / `UpdateDownloader` | 从 UI 抽取，底层仍直连 `HttpDownloadEngine` | 未统一 |

### 3.3 瓶颈结论

- **首次全量补全**：受旧链路未统一、线程数默认 4、多源未测速、磁盘合并影响，提升有限。
- **二次补全/修复**：本地复用未升级 CAS+硬链接，元数据缓存未完全接入，提升空间最大。
- **源不稳定场景**：多源顺序切换可用，但未测速、未分块级多源，有效吞吐仍可能被单源限制。
- **大文件**：分块合并串行，`FileChannel` 并发写未启用。
- **中断恢复**：不跨重启，大文件中断后整体重下。

## 4. P0：立即落地，收益最大

### 4.1 统一旧链路到 mod

**目标**：所有下载最终通过 `DownloadCoordinator.submit` 或至少统一走 `HttpDownloadEngine`。

优先顺序：

1. `AssetDownloader`
2. `LibraryDownloader`
3. `GameResourceCompleter`
4. `InstallEngine`
5. `LoaderInstallEngine`
6. `JavaInstall`
7. `TerracottaDownloader` / `AbstractTerracottaProvider`
8. `ContentDownloader` / `OverlayDownloader` / `UpdateDownloader`

实施方式：

- 保留原有公开签名，内部改为构造 `DownloadFileTask`，提交 `DownloadCoordinator`。
- 进度回调统一为 `IntConsumer progress` + `AtomicBoolean cancel` + `Consumer<String> stage`。
- `GameResourceCompleter` 的 `inheritsFrom` 解析、SHA-1 校验、取消传播保留在上层；底层文件下载替换为 mod 链路。
- `InstallEngine` 的 `fetchWithMirrors` 可保留用于字符串查询，但文件下载改走 mod。
- 旧 `HttpDownloadEngine` 单 URL 路径保留，供迁移期回退与特殊场景使用。

**收益**：全局线程池、按路径去重、多源链、限速、熔断、本地复用才能覆盖全部下载。

### 4.2 本地 CAS + 硬链接

**现状**：`LocalFileReuse` 按同相对路径 + size + SHA1 复制复用。  
**升级**：建立全局内容寻址缓存。

- CAS 路径：`{gameDir}/.download-cache/{sha1}`
- 下载前先查 CAS：
  - 同盘优先 `Files.createLink(dest, casFile)` 硬链接；
  - 不支持或跨盘再复制。
- 多个版本、多个整合包共享同一份 `libraries/assets/mod`。
- 只对只读游戏文件用硬链接；担心被修改则默认复制、可选硬链接。
- 命中 CAS 后仍用 `FileVerifier` 做最终校验。

**收益**：二次补全、修复已有游戏常见提升 **5～20 倍**，是最大提速点。

### 4.3 全局线程池与单 host 限制

**现状**：`DownloadSettings` 默认 4，最大 16。  
**建议**：

- 默认线程提到 **8～12**，上限开到 **32～64**。
- 单 host 并发限制：
  - 普通 CDN：4～8
  - bmclapi：2～4
  - github：2～4
  - modrinth CDN：4～6
- 播种循环 20ms 保留。
- 动态再分裂触发线从 256KB/s 提到 **512KB/s～1MB/s**。
- 小文件走 HTTP/2 多路复用，避免每个文件都开新连接。

**收益**：首次全量补全 1.5～2.5 倍，调到 16 线程可到 3 倍左右。

### 4.4 多源从“顺序切换”升级为“测速选源 + 分块级多源”

**现状**：`DownloadSourceChain` 按候选顺序切换、禁用。  
**升级**：

- `DownloadSource` 记录：
  - EWMA 吞吐
  - 首包时间
  - 失败率
  - 是否单线程源
- 选源时按速度排序，同时保留首源轮转，避免同时打一个源。
- 小元数据请求多源竞速，谁先返回用谁。
- 支持 Range 的多个源，不同 `DownloadPiece` 挂不同源同时下，突破单源限速。
- 必须最终整体 SHA1 校验，防止不同源文件版本不一致。
- `HostPolicy` 保留：bmclapi、github、modrinth CDN 默认低并发或单线程。

**收益**：源不稳定时有效吞吐 **2～10 倍**，或从失败到成功。

### 4.5 关闭限速与系统排除

- `GlobalSpeedLimiter.setLimit(-1)` 默认不限速。
- 必须限速时只用全局令牌桶，不做线程级限速。
- Windows Defender 排除：
  - 游戏目录
  - `{gameDir}/.download-cache`
- 临时文件与目标文件同盘，优先 SSD。
- 有线网络、高性能电源计划、关闭不必要的 VPN/代理。
- 进度回调节流到 100ms，避免 UI 阻塞下载线程。

## 5. P1：进阶优化

### 5.1 真正跨重启断点续传

**现状**：分块 `.part` 落 `{gameDir}/.download-cache/{fileHash}/`，但不跨重启恢复。  
**增强**：

- 同级写 `.meta` JSON：`start/end/done/sourceIndex`。
- 重启时校验 `.part` 大小，继续未完成分块。
- 合并前确认 `sum(piece.done) == fileSize`。
- 合并失败 3 次 × 500ms 退避后，整文件换源重下一轮。
- `.meta` 与 `.part` 不一致时回退重下该分块。

**收益**：大文件 `client.jar`、整合包、大 mod 中断后重来提升明显。

### 5.2 播种循环严格门控

一期在 `DownloadFileTask.tryBeginThread()` 内部做 HostPolicy / SourcesOnce / 碎片大小过滤。  
二期在 `DownloadCoordinator.seedTick` 补充：

- 仅当全局速度低于自适应线才追加线程。
- 准备中线程数 ≤ 下载中线程数，避免一窝蜂建连接。
- 慢文件更早加线程：慢速触发线 512KB/s～1MB/s。

### 5.3 磁盘与合并优化

- 临时文件与目标文件同盘，优先 SSD。
- 预分配目标文件空间。
- 用 `FileChannel.write(ByteBuffer, position)` 多线程写同一文件不同区间，省掉串行合并阶段。
- 小文件 <1MB 内存缓冲，批量落盘，减少磁盘 IO。
- 完成后 `Files.move(ATOMIC_MOVE)` 原子替换。
- 大文件合并时间预期减少 **30%～70%**。

### 5.4 校验与进度优化

- 边写边算 SHA1，或合并时同时算，省一次完整读。
- 大量小文件并行校验，复用 `VerifySettings` 并行开关。
- 本地复用先比 size，再比 hash，避免全量读。
- `FileVerifier` 已支持大小 + MD5/SHA1，够用。
- 进度回调节流到 100ms，UI 事件队列，别让 UI 阻塞下载线程。

## 6. P2：深度优化

### 6.1 运行时参数配置

`download-mod.json` 目前为骨架。建议接入：

- 全局线程数
- 单 host 并发
- 分块阈值
- 最小碎片
- 分裂点
- 慢速触发线
- 播种周期
- 连接超时基数/上限
- 慢速掐线阈值
- 合并重试次数与退避
- 限速值

### 6.2 `InstallPlan/PlanStage` 接入安装流程

当前为骨架。接入后：

- “分析缺失 → 下载 → 校验 → 后处理”完整走加权 DAG。
- 下载阶段权重 60～80%。
- 本地复用文件权重 0.2，网络文件权重 1.0。
- UI 进度 = 加权平均。
- 本地复用与全局调度覆盖完整安装链。

### 6.3 HTTP/JVM 调优

- `HttpClient` 用独立 Executor，避免公共 ForkJoinPool 瓶颈。
- 保留 HTTP/2 → HTTP/1.1 降级双客户端。
- DNS 缓存。
- 系统代理清理。
- 小文件 HTTP/2 多路复用。

## 7. 参数建议

| 参数 | 当前/默认 | 建议 | 说明 |
|---|---|---|---|
| 全局线程数 | 4，最大 16 | 默认 8～12，上限 32～64 | 受带宽/磁盘/服务器限制 |
| 单 host 并发 | 无限制 | 普通 CDN 4～8；bmclapi/github 2～4 | 避免 403/429 |
| 分块阈值 | 4MB | 1～2MB 才分块；<1MB 单线程内存缓冲 | 小文件不分块 |
| 最小碎片 | 256KB | 128～256KB | 小于此碎片不再切分 |
| 动态分裂点 | 已完成点后 60% | 50%～60% | 让新线程接管尾部 |
| 慢速触发线 | 256KB/s | 512KB/s～1MB/s | 慢文件更早加线程 |
| 播种循环 | 20ms | 20ms | 保留 |
| 连接超时 | 自适应 | `min(max(历史平均,15s)*(1+failCount),30s)` | 封顶 30s |
| 慢速掐线 | 两包间隔 >5s 且不足约 1KB | 保留，非单线程源 | 断开重连 |
| 合并重试 | 3 次 × 500ms | 保留 | 失败后换源重下 |
| 限速 | 默认关闭 | 默认关闭；开启用全局令牌桶 | 不做线程级限速 |
| 进度回调 | 无统一节流 | 100ms | 避免 UI 阻塞 |

## 8. 风险与规避

| 风险 | 规避 |
|---|---|
| 分块级多源导致文件版本不一致 | 最终整体 SHA1/MD5 校验 |
| 单 host 高并发触发 403/429 | `HostPolicy` 低并发/单线程黑名单 |
| 镜像某地址段系统性 404，每个文件都白付一次 404 | `SourceHealth` 容器级「主机 + 路径前缀」健康表：连续 8 次 404 后冷却期（120s）内跳过该地址段，成功即恢复；只按路径前缀拉黑，不连带同 host 的正常端点 |
| 硬链接被修改影响其他实例 | 只对只读文件用；默认复制，可选硬链接 |
| 跨重启续传 `.meta` 与 `.part` 不一致 | 校验 `.part` 大小，不一致回退重下 |
| `FileChannel` 多线程写同文件崩溃一致性 | `.meta` + 最终校验兜底 |
| 高线程数反而更慢 | 受总带宽、磁盘、服务器限速限制，不要盲目拉满 |
| 旧链路未接入 mod，全局调度局部生效 | P0 统一旧链路 |
| 元数据缓存过期导致版本列表不更新 | TTL 1 天；可手动刷新 |

## 12. 预期收益

| 场景 | 预计提升 | 主要原因 |
|---|---:|---|
| 首次全量补全，默认线程 | 1.1～1.5 倍 | 多源切换、调度优化 |
| 首次全量补全，线程 16，源支持 Range | 1.5～3 倍，乐观 4 倍 | 全局线程池、动态再分裂 |
| 大量小文件 assets/libraries | 2～5 倍 | 全局跨文件调度 |
| 大文件 client.jar/modpack | 1.5～3 倍 | 动态再分裂，但受单连接/磁盘限制 |
| 源不稳定/403/429 | 有效吞吐 2～10 倍，或从失败到成功 | 多源切换、测速、熔断 |
| 二次补全/修复已有游戏 | 5～20 倍甚至更高 | CAS + 硬链接 + 元数据缓存 |

| 只做类搬迁，不接调度/复用 | 接近 0 | 核心提速在全局调度、源链、本地复用、动态分裂 |

> 用 Amdahl 定律看：若下载占补全总时间 80%，下载加速 2 倍，总提升约 1.67 倍；下载加速 3 倍，总提升约 2.14 倍。总补全提升一定小于下载环节提升倍数。

## 14. 结论

只把线程数从 4 调到 16，通常只能到 1.5～3 倍。  
真正把首次全量补全推到 3 倍左右、二次补全推到 5～20 倍以上的关键路径是：

1. **P0**：统一旧链路接入 mod、全局线程池、本地 CAS/硬链接、多源测速与分块级多源、关闭限速。
2. **P1**：跨重启续传、播种严格门控、磁盘合并优化、校验与进度优化。
3. **P2**：`download-mod.json` 运行时读取、`InstallPlan/PlanStage` 接入、HTTP/JVM 调优。

一句话：**先复用，再全局调度，再源测速，最后磁盘优化。**
