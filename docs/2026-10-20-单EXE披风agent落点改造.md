## 2026-10-20 单 EXE 形态下披风 agent 的落点改造

日期：2026-10-20
涉及版本：1.0.0-RELEASE
关联文档：[2026-10-01-离线皮肤改造PCL2风格.md](2026-10-01-离线皮肤改造PCL2风格.md) §16、[2026-10-07-E0001启动失败签名一致性修复.md](2026-10-07-E0001启动失败签名一致性修复.md)

## 一、问题

`cape-url-patch-agent.jar` 原先是「工作目录下 `lib/` 里的一份文件」，由
`LocalCapeProxy.agentJvmArg()` 拼成 `-javaagent:<绝对路径>=<端口>` 注入游戏 JVM。

但发布形态是 **GraalVM Native Image 单 EXE**（`build-single-exe.bat`）：

- 用户拿到的只有一个 `.exe`，**没有 `lib/` 目录**；
- 整个启动器被编进镜像，不是「jar + classpath」结构，`user.dir` 只是用户从哪儿双击的；
- `-javaagent:` 却只能指向**真实存在的磁盘文件**。

结果：单 EXE 下 `resolveAgentJar()` 两级回退（`user.dir/lib`、classes 向上查找）全部落空，
`agentJvmArg()` 返回 null，离线账号的 OptiFine 披风静默失效——日志里只有一行
「未找到 CapeUrlPatchAgent jar」。

## 二、方案：内置资源 → 释放到用户数据目录 → 兜底联网下载

```
lib/cape-url-patch-agent.jar            唯一真源（仓库内，MIT）
  └─ 构建期 pom <resource> 打进 target/classes/assets/agent/
       └─ native-image 按 resourcesList 编进 exe
            └─ 运行期 CapeAgentInstaller.ensure() 释放到 ~/.starlight/cape-url-patch-agent.jar
                 └─ -javaagent:"<该路径>"=<本地披风端口>
```

### 2.1 两条获取路径

| 顺序 | 来源 | 触发条件 | 校验 |
|---|---|---|---|
| 1 | **内置资源释放** | 磁盘副本不存在 / 大小异常 / 哈希与内置资源不符 | 与内置资源自身逐字节比对（所以 agent 重建后旧副本会被自动覆盖） |
| 2 | **联网下载兜底** | exe 内没打到该资源（构建配置遗漏等） | **必须**与 `EXPECTED_SHA256` 完全一致，否则丢弃并跳过披风注入 |

下载兜底强校验的理由：这个文件会被当 `-javaagent` 载入游戏 JVM，
等同于让其中的字节码在主类加载前执行。宁可没有披风，也不加载来源不明的 jar。

下载地址走唯一真源 `services.capeAgentUrl`（`assets/endpoints.json` + `Endpoints.capeAgentUrl()`），
默认**空串**——即不开联网兜底。这样仓库默认行为是「完全离线」，部署方填了地址才启用。

### 2.2 为什么开发形态不经过安装器

`LocalCapeProxy.resolveAgentJar()` 仍是两级：

1. `user.dir/lib/cape-url-patch-agent.jar`（IDEA / `mvn javafx:run` / 项目根目录运行）；
2. 以上找不到才交给 `CapeAgentInstaller.ensure()`。

好处：本地改 agent、重新打包后立刻生效，不需要同步 `EXPECTED_SHA256`。
该常量只在「exe 缺内置资源、要联网下载」时参与校验。

### 2.3 顺带修掉的引号问题

agent 落到用户数据目录后，路径变成 `C:\Users\<用户名>\.starlight\cape-url-patch-agent.jar`。
Windows 用户名常含空格（`Zhang San`），而注入参数此前是拼成字符串再用 `split("\\s+")` 切开的：

```java
info.setJvmArgs(Arrays.asList(config.jvmArgs.split("\\s+")));   // 旧
```

这会把 `-javaagent:C:\Users\Zhang San\...` 拆成两条参数，JVM 直接认不出、启动失败。
现在统一改走 `LaunchInfo.splitCommandLine(String)`（按双引号分组，剥掉外层引号），
`agentJvmArg()` 也相应把路径用双引号包起来。四个调用点全部替换：
`GameLauncherService.buildLaunchInfo`、`UIGeneralLaunchClass.buildLaunchInfo`、
披风注入后同步 `info.setJvmArgs`、`MenuHandler.buildMinecraftCommand`。

## 四、验证

`mvn -o compile` 通过；另在 `temp/verify-split/` 跑了三个一次性验证（已删）：

1. `splitCommandLine`：`-javaagent:"C:\Users\Zhang San\.starlight\cape-url-patch-agent.jar"=9878`
   正确切成**一条**参数（引号剥除、内含空格保留），多参数与空串场景也通过。
2. `CapeAgentInstaller.ensure()`：临时 `user.home` 下首次释放成功，字节与 `lib/` 原件一致；
   第二次调用不重写（幂等）；磁盘副本被写坏后自动覆盖修复。
3. 真机载入：把释放出来的 jar 用 `-javaagent:"<含空格路径>"` 拉起一个探针类，
   子进程打印 `[CapeUrlPatchAgent] 已注册披风 URL 重写：http://127.0.0.1:9878` 且退出码 0。

## 五、仍需人工确认

- 真机跑一次 `build-single-exe.bat`，确认 native-image 下 `getResourceAsStream("/assets/agent/...")` 能读到
  （`resourcesList` 已加 `jar` 后缀；若 exe 内取不到，日志会打印
  「exe 内未找到内置披风 agent 资源」，此时才会走联网兜底）。
- 若要启用联网兜底，请在 `assets/endpoints.json` 填 `services.capeAgentUrl`，
  并确认指向的文件与 `EXPECTED_SHA256` 一致。
