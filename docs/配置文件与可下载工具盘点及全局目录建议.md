# 配置文件与可下载工具盘点 · 全局目录（`.starlight`）迁移建议

> 盘点范围：`src/main/java` 全部运行时读写路径 + 已有磁盘产物 + classpath 内置资源。
> 盘点方式：只读检索（grep/read/glob），未修改任何现有文件。
> 目标目录：`C:\Users\Administrator\.starlight`（用户消息中的 `C:\User\Administrator\` 按 Windows 实际路径 `C:\Users\Administrator\` 理解）。

---

## 一、结论速览

### 1.1 当前配置文件分散在 **5 个根**，不是 1 个

| 根 | 谁在用 | 典型内容 |
|---|---|---|
| **工作目录**（exe/jar 所在目录，`user.dir`） | 绝大多数代码 | `Starlight-Launcher/` 全部配置、`logs/`、`tools/java/` |
| **用户主目录 `~/.starlight-launcher/`** | 账号/登录/皮肤注入（老代码） | `accounts.json`、`login.json`、`authlib-injector.jar`、`avatars/` |
| **用户主目录 `~/.starlight/`** | 缓存（新代码，2026-09 之后） | `cache/`、`terracotta-cache/` |
| **`%APPDATA%\StarlightFrameGen\`** | 帧生成器（反编译移植模块） | `config.properties` |
| **游戏目录 `gameDir`** | 版本级配置与校验缓存 | `.cache/`、`versions/*/config.overrides.json` |

> ⚠ **最重要的现存问题**：项目里已经同时存在 `~/.starlight-launcher`（老）和 `~/.starlight`（新）**两套用户级约定**。
> 用户问的 `.starlight` 正是其中较新的那套。本次建议的核心动作之一，就是把老的那套并进来、只保留一个根。

### 1.2 一句话建议

- **配置类（小文件、纯用户数据）→ 全部迁 `~/.starlight/`**：账号、INI、缓存、插件状态、日志、壁纸、皮肤。
- **组件类（大文件、可执行）→ 迁 `~/.starlight/` 但保留"本地优先、全局兜底"双层查找**：JDK、Terracotta、SLan、ColorBlindOverlay。
- **绝不能全局化**：游戏目录内的 `.cache/`、`config.overrides.json`（版本隔离语义，跟着游戏目录走）。
- **打开方式建议**：不要硬切，做成"默认全局 + `--portable` 回落工作目录"，否则会直接破坏 README 里承诺的便携性。

产物：同目录 `Starlight Launcher.exe.new` + `sl-update.bat`（自替换后重启）。仅在 exe 名为 `Starlight Launcher.exe` 时启用，开发环境回退浏览器下载。

### 3.8 frpc / frpc.exe — **按需自动下载**

`frp/SakuraFrpService`：首次启动 SakuraFrp 隧道时调用官方 `GET /system/clients` 取 Windows frpc 下载项，下载到 `AppDirs.frpDir()` 并校验 MD5 / 文件大小，版本写入 `frp/version.txt`；已安装且版本匹配时直接复用。联机页也提供手动「下载 / 更新」按钮。

注：`main/MenuHandler#startFrpTunnel` 与 CLI `frp` 现在只启动 SakuraFrp 隧道（读取本机已保存的访问密钥），不再要求手动放置 frpc，也不再写 `frpc_temp.ini`。

### 3.9 Mod 中文字典（数据文件，非可执行）

`ModsApi/ModDictionaryManager`：`mod_data.txt` / `modpack_data.txt`，默认源为 HMCL 仓库 raw 链接，**只由用户在设置页手动触发**更新，落盘 `Starlight-Launcher/mod-dictionary/`。

### 3.10 严格来说属"内容"而非"工具"（一并列出以免遗漏）

- **游戏本体**：version JSON、`client.jar`、`server.jar`、assets 索引与对象、libraries、natives（`GameResourceCompleter` / `AssetDownloader` / `LibraryDownloader` / `VersionManifest` / `InstallEngine`）
- **加载器**：Forge / NeoForge / Fabric / Quilt / OptiFine / QSL 的 installer jar 与 maven 库（`LoaderInstallEngine`）
- **整合包/模组/资源包/光影/存档**：Modrinth + CurseForge + 世界 zip（`DownloadCenterPage` + `HttpDownloadEngine`）
- **构建期本地依赖**：`lib/StarlightLauncher-2.0.0.jar`（需 `mvn install:install-file`，非运行时下载）

## 五、明确不建议迁移的项

### 5.1 游戏目录内的配置 —— 必须留在 gameDir

- `.cache/verify-state.json`、`.cache/meta/`
  判据是**文件自身 mtime + size**（`MTIME_TOLERANCE_MS = 0`，见 `VerifyStateCache` 的安全边界注释）。全局化会让多个游戏目录的校验记录互相污染，直接违背"精确相等才可信"的设计。
- `versions/<版本>/config.overrides.json`
  语义是"版本独立设置动态继承全局配置"。落点必须跟着版本目录，否则版本隔离失效。

### 5.2 `multiplayer.json` —— 需先明确它到底是"用户配置"还是"运营配置"

现状矛盾：`MultiplayerSettingsPage` 当它是用户可改配置（显示 `SLanConfig.configPath()`），但 `SLanConfig` 又把它当"随启动器分发的默认模板"（首次从 `/assets/multiplayer.json` 复制，之后**磁盘整体覆盖模板**）。
全局化后的正确姿势：**jar 内保留运营默认值，全局目录只存用户覆盖，读取时逐键回落** —— 而不是"有磁盘文件就完全不看内置"。

### 5.3 启动器 MOD（`mod/`）

`plugins-state.json` 可以全局，但 **MOD JAR 本体建议留在本地**：插件以独立子进程 `java -jar` 运行、通过本地 HTTP API 与启动器握手，天然与启动器版本/API 版本绑定。全局化会带来"旧启动器加载了为新版 API 写的插件"的错配风险。
若确实想跨启动器目录共享插件，用 §4 第 6 条的"叠加扫描"而非搬移。

## 六、注意事项与风险

1. **便携性契约被破坏**：README 明确写"所有运行时数据放在工作目录下 `Starlight-Launcher/`（便携式，不写入注册表）""想重装启动器：删掉 `Starlight-Launcher/` 目录即可"。全局化后这句话必须改写，且"删目录重装"会连账号一起删 —— 需在文档与关于页同步更新。
2. **`user.home` 在游戏进程里被改写过**：`startmc/launcher/BaseLauncher:937-940` 在非 Windows 下给游戏加 `-Duser.home=<gameDir父目录>`。只影响游戏进程，但排查时容易被误认为启动器路径异常。
3. **隐藏目录可用性**：`.starlight` 以点开头，Windows 资源管理器默认难找。建议设置页加"打开配置目录"按钮（`DevPage` 已有 `openDirBtn` 打开 `logs` 的现成实现），并在目录内放一份 `目录说明.txt`。
4. **`tools/java` 的双重身份**：`JavaEnvironmentManager#JAVA_TOOLS_DIR = "tools/java"` 相对工作目录，而项目里 `tools/` 又是构建脚本目录（`check_env.ps1`、`rcedit-x64.exe`）。运行时自动下载的 JDK 会和构建工具混在同一层，迁移时务必分家。
5. **`setx` 副作用**：JDK 安装会永久改用户级 `JAVA_HOME` 与 `PATH`。这是与 `.starlight` 无关但同一链路上的既存行为，建议改为可选。
6. **权限**：迁移目标在用户目录下，通常无需管理员权限；但若启动器被装在 `Program Files` 而数据仍在工作目录，当前写入本就会失败 —— 全局化反而顺带修掉这个隐患。
7. **迁移必须可回滚**：建议首次启动时"复制"而非"移动"老文件，观察一个版本周期后再清理。
