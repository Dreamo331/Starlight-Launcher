# 2026-10-22-PCL 下载引擎交付交接

> 项目：Starlight Launcher（Java 17 / Maven）
> 交付内容：**在保留原下载引擎的前提下，新增一套对标 PCL2 逻辑的下载引擎，并在设置页可切换。**
> 默认仍是原引擎，未切换时行为与交付前一致。

## 一、交付了什么

### 1. 新增：PCL 引擎（`com.example.starlight.download.pcl`）

| 文件 | 职责 |
|---|---|
| `pcl/PclHttp.java` | HTTP 层。**成功路径不调用 `disconnect()`**，连接由 JDK keep-alive 池回收；启动时把 `http.maxConnections` 提到并发上限；保留 `setReadTimeout` 作为停滞判定的外层兜底 |
| `pcl/PclFileTask.java` | 一个目标文件 = 一个任务（对标 PCL 的 `NetFile`），持有候选源、期望大小/SHA-1、段列表与统计 |
| `pcl/PclDownloadManager.java` | 全局调度器（对标 `NetManager`）：单一并发配额、段队列、几何分裂、自适应读超时、速率型停滞判定、多源重试、合并与校验 |
| `pcl/PclResourceCompleter.java` | 资源补全入口：解析版本 JSON（含 `inheritsFrom`）/ 资产索引 / 库规则，构建任务清单并驱动调度器 |

### 2. 新增：分流器

- `download/DownloadEngineRouter.java`：**唯一的引擎判断入口**。调用方（启动准备 / 旧 GUI / `DownloadService` / 插件 API）一律走这里，不各自判断该调哪个引擎。

### 3. 新增：设置项与开关

- 键：`DownloadEngine`（`Starlight` / `PCL`，默认 `Starlight`）、`PclDownloadThreads`（默认 **64**，对齐 PCL2 `ToolDownloadThread + 1`）
- 已登记进 `main/ConfigManager.java` 的 `CLIENT_KEYS`（否则保存后重启即丢）
- UI：**设置 → 下载 → 下载引擎**（下拉 + 并发滑块 + 保存，保存即生效）

### 4. 改动：接线点（只做分流，不改旧引擎逻辑）

| 文件 | 改动 |
|---|---|
| `service/ParallelLaunchManager.java` | `completeNativeJarsOnly` / `completeAll` 改走分流器 |
| `service/GameLauncherService.java` | 串行路径的 `completeAll` 改走分流器 |
| `gui/UIGeneralControlClass.java` | 两处 `completeAll` 改走分流器 |

## 二、PCL 引擎相对原引擎的四个结构差异

1. **连接复用**：成功路径归还连接，不再每请求一次 TCP+TLS 握手。
   原引擎在 `GameResourceCompleter`/`ChunkedDownloader` 的 `finally` 里无条件 `disconnect()`，
   一次补全 3500+ 个小文件就是 3500+ 次握手，而单个小文件只需几十毫秒传完 —— 开工率因此塌到约 10%。
2. **全局单一并发配额**：整批共享一个线程池（默认 64），而不是原引擎「小文件池 32 + 大文件池 4（`BIG_POOL_THREADS`）」。
3. **几何分裂分块**：仅当「本段剩余 > 256KB」且**线程池确有闲置线程**时，才在本段**最后 40%** 切出新段（PCL `ModNet.vb:861-862`）。
4. **速率型停滞判定**：包间隔 > 5s **且** 该间隔内不足 1KB/s 才断开（PCL `ModNet.vb:1025-1028`）；
   配合自适应读超时 `min(max(connectAvg,15s)×(1+失败数), 30s)`。不再用固定 5s 读超时误杀慢但正常的响应。

### 顺带对齐 PCL 的两点

- **单线程黑名单**：`HostPolicy` 里已在名单的 host（`bmclapi` / `github` 等）**不做分段**。
  原引擎没有这一步，会把 bmclapi 的文件切成 8 段，而 bmclapi 资产端点是 302 分发的 —— 等于同时撞 8 个不同第三方节点。
- **哈希只算一次**：单连接路径边下边 digest（内存缓冲），分段路径在合并分片时顺带 digest。
  原引擎是「写临时文件 → 对临时文件算一遍 → 移动 → 再对目标文件算一遍」，每个文件两次整文件重读。

## 三、验证结果（实网）

用真实 1.20.1 资产对象（含 6 个小文件、4 个 ≥1MB、1 个 17.34MB）跑新引擎：

| 项 | 结果 |
|---|---|
| 文件校验 | **11/11 全部通过 SHA-1 与大小校验** |
| 分段路径 | ≥1MB 文件确实分成 **3~6 段**；17.34MB 文件 6 段合并后字节精确 |
| 小文件路径 | 1 段（内存缓冲 + 流式哈希） |
| 吞吐（3 次） | **7681 / 8240 / 9194 KB/s** |

对照：原引擎在 `21:46` 那次 621MB 全量补全中实测 **928 KB/s**（684.5 秒）。

> ⚠️ **口径说明**：这不是严格 A/B（文件集不同、时间点不同）。原引擎的数字来自 621MB 的真实全量补全，新引擎的数字来自 24.9MB 的小批量验证，两者只能作为量级参考，不能当作精确提速比。
> 若要出正式数字，应做「同一批文件、清空目标目录、两个引擎各跑一次」的对照。

### 过程中修掉的一个真实缺陷

首次实网验证时，4 个 ≥1MB 文件全部失败，报「分段长度不符」。根因是分段长度自检写成了
`Content-Length == 文件总长 − 起始点` —— 该等式**只在「段终点 = 文件末尾」时成立**，
而几何分裂会产出中间段。已修正为 `Content-Length == 本段区间长度`，并把可分段的文件一律改为带**闭合 Range**（避免服务端整份回传）。修复后 11/11 通过。

## 四、已知缺口（交给下一位）

### 必须知道的行为差异

1. **legacy 资产索引未支持**：`PclResourceCompleter` 只处理 `objects` 形态。
   ≤1.6 等使用 legacy/`virtual` 索引的版本，PCL 引擎会**跳过资产补全**（原引擎有 legacy 分支）。
   影响面：老版本启动。若要覆盖，需要把原引擎的 `downloadAndProcessLegacyAssets` / `handleVirtualResources` 逻辑搬过来。
2. **`completeLibrariesOnly` 走的是 natives 路径**：分流器里 `completeLibrariesOnly` → `PclResourceCompleter.completeNativeJarsOnly`
   （`includeArtifacts=false, includeClassifiers=true`）。语义上「库补全」应包含 artifacts，
   这里是一处近似，**建议修正**为独立入口。
3. **版本 JAR 仍走原引擎**：单文件、差异小，有意统一交给原引擎，避免为单文件重复实现候选逻辑。

### 未实现、但收益最大的一项

4. **跨目录资产复用（CAS / 硬链接）**：这是此前分析中量级最大的一项 ——
   实测 D 盘所需的 3575 个对象里，有 **3433 个能在其它游戏目录的 `assets/objects` 里直接命中**，只缺 142 个 / 86 MB。
   也就是说一次「首次全量」可以变成 86 MB 的量。`download/mod/LocalFileReuse.java` 有骨架，但只按同相对路径复用，未做内容寻址索引。

### 其他

5. 不做端点预探测（有意）：健康表按 `host + 目录前缀` 记账，坏源重试几次后自然被跳过；
   预探测的假路径与真实分发链路不同，原引擎已踩过这个坑。
6. 不支持跨进程重启续传（与原引擎一致）。
7. 新引擎的进度上报按「已写字节 / 总字节」，每 500ms 一次；分段任务在合并前 `writtenBytes` 是分段累加值，属正常。

## 五、如何切换与回退

```
设置 → 下载 → 下载引擎
  Starlight（默认）= 原引擎，行为与交付前一致
  PCL              = 新引擎，右侧滑块调并发（默认 64，上限 128）
```

- 切换写入 `starlight-client.ini` 的 `DownloadEngine` / `PclDownloadThreads`，**下一次补全即生效，无需重启**。
- 任何异常都可用「恢复默认」或把 `DownloadEngine` 改回 `Starlight` 立即回退，新引擎不会影响旧链路。
- 引擎名会写进日志（`PCL engine: versionId=... 待下载 N 个文件，M MB`），便于确认当前跑的是哪套。
