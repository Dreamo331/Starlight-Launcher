# 下载提速：Starlight × XMCL 机制混合方案

> 目的：把 XMCL 的可用机制与 Starlight 已有机制**混合**，形成一份可直接排期实施的提速方案（本文件只给方案，不改代码）
> 前提文档：[文件补全代码说明](2026-09-30-文件补全代码说明.md)、[XMCL 文件补全实现分析](2026-09-30-XMCL文件补全实现分析.md)
> 日期：2026-09-30

---

## 1. 混合的三条原则

混合不是"把 XMCL 抄过来"，而是按下面三条决定谁留谁改：

### 原则一：不同**时间尺度**的机制叠加，不做二选一

当前项目的问题是把所有失效判定塞进**一个固定超时**，导致既治不了秒级卡死、也调不准稳态慢速。XMCL 的机制分布在完全不同的时间尺度上，理应**分层共存**：

| 时间尺度 | 判定"这个源不行"的依据 | 归属机制 | XMCL | Starlight |
|---|---|---|---|---|
| **秒级（1~10s）** | 连接后无首字节 / 中途停顿 | **停滞看门狗** | ✅ ttfb 5s / stall 5s | ❌ 缺 |
| **十秒级（10~60s）** | 单个请求整体超时 | 请求上限（兜底） | 无（不需要） | ⚠️ 45s，目前是唯一机制 |
| **单次尝试** | HTTP 状态码（404/410/5xx） | 错误分类 | `shouldReroll` | ✅ `record404` |
| **单文件** | 收到的字节数少于应有量 | 短交付检测 | ✅ `offset < total` | ✅ `totalRead == 0` |
| **容器级（跨文件）** | 连续 N 次失败 | 熔断器 | ✅ 数据熔断 + 慢源隔离 | ✅ `SourceHealth` 三类计数 |
| **跨会话** | 历史吞吐表现 | 速度模型 | ✅ EWMA + 持久化 | ❌ 缺 |

**结论**：**停滞看门狗要新增**，而现有的 45s 请求超时**降级为纯兜底**（提到 60s，不再承担主判定责任），404/空正文/超时分类与 `SourceHealth` **全部保留**。它们互不冲突。

### 原则二：**无进展（no-progress）** 与 **慢（slow）** 必须分开处置

这是投入产出比最高的一条，也是当前实现真正缺的语义：

| 类型 | 判据 | XMCL 预算 | 处置 |
|---|---|---|---|
| **无进展** | ttfb / stall | **2 次**重掷 | 快速换源，**不必耗完预算** |
| **慢** | 达标但低于期望 | 2 次重掷 + 5 次续传 | 可权衡，**最后一个源必须忍** |

当前项目把所有"不行"都按同一个逻辑换源，于是出现 XMCL 明确规避的两种反模式：

- **反模式 A**：唯一能用的源慢 → 反复掐断 → 永远下不完
- **反模式 B**：死源把重掷预算吃光 → 一直重试同一个死源

### 原则三：能**顺势利用现有结构**的才做，不为了抄而抄

例：XMCL 的"跨镜像 Range 分片"需要重写传输层；但**本项目的 `DownloadFileTask` 已经是"每分块一个独立 `.part` 文件 + 每分块可挂不同源"**——结构上天然支持跨源分片，改造成本远低于 XMCL 那套。这类才值得做。

反之，XMCL 的"三段式 Materialize 事务/回滚"对本项目收益低（Minecraft 文件补全是幂等覆盖写），**不建议引入**。

## 2. 成本模型：先算清楚提速空间在哪

补全一批文件的墙钟时间近似：

```
T_total ≈ (N_net / C_eff) × t_avg   +   T_verify   +   T_waste
```

| 项 | 含义 | XMCL 对应机制 | 当前项目状况 |
|---|---|---|---|
| `C_eff` | **有效并发数** | 停滞看门狗 + 无进展快速换源 | ❌ 卡死源会吃光固定线程池 → `C_eff → 0` |
| `t_avg` | 单文件平均耗时 | 最优停止 / 速度模型 | ⚠️ 45s 固定超时，慢源无差别 |
| `T_verify` | 校验总耗时 | `validatedAt` 时间戳快路径 | ❌ 每次启动全量重算 SHA-1 |
| `T_waste` | 白扔的时间 | 熔断 + URL 轮换 + 退避 | ⚠️ 有健康表，但冷却期内完全不试 |

**四项里有三项是当前项目的短板**，所以混合方案的收益是相乘的：

| 场景 | 主要改善项 | 预期 |
|---|---|---|
| 首次全量、源健康 | `t_avg` 略微、`C_eff` 稳定 | 1.1~1.5× |
| **源不稳定 / 有死源** | **`C_eff` 不被吃光**（P0） | **2~10×，或从失败到成功** |
| 二次补全 / 修复 | **`T_verify` 归零**（P1） | **5~20×** |
| 大文件 | 跨源 Range 分片（P2） | 1.5~3× |
| 白扔的重复请求 | `T_waste`（P0/P1） | 省掉成片 0 B / 404 往返 |

## 3. 混合机制详解（8 项）

按"混合了什么"组织。每项给：动机 → 混合方式 → 改动点 → 开关 → 验收。

### M0 ★★★ 修正资产对象镜像 URL —— ✅ **已实施（根因修复，收益最大）**

**动机**：排查「BMCLAPI 一直返回 404 / 0 字节」时，先入为主地把根因归为「镜像不提供该路径」，
于是做了 `SourceHealth` 熔断去"跳过坏地址段"。**真正原因是本项目自己把 URL 拼错了**：

```
官方    https://resources.download.minecraft.net/2d/2d888ac14e51d7cab64b5e735456d25bf000720e  → 200, 605451 B
BMCLAPI https://bmclapi2.bangbang93.com/assets/2d/2d888ac14e51d7cab64b5e735456d25bf000720e  → 200, 605451 B  ✅
BMCLAPI https://bmclapi2.bangbang93.com/assets/2d/2d888ac14e51d7cab64b5e735456d25bf000720e     → 404            ❌ 旧代码
```

BMCLAPI 的 assets 端点**完全镜像官方目录结构**。旧模板 `.../assets/%s` 只能填裸 hash，漏掉前两位目录。

**修复**：模板改 `%s/%s`；调用方传完整 asset object location（`firstTwo + "/" + hash`）；
接口 Javadoc 写清契约（参数是 location 不是裸 hash）；三个 provider 加「误传裸 hash 自动补前两位」容错。

**收益**：镜像源从"每个资产都失败一次"变为"直接命中"——**每个资产省一次往返**，
且「镜像优先」的默认配置第一次真正可用（此前镜像形同虚设，全靠熔断后回落官方源）。

> **方法论教训（比修复本身更重要）**：看到「某个源全线失败」时，**先拿官方地址做同源对照，
> 确认 URL 是否拼对**，再决定是"源的问题"还是"自己的问题"。
> 否则会用一层熔断逻辑，把一个两行就能修好的 Bug 永久掩盖掉 —— 这次差点如此。

### M1 ★ 停滞看门狗 + 现有超时分层 —— **P0，最高优先**

**动机**：这是「后期特别慢」的根因。已实测确认两个事实：
1. `HttpRequest.timeout` **不覆盖正文读取**（服务端发完头卡住时，`timeout=2s` 的请求仍能读满 60s）；
2. `Thread.interrupt()` **打断不了**阻塞中的正文 `read()`（实测 120s 未返回）。

所以必须在**阻塞之外**做独立计时，并把"卡死"翻译成一个可被候选循环处理的失败。

**混合方式**：
- 新增 `ReadWatchdog`（独立守护线程），分别计 **TTFB 期限**与**中途停滞期限**；
- 现有 `REQUEST_TIMEOUT_SEC`（45s）**保留但降级为纯兜底**，提到 **60s**，关键词从"主判定"改为"最后防线"；
- 超时判定不再依赖它 —— 停滞看门狗通常 5s 内就终结一次尝试，45s/60s 几乎永不触发。

**关键实现决策（重要）**：不能再用 `worker.interrupt()`（已证无效）。**M1 已实施，最终选定的机制是换掉传输层**：

| 方案 | 实测结果 |
|---|---|
| A1 `Thread.interrupt()` | ❌ 阻塞中的 `read` 120s 未返回 |
| A2 看门狗线程 `close()` 掉 body 流 | ❌ 无法唤醒 `read`（180s 未返回） |
| A3 `BodyHandlers.ofFile` + `request.timeout` | ❌ timeout 不覆盖正文阶段 |
| A4 `sendAsync` + `future.cancel(true)` | ❌ `cancel()` 返回 false，传输照旧挂着 |
| **A5 `HttpURLConnection.setReadTimeout`** | ✅ **3.079s 抛 `SocketTimeoutException`** |

**结论：`java.net.http.HttpClient` 没有任何办法终结卡死的正文读取。** 因此补全的**文件正文传输**改用 `HttpURLConnection`（其 `setReadTimeout` 是**单次 read 间隔**语义，不是文件总时长），`HTTP_CLIENT` 仍保留给元数据 / 版本 JSON / SHA-1 探测。

**改动点**：
- `GameResourceCompleter.downloadFile`（`:974`）：包一层看门狗生命周期；
- 新增 `download/ReadWatchdog.java`（或并入 `download.mod`）；
- `REQUEST_TIMEOUT_SEC`（`:90`）默认值 45 → 60，文档同步。

**开关**：
```
DownloadStallTimeoutSec      默认 5    0 = 关闭看门狗
DownloadTtfbTimeoutSec       默认 5    0 = 关闭
DownloadRequestTimeoutSec    默认 60   （纯兜底）
```
（沿用已建好的 `DownloadSettings` 承载 + 设置页「高级下载设置」）

**验收**：
- 造一个"发完头就卡住"的测试服务器，补全能**在 5~8s 内换源**并最终成功（当前会一直挂着）；
- 日志出现明确的 `源卡死（停滞 5s），换源重试: <url>`；
- 稳定网络下正常补全**不出现任何停滞中止**（0 误杀）。

**风险**：误杀慢但正常的连接 → 用 `warmup`（首字节后 2.5s 内不判慢）+ **仅对"可换源"候选启用**（见 M3）缓解。

### M2 ★ 校验三级缓存 + 现有 `VerifySettings` 分层 —— **P1**

**动机**：`T_verify` 是二次补全的主要成本。当前 `GameResourceCompleter.isFileValid`（`:804`）对**每个文件**算 SHA-1。

**混合方式**：把 XMCL 的 `validatedAt` 塞进现有 `VerifySettings` 的判定链，**作为新的一级插在"大小比对"与"算哈希"之间**，不动 `FastVerify` 的语义：

```
现有：FastVerify?(有size→信) : SHA-1
混合：FastVerify?(有size→信)
      : (mtime ≤ 上次通过时间? 信)          ← 新增，比 SHA-1 便宜几个数量级
      : SHA-1
```

**持久化**：一份 `{gameDir}/.cache/verify-state.json`，记录 `path → {size, mtime, validatedAt}`。

**关键设计**：
- **只记录"校验通过"的时间戳**；
- 下载写盘后**必须更新该条目的 mtime/timestamp**，否则下次会误信；
- 文件被外部修改（mtime 变新）→ 自动回落 SHA-1，安全；
- 下载完成后的校验（`downloadFile` 里那次 SHA-1）**不受此影响** —— 新下载内容一律全量校验，这正是 XMCL `trustExistingSize` 注释强调的语义。

**改动点**：
- `GameResourceCompleter.isFileValid`（`:804`）、`downloadFile` 成功分支；
- 新增 `download/mod/VerifyStateCache.java`；
- `VerifySettings` 增加第 4 个开关 `VerifyStateCache`（默认开）。

**开关**：
```
VerifyStateCache   默认 true   设置 → 高级设置（与现有三个校验开关同页，AdvancedPage.java:195-217）
```

**验收**：
- 首次补全后，二次补全的**校验阶段耗时下降 > 90%**（日志里"校验中: x/y"段）；
- 手动改坏一个文件后，仍能被检出并重下；
- 关掉开关后行为与当前完全一致。

**✅ 已实施，实测结果**（1500 文件 × 320KB ≈ 468MB，JIT 预热后 3 轮中位数）：

| 路径 | 耗时 |
|---|---|
| 全量 SHA-1（关闭缓存） | **1761 ms** |
| 缓存命中（只 stat） | **186 ms** |
| **提速** | **9.5×**（468MB 完全不必读；收益随数据量线性增长） |

**实施中踩到并修掉的一个真实缺陷**（务必保留该设计）：初版判据写成
`mtime <= validatedAt + 2s容差`，实测发现**文件改写后仍然命中**。根因是登记时
`validatedAt = max(mtime, now)` 会比文件 mtime 晚几十到几百毫秒，随后几百毫秒内的改写
落进了容差窗口。改为**记录文件自身 mtime + 精确比较（容差 0）**后，14 项行为/安全探针全通过。
教训：时间型缓存判据不要用"当前时刻 ± 容差"，要用被验证对象自身属性做精确比对。

### M3 ★★ 无进展 / 慢 分流 + **最后候选源 committed** —— **P0，防反模式 A**

**动机**：当前 `downloadSingleAsset`（`:858`）的候选循环对**所有**候选源一视同仁。当唯一可用的官方源慢时，会被反复判定失败。

**混合方式**：在候选循环里引入 XMCL 的 `committed` 概念：

```
遍历候选：
  若 该候选是「最后一个可用候选」：
      进入 committed 模式 → 不受停滞看门狗的中止，只受真实网络错误影响
  否则：
      正常判定（停滞/超时/404 都可换源）
```

**为什么必须**：XMCL 原文（`download.ts:558-561`）——
> *The re-roll budget is spent. A slow-but-working connection is never a hard failure on the last source — commit to finishing.*

**改动点**：`downloadSingleAsset`（`:821-869`）候选循环；与 M1 的看门狗开关联动。

**开关**：`DownloadCommitLastSource` 默认 true。

**验收**：把主源限速到极慢、备用源正常 → 仍能下完（当前可能在主源上反复失败直到整批超时）。

### M4 ★★ 半开探测 + 反向收敛 —— **P1，修 `SourceHealth` 的两个逻辑漏洞**

**动机**：已实现的 `SourceHealth` 有两个缺口：

| 缺口 | 现状 | XMCL 做法 |
|---|---|---|
| **冷却期内完全不试** | 拉黑后 60~120s 内一次都不试，源恢复了也要等满 | **半开探测**：期间每 24 个请求放 1 个，成功立即闭合 |
| **熔断把流量赶到同样死的保底源** | 无处理 | **反向收敛**：保底源也不给数据 → 关闭熔断器，重新考虑镜像 |

**混合方式**：两处逻辑补进 `SourceHealth`，与现有三类计数（404 / 超时 / 空正文）共存：

```java
isBlocked(url):
  若 key 已拉黑:
     若 冷却到期 → 解禁（现有逻辑）
     否则:
        probeTick = (probeTick + 1) % cbProbeEvery   // 默认 24
        if (probeTick == 0) return false             // 放行一次探测 ← 新增
        return true

recordSuccess(url):
  ...（现有清零）...
  // 探测成功 → 闭合熔断；这是现有逻辑已有的部分，需要确认半开路径也走到这里
```

反向收敛放在 `GameResourceCompleter` 层（因为它知道"哪个是保底源"）：
```
若 健康表处于拉黑状态 且 本次失败同样"几乎没数据" 且 失败源是官方保底源:
    → SourceHealth.clearAll()    // 镜像的"下一个 assignment"可能比死掉的官方源更快
```

**改动点**：`download/mod/SourceHealth.java`（新增 `cbProbeEvery` 与 half-open 分支、新增 `clearAll()`）；`GameResourceCompleter` 在失败分类处调用收敛。

**开关**：`DownloadSourceHealthProbeEvery` 默认 24（1 = 永远探测，即禁用跳过）。

**验收**：
- 让镜像"坏 10s 后恢复"：半开探测能在**冷却期内**切回镜像（日志出现"镜像地址段已恢复"早于冷却结束）；
- 让镜像与官方源同时不可用：不会出现"两边都不试"的死锁。

### M5 ★ 失败文件级重排 + 候选轮换 + 退避抖动 —— **P1**

**动机**：当前 `downloadConcurrently`（`:679-706`）是"整批跑一遍，失败只计数不重试"；XMCL 是"只重排失败项 + 每轮轮换候选 + 指数退避"。

**混合方式**：保留当前的**批内并发**结构，在其外面加一层**收敛重试轮**：

```
round = 0
pending = 初始待下载集合
while pending 非空 且 round < maxRounds(默认 3):
    downloadConcurrently(pending)          // 现有实现，直接复用
    pending = 本轮失败的
    对每个失败项：candidateList 左移一位    // ★ XMCL installManifest.ts:229-231
    sleep(min(retryMax, retryBase * 2^round) × (0.75 + rand×0.5))   // ★ 退避+抖动
```

**与现有 `SourceHealth` 的关系**：两者**互补不冲突** —— `SourceHealth` 决定"候选是否被跳过"，轮换决定"未被跳过时先试哪个"。轮换会让**每轮的首选源不同**，天然避开"整批都先撞同一个慢源"。

**改动点**：`downloadConcurrently`（`:660-745`）外层；`updateBatchProgress` 的 `total` 口径需要包含重试，避免进度回退。

**开关**：`DownloadRetryRounds` 默认 3；`DownloadRetryBaseMs` 默认 500；`DownloadRetryMaxMs` 默认 4000。

**验收**：模拟"某源 30% 概率失败" → 最终失败数显著下降；进度条**单调不回退**。

### M6 ★★★ 跨镜像 Range 分片 —— **P2，顺势利用现有结构**

**动机**：源不稳定时单连接吞吐受限。XMCL 的做法是"每个分片是独立请求 → 签名 CDN 给每个请求独立重定向 → 天然跨镜像并行"。

**混合方式（本项目的优势路径）**：**不需要改成独立请求**。现有 `DownloadFileTask` 已经具备：
- 分块写**独立 `.part` 文件**（`DownloadPiece`）；
- `tryBeginThread()` 动态再分裂；
- 每分块 `setMountedSource(src)` —— **每块可挂不同源**。

只需要把"分裂时选源"从"选下一个可用源"改成**"按速度模型挑最快的可用源"**，即可实现跨源并行分片：

```
tryBeginThread():
  src = chain.nextSource(false)            // 现状：环形取下一个
  → chain.fastestAvailableSource()         // 改为：按 EWMA 速度排序取最快且未被拉黑的
```

**依赖**：需要 M7（速度模型）先落地，否则"最快"无从判断。**因此本项排在 M7 之后。**

**改动点**：`download/mod/DownloadSourceChain.java`（新增按速度选源）、`DownloadFileTask.tryBeginThread()`。

**验收**：双源场景下，抓包/日志显示**同一文件的不同分块打到不同源**。

---

### M7 ★★ 按源 EWMA 速度模型 + 跨会话持久化 —— **P2**

**动机**：当前 `DownloadCoordinator.observedBps` 是**全局单一值**，`GlobalSpeedLimiter.isBelowLowSpeedThreshold` 用**固定慢速线**。无法回答"换一个源会不会更快"。

**混合方式**：引入 XMCL 的双层 EWMA，但**按本项目的源粒度**（本项目没有"签名重定向到镜像"这层，源就是 URL 的 host）：

| 模型 | 作用 |
|---|---|
| `global.score` | 一次"换源"能达到的吞吐期望 |
| `hosts[host].score` | 每个源的历史表现 |

配合 XMCL 的**最优停止**规则替代固定慢速线：

```
remaining = total - done
overhead  = 换源成本（本机估算，默认 600ms）
vMin      = remaining / (overhead + remaining / global.score)
若 speed < vMin × 0.85 → 中止换源
```

特点：**剩余量越大越愿意换源**，剩余量小时即使慢也忍着 —— 精准命中"最后几个文件特别慢"。

**持久化**：`{gameDir}/.cache/source-speed.json`，10s 防抖保存，跨会话复用。

**改动点**：新增 `download/mod/SourceSpeedModel.java`；`GlobalSpeedLimiter.isBelowLowSpeedThreshold` 改为查模型（保留固定线作为模型未置信时的兜底）；`DownloadSettings` 增加 `DownloadBestStopEnabled` / `DownloadReconnectOverheadMs`。

**验收**：人为让 A 源比 B 源慢 3×，跑一轮后第二轮（重启后）**首选即为 B 源**。

---

### M8 结构校验兜底 validator —— **P1，低成本**

**动机**：无 SHA-1 时（`downloadFile` 的通用路径、`AssetDownloader`、客户端 JAR 兜底），当前只比大小或直接放行，无法识别"返回了 HTML 错误页"。

**混合方式**：复用现成的 `download/mod/FileVerifier.isJson(Path)`（已实现），补一个 `isZip(Path)`，形成 validator：

| validator | 判据 | 用于 |
|---|---|---|
| `file` | `stat` 成功 | 现状 |
| `json` | `FileVerifier.isJson`（已有） | 版本 JSON、asset index |
| `zip` | zip 可打开且至少一个非目录条目 | 库、客户端 JAR、整合包 |

**改动点**：`download/mod/FileVerifier.java` 补 `isZip`；`GameResourceCompleter.isFileValid` 在无 hash 分支后追加 validator 判定。

**开关**：`DownloadValidatorEnabled` 默认 true。

**验收**：把某 URL 指向一个返回 HTML 的服务器 → 能被判失败而不是写进 `libraries/`。

## 4. 分期与依赖

```
P0（治症状：不再越下越慢）
  M1 停滞看门狗 ──┬── M3 committed last source
                  │        （M1 的看门狗必须知道"最后候选要忍"）
                  └── M4 半开探测 + 反向收敛
                            （同样依赖"无进展"这个分类）

P1（提速二次补全 + 减少白扔）
  M2 校验三级缓存（独立，无依赖）
  M5 失败重排 + 轮换 + 退避（独立）
  M8 validator（独立）

P2（稳态提速）
  M7 速度模型 ──→ M6 跨源分片（M6 依赖 M7 的"最快源"判据）
```

**依赖关系说明**：
- **M1 是 P0 的地基**，M3/M4 都建立在"能把失败区分成无进展 / 慢 / 错误码"之上。
- **M2/M5/M8 互相独立**，可并行开发，互不阻塞。
- **M6 依赖 M7** —— 没有速度模型就没有"最快源"可挑。

**建议实施顺序**：M1（含技术验证）→ M3 → M4 → M2 → M5 → M8 → M7 → M6

## 5. 机制交互矩阵（避免互相打架）

| | M1 看门狗 | M2 校验缓存 | M3 committed | M4 半开 | M5 重排 | M7 速度模型 |
|---|---|---|---|---|---|---|
| **M1** | — | 无交互 | **M3 是 M1 的安全阀**：无 M3，M1 会掐死唯一可用源 | 无交互 | 无交互 | M7 的最优停止**取代** M1 的固定慢速线；停滞线保留 |
| **M2** | 无 | — | 无 | 无 | 无 | 无 |
| **M3** | 见上 | 无 | — | 无 | 无 | 无 |
| **M4** | 无 | 无 | 无 | — | **M5 轮换 + M4 探测协同**：轮换给出新首选，探测保证不永久放弃 | 无 |
| **M5** | 无 | 无 | 无 | 见上 | — | M7 影响"轮换后的首选"排序 |
| **M7** | 见上 | 无 | 无 | 无 | 见上 | — |

**三个必须注意的交互**：

1. **M1 × M3（强制）**：加了停滞看门狗但没加 committed 保护 → 官方源慢时会永远下不完。**必须同批上线。**
2. **M1 × M7（阶段性）**：M7 落地后，固定慢速线（`GlobalSpeedLimiter.LOW_SPEED_THRESHOLD_BPS`）应改为"模型未置信时的兜底"；**停滞线（M1）与慢速线（M7）职责不同，都要保留**。
3. **M2 × 现有 `FastVerify`（层级）**：`FastVerify` 是用户显式选择"不要哈希"，优先级**高于** M2 的缓存；M2 只在 `FastVerify` 关闭时生效。这样不破坏现有设置页语义。

## 7. 验收与度量（怎么证明真的快了）

**基线**：当前版本跑一次「首次全量补全」与「二次补全」，记录：

| 指标 | 采集方式 |
|---|---|
| 总耗时 | 日志起点/终点 |
| 平均下载速度 | `DownloadCoordinator.getObservedBps()` |
| **有效并发数** | `DownloadCoordinator.getActiveThreads()` 采样（★ 关键指标） |
| 失败数 / 白扔请求数 | `SourceHealth.getSkippedRequests()` + 失败计数 |
| 校验阶段耗时 | 日志"校验中: x/y"段 |
| **停滞中止次数** | M1 新增计数（★ 关键指标） |

**关键判据**：**有效并发数在补全后期是否保持稳定**。当前版本它在后期塌陷，这是"越下越慢"的量化特征；P0 做完后这条曲线应当接近水平。

**回归**：更新下载、Java 下载、陶瓦联机下载、模组/整合包安装（这四条走的是旧链路，不在本方案范围内）。

## 8. 明确**不建议**混合的部分

| XMCL 机制 | 为什么不抄 |
|---|---|
| 三段式 Materialize 事务 + 回滚 | MC 文件补全是幂等覆盖写，事务开销 > 收益 |
| 签名 CDN 的"重掷同一 URL 换镜像" | 本项目没有签名重定向层，源是固定 URL，"重掷"等于重试同一地址，无意义 |
| `InstallPlan` 三段式 DAG 编排 | 本项目已有等价骨架（`InstallPlan`/`PlanStage`），但**接线**是独立议题，不属提速 |
| 按最终镜像主机的声誉 | 同上，本项目没有镜像重定向层，按 host 记即可 |
| 跨会话 EWMA 的 6h 半衰期 | 本项目源集合更少且更稳定，2h 更合适（可调，不必照搬） |
