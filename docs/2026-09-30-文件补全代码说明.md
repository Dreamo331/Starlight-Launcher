## 1. 一句话结论

**「文件补全」的真正执行体是 `GameResourceCompleter`，它是一个自包含的三阶段补全器：自建 `HttpClient`、自建线程池、自建校验与回退逻辑。**

`com.example.starlight.download.mod` 那一整套提速链路（`DownloadCoordinator` / `DownloadFileTask` / `DownloadPiece` / `LocalFileReuse` / `InstallPlan` / `MetaDiskCache`）目前**只被通用单文件下载 `DownloadService.downloadFileAsync` 使用**，而该方法在 `src/main` 内**没有业务调用者** —— 也就是说 mod 链路处于“已建成、业务未接入”状态。

补全与 mod 链路目前仅有的交集是两处：

| 交集点 | 位置 | 作用 |
|---|---|---|
| `SourceHealth` | `GameResourceCompleter.java:862`（跳过候选）、`:1045`（记 0 字节）、`:1062`（记成功）、`:1076`（记超时）、`:1201`（记 404） | 容器级「主机 + 路径前缀」健康表，避免镜像死端点被逐文件白试 |
| `DownloadSettings.getDownloadThreads()` | `GameResourceCompleter.java:669`（下载池）、`:733`（校验池） | 并发线程数取自「设置 → 下载 → 并发下载数」 |

## 5. 并发模型

`downloadConcurrently` 有一对重载：`:646`（8 参，指定 primary/fallback 模板）与 `:728`（7 参，直接委托前者并写死资产模板）。

流程（`:646-724`）：

```
1. 校验分流  :651-657
   并行开 → verifyInParallel(:732)   并行开 → 校验池 :733-737（线程数 = min(任务数, DownloadSettings.getDownloadThreads())，上限 1）
   并行关 → verifySerially(:776)     串行
2. 分拣结果  alreadyDone（已存在）/ pending（待下载）
3. 下载池    :673 Executors.newFixedThreadPool(threadCount)
             :669 threadCount = min(needDownload, DownloadSettings.getDownloadThreads())，下限 1
4. 逐任务提交 CompletableFuture.runAsync(task, executor)  :679-692
5. 等待      :694 CompletableFuture.allOf(...).get(30, TimeUnit.MINUTES)   ← 30 分钟硬超时
6. 收尾      :704-713 executor.shutdown() + awaitTermination(5s) → 超时 shutdownNow()
```

**线程池没有命名**（`:673` 直接 `Executors.newFixedThreadPool(threadCount)`，未传 ThreadFactory）—— 这解释了日志里 `pool-6-thread-8` 这类线程名，以及为何找不到业务语义的线程名。

对比：校验池 `:732-737` **有**命名（`"verify-worker"`，守护线程）。

**进度聚合**（`updateBatchProgress`，`:1128-1135`）：
```java
percent = total > 0 ? Math.min(completed * 100 / total, 100) : 0;
msg     = String.format("%s: %d/%d (失败: %d)", label, completed, total, failed);
```
`completed` 初值 = 已存在文件数（`:658`、`:674`），因此**校验段与下载段共用同一个 0~100 子区间，整体单调递增**，不会因“先校验后下载”而回退。

**校验段的进度**：`verifyInParallel` `:750-754` 与 `verifySerially` `:788-790` 都用 `done*100/total`，并用 `lastReportedPct` 去重（只在整数百分比变化时才回报）。

### 5.1 文件有效性判定 `isFileValid`

判定顺序按**成本递增**排列，任一级否定即返回 `false`：

```java
// 1) 文件不存在                                  → 无效（并作废缓存条目）
if (!Files.exists(file)) { verifyCacheInvalidate(file); return false; }

// 2) 大小不符                                    → 无效（必重下，不看缓存）
if (task.size > 0 && Files.size(file) != task.size) { verifyCacheInvalidate(file); return false; }

// 3) FastVerify 开启且有 size                    → 有效（用户显式选择"不要哈希"，优先级最高）
if (VerifySettings.isFastVerifyEnabled()) { ... verifyCacheMark(file); return true; }

// 4) ★ M2 校验状态缓存命中（size + mtime 都没变） → 有效，跳过哈希计算
if (cache != null && VerifySettings.isStateCacheEnabled() && cache.isFresh(file)) return true;

// 5) 否则算 SHA-1 比对（通过则登记缓存，失败则作废）
return verifySha1(file, task.hash);
```

**第 4 级是 M2 的收益点**：二次补全时绝大多数文件命中它，校验阶段从"读完全部文件算哈希"降到"只 stat 一遍"。详见 §10.4。

### 5.3 具体 HTTP 动作 `downloadFile`（`:974` 起）

> **重要**：文件正文传输**不使用** `HttpClient`，而是用 `HttpURLConnection`。原因见 §5.4。

| 环节 | 要点 |
|---|---|
| 取消前置检查 | `isCancelled(cancel)` |
| 建连 | `HttpURLConnection`；`setConnectTimeout(DownloadSettings.getConnectTimeoutMs())` |
| **停滞看门狗** | **`setReadTimeout(DownloadSettings.getStallTimeoutMs())`** —— 单次 read 无字节即抛 `SocketTimeoutException`，这是"卡死源"能被及时换掉的**唯一有效机制** |
| 重定向 | 手动跟随，最多 `MAX_REDIRECT_HOPS = 5`；`Location` 含非 ASCII 时经 `sanitizeRedirect` 只对非 ASCII 字节做百分号编码 |
| **续传** | 已有 `totalRead > 0` 时带 `Range: bytes=<totalRead>-`（content-addressed 资源，任何镜像字节一致） |
| 发送日志 | 在真正发请求**之前**记（否则与响应日志同毫秒相邻，读起来像发了两次） |
| 非 2xx | 记响应日志；`recordHttpFailure(url, code)` → 404/410 计入 `SourceHealth`，其余不计数 |
| 临时文件 | `uniqueTempFile(target)` = `<name>.<pid>-<seq>.tmp` |
| 流式写盘 | 缓冲 `BUFFER_SIZE = 64 * 1024`；每读一块都检查取消 |
| **0 字节判定** | `totalRead == 0` 且该文件应有内容（给了期望 SHA-1）→ 判失败、`recordEmpty`、换源。在算 SHA-1 **之前**，省掉一次无用的全文件哈希 |
| 长度校验 | `contentLength > 0 && totalRead != contentLength` → 判失败 |
| SHA-1 校验 | 失败时先看目标文件是否已就绪（直接采用），否则删临时文件返回 false |
| 记成功 | `recordSuccess`（清零三类计数并解禁）后 `Files.move(ATOMIC_MOVE)` |
| 停滞/IO 异常 | `InterruptedIOException`（即 `SocketTimeoutException`）→ 明确记为**源停滞**、`recordTimeout`、删临时文件、返回 false |

### 5.3.1 「卡在后期」的两个静默成因（已修）

用户在补全后期观察到"卡住不动"。排查后定位到两处**没有进度反馈**的同步工作，它们都排在下载阶段之后，此时进度条已经到 100%：

**成因一：虚拟资源整理（`handleVirtualResources`）—— 主因**

旧版（1.6 及以前）的 legacy 索引若带 `virtual` 标志，全部资产下载完成后会把每个对象**逐文件同步复制**到 `assets/virtual/legacy`。旧实现：

```java
// 修改前：没有 progress 参数、不检查 cancel、没有任何中间日志
private static void handleVirtualResources(String gameDir, Path indexFile) {
    for (Map.Entry<String, JsonElement> entry : objects.entrySet()) {
        ...
        Files.copy(source, target);      // 上万个文件，逐个复制
    }
    log.info("Virtual resource copy finished: {} files", copied);   // 只有结束才有一行日志
}
```

实测这段复制耗时（20KB/文件，贴近 legacy 资产均值）：

| 文件数 | 耗时 | 用户看到的现象 |
|---|---|---|
| 2 000 | 4.2 s | 进度条不动 4 秒 |
| 10 000 | 15.5 s | 进度条不动 15 秒 |
| 20 000 | **29.4 s** | 进度条不动近半分钟 |

**修复**：改成 `handleVirtualResources(gameDir, indexFile, progress, cancel)` —— 映射到 **95~100%** 区间上报，每 2 秒或每 200 个文件回报一次（`正在整理虚拟资源目录: 3/12000 已检查，210 已复制`），并在循环内检查取消。用户现在能看出"在推进、推进了多少"。

**成因二：批处理等待没有反馈**

`downloadConcurrently` 末尾的 `CompletableFuture.allOf(...).get(30, MINUTES)` 在超时（`TimeoutException`）时只记一行 `log.error`，用户侧完全没有反馈。**修复**：新增批处理看门狗（`sl-batch-watchdog`，每 20 秒检查），若**超过 60 秒没有任何文件完成**就打一行点名日志：

```
[资产文件] 已 73s 无文件完成（完成 412/1200），仍在等待: 
  minecraft/sounds/ambient/cave/cave1.ogg, minecraft/textures/gui/widgets.png, …
```

配合 M1 的停滞看门狗（`源停滞（15s 无数据），换源重试: <url>`），后期卡住能直接定位到**是卡在下载、卡在哪个文件、还是卡在整理**。

**成因三：坏/空资产索引被静默接受（已修）**

`downloadAssetIndex` 原来在 SHA-1 校验失败时只 `log.warn` 并**继续使用坏索引**：

```java
if (sha1 != null && !verifySha1(targetFile, sha1)) {
    log.warn("Asset index SHA-1 verification failed, keeping downloaded file: {}", assetId);
}
```

空索引 → `objects` 为空 → 报告"补全完成"但**一个资产都没下**（静默退化，不是卡住但更难查）。**修复**：空文件 / 非合法 JSON（`FileVerifier.isJson`，可挡 HTML 错误页）/ SHA-1 不符 **一律判失败并删除**，让上层重试。

### 5.4 超时语义（本项目最容易踩的坑，已实测确认）

补全里有两个**从未被使用**的常量：`CONNECT_TIMEOUT_SEC`（`:79`）与原来的 `READ_TIMEOUT_SEC`。真正生效的读超时只有一条路径：**`HttpURLConnection.setReadTimeout`**。

**实测结论：`java.net.http.HttpClient` 没有任何办法终结卡死的正文读取。** 用一个「发完响应头 + 8KB 后卡住不关连接」的服务器逐一验证：

| 方案 | 结果 |
|---|---|
| ① `HttpRequest.timeout(2s)` | 拿到响应头后，正文读取**一直阻塞到 60s** 对端关闭 —— **超时没触发** |
| ② `BodyHandlers.ofFile` + `timeout(3s)` | 同样不覆盖正文阶段，一直挂到对端关闭 |
| ③ `sendAsync` + `future.cancel(true)` | `cancel()` 返回 **false**，传输照旧挂着；20s 后 reader 仍未退出 |
| ④ 看门狗线程 `close()` 掉 body `InputStream` | **无法唤醒**阻塞中的 `read()`（180s 未返回） |
| ⑤ `Thread.interrupt()` 工作线程 | 同样**打断不了**（120s 未返回） |
| ⑥ **`HttpURLConnection.setReadTimeout(3s)`** | ✅ **3.079s 抛 `SocketTimeoutException: Read timed out`** |

推论：
- `HttpRequest.timeout` 只在「到点还没拿到响应头」时生效；**一旦响应头到手，正文想读多久读多久**。
- `java.net.http.HttpClient` **没有 socket read timeout 的概念**，也没有 API 可设。
- 因此补全的**文件正文**改用 `HttpURLConnection`；而 `HTTP_CLIENT` 仍留给元数据 / 版本 JSON / SHA-1 探测等非正文场景。

**业务后果（修前）**：一个「连得上、开始能下、然后挂住不动」的源会把一个工作线程**无限期**占住。而 `downloadConcurrently` 用的是**固定大小**线程池，所以前期快、后期卡死源累积吃掉线程 → **越下越慢**。

**已做的收敛**：
1. 文件传输改走 `HttpURLConnection.setReadTimeout`（默认 **15s**，可配）；
2. **最后候选源放宽 4 倍**（`LAST_RESORT_TIMEOUT_FACTOR`）：依据 XMCL 的 <i>"a slow-but-working connection is never a hard failure on the last source — commit to finishing"</i>，慢但能用的最后一条路不该被反复掐断；
3. 停滞同时计入 `SourceHealth`（`recordTimeout`），反复停滞的地址段会被跳过。

> 注意 `setReadTimeout` 是**单次 read 间隔**语义，不是文件总时长 —— 慢但在持续推进的大文件不受影响，这是它与原来那个"整体超时"的本质区别。

## 8. 并发协调：`withCompletionLock`

```java

要点：
- **锁 key 只含 `gameDir`，不含版本** → 同一游戏目录下不同版本的补全会互相阻塞（保守但安全：避免并发写 `assets`/`libraries`）。

### 9.2 `SourceHealth`（容器级失败健康表）

文件：`download/mod/SourceHealth.java`

**解决的问题**：镜像某个地址段一旦持续失效，没有这层保护时**每个文件都要重新试一遍**，白付一次往返才回落官方源 —— 对上千个 assets + 几百个库就是成片的浪费。

> **⚠️ 这里曾经误判过一次根因，务必区分「代码写错 URL」与「镜像真的挂了」**
>
> 最初观察到的现象是 BMCLAPI 对每个资产都失败（成片 `404 | 数据包 0 B`），
> 当时把根因归为「镜像不提供该路径」，于是加了这张健康表来"跳过坏地址段"。
> **真正的原因是本项目自己把 URL 拼错了**：资产对象请求漏掉了 sha1 前两位目录。
> 实测对照（hash=`2d888ac1…`）：
> ```
> 官方    https://resources.download.minecraft.net/2d/2d888ac…        → 200 (605451 B)
> BMCLAPI https://bmclapi2.bangbang93.com/assets/2d/2d888ac…       → 200 (605451 B)  ← 正确
> BMCLAPI https://bmclapi2.bangbang93.com/assets/2d888ac…          → 404            ← 旧代码
> ```
> 根因已修（见 §9.3）。**教训：看到"某个源全线失败"时，先拿官方地址同源对照验证 URL 是否正确，
> 再决定是"源的问题"还是"自己的问题"** —— 否则会用一层熔断把一个两行就能修好的 Bug 永久掩盖掉。
> 健康表本身仍有价值：镜像**真的**挂掉时它负责整体跳过。

**三类失败各自独立计数**（这是它的核心设计）：

| 失败类型 | 触发 | 阈值 | 冷却 | 为什么单独计数 |
|---|---|---|---|---|
| 404 / 410 | 状态码 | 8 | 120s | 「这段路径没有」，代价是一次快速往返 |
| 请求超时 / 停滞 | `SocketTimeoutException` | 3 | 60s | 「连上了但不干活」，占满线程一整个超时周期，代价最大 |
| 200 但 0 字节 | 正文为空 | 5 | 90s | 镜像活着会持续复现；且不带 `Content-Length` 时长度校验拦不住 |

**为什么按路径前缀而非整个 host**：404 的语义是「这段路径在镜像上不存在」，只拉黑整个 host 会连带干掉同机器上**正常**的 `/libraries/`、`/version/`、`/maven/`。

**接入点**：
- `GameResourceCompleter.java:862` —— 候选循环跳过被拉黑地址段
- `GameResourceCompleter.java:1201` —— 非 2xx 时按 404/410 上报
- `GameResourceCompleter.java:1045` —— 「200 但 0 字节」上报
- `GameResourceCompleter.java:1076` —— 请求超时上报
- `GameResourceCompleter.java:1062` —— 成功（且 SHA-1 通过）后上报解禁
- `AssetDownloader.java` —— 同一套上报与跳过（含 0 字节判定）
- `DownloadSource.isAllowed()` —— mod 链路侧串联判定（域名熔断 + 文件级禁用 + 地址段健康）
- `DownloadPiece.java` —— 分块 404/410 上报

### 10.4 ★ 校验状态缓存 `VerifyStateCache`（M2）

文件：`download/mod/VerifyStateCache.java`。缓存位置：`{gameDir}/.cache/verify-state.json`。

**解决的问题**：`isFileValid` 原本对**每个**文件算一遍 SHA-1。二次补全/修复已有游戏时绝大多数文件其实没变，重算哈希纯属浪费 —— 对上千个 assets + 几百个库，这是二次补全里最大的一块 I/O。

**判据设计（关键）**：`markValidated` 记录**文件自身的 mtime** 与 size；`isFresh` 要求**两者精确相等**才算"没被动过"。

```java
// 登记：记录文件自身 mtime（不记录"当前时刻"）
entries.put(key, new Entry(size, fileMtime(file), System.currentTimeMillis()));

// 判定：精确相等才算命中
return Files.size(file) == e.size && Math.abs(fileMtime(file) - e.mtime) <= 0;
```

> ⚠️ **这里踩过一次真实的坑，务必保留注释**：最初写的是"比较当前时刻 + 2 秒容差"
> （`mtime <= validatedAt + tolerance`），结果实测发现**改写后仍然命中**。
> 根因：`validatedAt` 用 `Math.max(mtime, now)` 生成，会比文件 mtime 晚几十到几百毫秒，
> 于是**随后几百毫秒内发生的文件改写落进了容差窗口被错误信任**。
> 改为"记录文件自身 mtime + 精确比较"后，任何改动必然被发现（探针 14 项全通过）。
> 教训：**时间型缓存判据不要用"当前时刻 ± 容差"，要用被验证对象的自身属性做精确比对。**

**安全边界**：
- 只记录「校验通过」的时刻，**不记录失败**；
- 文件被外部修改 → mtime 变 → 自动回落完整哈希；
- 大小不符 / 文件被删 → 立即作废该条目；
- 缓存文件损坏或缺失 → 当空缓存处理，**绝不阻断补全**；
- 缓存键是**相对 gameDir 的路径**（不含绝对路径），目录迁移后仍可用。

**登记时机（两个都必须有，缺一会误信或失效）**：
| 时机 | 位置 | 原因 |
|---|---|---|
| 完整哈希校验通过 | `isFileValid` 第 5 级 | 这是缓存的主要来源 |
| **下载并校验通过后** | `downloadSingleAsset` / `downloadClientJar` | 否则新下载的文件不在缓存里，下次仍要算一遍哈希 |

**落盘**：`downloadConcurrently` 末尾调 `flushVerifyCache()`（assets/libraries/natives/legacy 四条路径都汇聚到这里），原子替换写入。

**实测收益**（1500 个文件 × 320KB ≈ 468MB，JIT 预热后取 3 轮中位数）：

| 路径 | 耗时 |
|---|---|
| 全量 SHA-1（关闭缓存） | `[1748, 1761, 1762]` ms → 中位数 **1761 ms** |
| 缓存命中（只 stat） | `[184, 186, 188]` ms → 中位数 **186 ms** |
| **校验阶段提速** | **9.5×**（省下约 1.58 s，且 468MB 完全不必读） |

> 绝对收益随数据量线性增长 —— 真实 `.minecraft/assets/objects` 常达 GB 级，
> 二次补全省下的时间是分钟级。小数据量下比例会低一些（被每文件固定开销摊薄）。

**关闭方式**：高级设置 → 「校验状态缓存」开关（`VerifyStateCache=false`），关闭后每次补全都做完整哈希校验。

## 12. `download.mod` 各组件接线现状

`download.mod` 包共 16 个类，**仅 `DownloadFileTask` / `DownloadPiece` / `DownloadCoordinator` / `DownloadSource*` / `SourceHealth` 处于活跃调用路径上**，且该路径的唯一入口 `DownloadService.downloadFileAsync`（`DownloadService.java:109-153`）在 `src/main` 内**无业务调用者**（grep `downloadFileAsync(` 仅命中定义与 `UIGeneralControlClass.java:1566` 这个同样无人调用的包装）。

| 类 | 状态 | 说明 |
|---|---|---|
| `DownloadCoordinator` | 已接线 | 被 `DownloadService` 与设置页（`setThreadLimit`）使用 |
| `DownloadFileTask` / `DownloadPiece` | 已接线 | 同上 |
| `DownloadSource` / `DownloadSourceChain` | 已接线 | 同上 |
| `HostPolicy` | 已接线 | 被 `DownloadFileTask.tryBeginThread` 判定单线程 host |
| `GlobalSpeedLimiter` | 已接线 | 令牌桶，默认不限速 |
| `RetryPolicy` | 已接线 | 连接超时 / 慢速掐线 / 合并退避 |
| `SourceHealth` | 已接线 | **补全链路也在用**（见 §9.2） |
| `FileVerifier` | 仅被未接线类引用 | 见 §12.1 |
| `LocalFileReuse` | **未接线** | 见 §12.1 |
| `MetaDiskCache` | **未接线** | 见 §12.1 |
| `InstallPlan` / `PlanStage` | **未接线（骨架）** | 见 §12.1 |
| `RangeNotSupportedException` / `SourceDisabledException` | 已接线 | mod 链路的控制流异常 |

### 12.1 未接线组件详情

**`LocalFileReuse`（`download/mod/LocalFileReuse.java`）**
- 设计意图：下载前扫描已有 MC 目录，按「同相对路径 + 同大小 + SHA1」复用已有文件，命中则**复制**到目标，**不进网络队列**（进度权重 0.2 而非 1.0）。
- 并发：每 40 个文件一个检查线程、最多 8 线程（`:27-30`）。
- **现状：无任何生产调用者** → 文档中「二次补全提速 5~20 倍」的能力**目前并未生效**。

**`MetaDiskCache`（`download/mod/MetaDiskCache.java`）**
- 小 JSON 磁盘缓存：按 URL 的 MD5 命名存 `{gameDir}/.cache/meta/`，TTL 1 天（`:28`），只存/取字符串，不解析 JSON。
- **现状：无生产调用者**。

**`InstallPlan` / `PlanStage`（`download/mod/InstallPlan.java`、`PlanStage.java`）**
- 设计意图：把「分析缺失 → 下载 → 校验 → 后处理」建模为带权重的阶段列表，`overallProgress = Σ(阶段进度 × 权重) / Σ权重`（`InstallPlan.java:36-47`）。
- `PlanStage.Type`：`ANALYZE / DOWNLOAD / VERIFY / POST`。
- **现状：无生产调用者** —— 补全的进度仍是 §7 的 `wrapProgress` 硬编码区间。

**`FileVerifier`**
- 只被 `LocalFileReuse`（同样未接线）引用；补全走自己的 `verifySha1`（§10.2）。

**`AssetDownloader` / `LibraryDownloader`**
- 仍可由 `DownloadService.downloadAssetIndexAsync`（`:48`）、`:60`、`:72` 及 `UIGeneralControlClass.java:1987-2012` 调用，但这两处包装**均无 UI 调用者**。
- 真实补全不经过它们；`AssetDownloader` 已接入 `SourceHealth` 以便将来启用时不重复踩坑。

## 13. 其它下载器接线现状

以下类**均未接入 `download.mod`**，各自使用独立的 HTTP 实现：

- `HttpDownloadEngine` 的镜像改写只对 `cdn.modrinth` / `edge.forgecdn` / `mediafilez.forgecdn` 生效（`:189-196`），候选为「MCIM 镜像优先（`:207` 经 `CDN_MIRROR_BREAKER.allowMirror()`）→ 官方直链兜底（`:211`）」。

- `JavaInstall.java:31-38` 硬编码 3 组「清华主源 + 华为云备用」；`:181-183` 只要文件已存在就跳过；`:253` 8KB 缓冲直写最终路径。
