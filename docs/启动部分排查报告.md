## 高优先级（会导致启动失败 / 数据异常）

### 1. Forge Modern 完全没有解析 `arguments.jvm`（结构性缺陷）

`ForgeModernLauncher.launch()` 里的 JVM 参数全部硬编码（`-DignoreList`、`-DmergeModules`、`-p`、`--add-modules`、3 组 `--add-opens/--add-exports`）。

但 Forge 1.17+ 的 version.json 本身带 `arguments.jvm` 数组，里面有**一堆本版本必需的** `--add-opens`、`--add-exports`、`-Dxxx` 和 `-p ${library_directory}/...`。当前代码一个都没读，只在 `buildGameArgsFromJson` 里读了 `arguments.game`。

后果：换一个 Forge 小版本，硬编码的 `--add-opens` 覆盖不全（比如新版本需要 `java.base/java.lang`、`java.base/java.nio` 等），`BootstrapLauncher` 直接起不来。`buildModulePath()` 动态扫出的 `-p` 也可能和 Forge 自带的 `-p` 不一致，尤其是 Forge 升级引导模块版本时。

正确做法：像 `buildGameArgsFromJson` 那样解析 `arguments.jvm`（替换 `${library_directory}` 等占位符后追加），硬编码部分作为兜底或删掉。同理 NeoForge 也依赖 `arguments.jvm`。

> 这是我认为最可能造成"某天换个 Forge 版本就启动不了"的根因。

### 2. 日志系统线程不安全（两处叠加）

`BaseLauncher`：
- `protected static final SimpleDateFormat LOG_TIMESTAMP` —— `SimpleDateFormat` 本身**非线程安全**，而它被 stdout 泵、stderr 泵、监控线程、主线程并发调用 `format()`。
- `writeLog` / `writeLogToFile` 里直接 `logWriter.write(...)`，`BufferedWriter` 也**非线程安全**，同样被上述 4 个线程并发写。

后果：长时间运行或 stderr 大量输出时，日志可能出现时间戳错乱、行交错、甚至偶发 `ArrayIndexOutOfBoundsException`（`SimpleDateFormat` 的经典并发崩溃）。

建议：`SimpleDateFormat` 改 `ThreadLocal` 或 `DateTimeFormatter`；日志写入加 `synchronized` 或改单线程日志队列。`FILE_TIMESTAMP` 只在 `initLogging` 用，问题小，但既然一起改可以顺手处理。

### 3. 新格式 natives jar 被错误地塞进 classpath

`getLibraries()` 的判定：
```java
boolean hasMainArtifact = lib.has("downloads") && lib.getAsJsonObject("downloads").has("artifact");
if (!hasMainArtifact) { /* 才检查 nativeOnly */ }
```

但 LWJGL 3（1.17+ 原版）的 natives 条目长这样：
```json
{"name":"org.lwjgl:lwjgl:3.3.1:natives-windows",
 "downloads":{"artifact":{"path":".../lwjgl-3.3.1-natives-windows.jar"}},
 "rules":[{"action":"allow","os":{"name":"windows"}}]}
```
它有 `downloads.artifact`，只不过 artifact **本身就是 natives jar**。当前逻辑 `hasMainArtifact=true` → 不进入 nativeOnly 检查 → `resolveLibraryPath` 返回 natives jar 路径 → 被加入 classpath。

后果：classpath 混入一堆 `*-natives-*.jar`。通常不致命（这些 jar 里只有 DLL 和 META-INF），但会污染 classpath、拉长命令行（Windows 有 32KB 上限风险），且部分 mod/库扫描 `META-INF/services` 时可能误触发。HMCL 是排除的。

建议：判定改为同时看 `name` 是否带 classifier（`name.split(":")` 长度 ≥ 4）或 `artifact.path` 是否含 `natives-`，命中则视为 native-only 跳过。

### 4. `buildGameArgsFromJson` 的 RuledArgument 规则求值初始值错误

```java
boolean allow = true;   // ← 这里
if (obj.has("rules")) {
    for (rule : rules) {
        if (rule.has("os") && osName.equals(currentOs))
            allow = "allow".equals(action);
        if (rule.has("features")) { ... }
    }
}
```

Mojang 规范是**默认拒绝，逐条匹配，最后一条匹配的规则决定**，即初始应为 `false`。对比 `CompatibilityHelper.appliesToCurrentEnvironment`（libraries 用的那份）就写对了：`boolean allowed = false;`。

后果：形如 `{"rules":[{"action":"allow","os":{"name":"windows"}}],"value":["--xxx"]}` 的参数，在 Linux/macOS 上 `osName != currentOs` → 不进入 if → `allow` 保持 `true` → **本不该传的参数被传进游戏**。这类带 os 规则的 game 参数在原版里存在（如平台专属选项），错误求值会导致跨平台传参错乱。

同时 features 分支 `if (!Objects.equals(expected, actual)) { allow = "disallow".equals(action); }` 也是错的：features 匹配时（`Objects.equals == true`）不进 if，`allow` 不变，但"匹配的 allow 规则"本应把 `allow` 置 `true`。建议参照 `CompatibilityHelper` 重写。

### 5. `processNatives` 回退分支 `Files.walk` 未关闭

```java
Files.walk(libsRoot)
    .filter(...)
    .forEach(p -> nativeJars.add(...));
```

`Files.walk` 返回的 `Stream` 持有 `DirectoryStream`，必须 try-with-resources 关闭。这里没关，**文件句柄泄漏**。同文件其他地方（`Files.list`）都用了 try-with-resources，说明是遗漏。

后果：Windows 上泄漏的句柄会让后续删除/移动 `libraries` 目录失败；大量版本切换后句柄耗尽。应改为：
```java
try (Stream<Path> s = Files.walk(libsRoot)) { s.filter(...).forEach(...); }
```

## 中优先级（功能缺陷 / 健壮性）

### 6. `deleteRecursively` 吞掉删除异常

```java
.forEach(p -> { try { Files.delete(p); } catch (IOException ignored) {} });
```
natives 目录清理、不完整目录删除都走这里。若 DLL 被占用（上次游戏没退干净、杀软扫描），删除静默失败，后续 `Files.createDirectories(extractDir)` 可能成功（目录已存在），接着 `Files.copy(..., REPLACE_EXISTING)` 撞到被占用文件抛异常——但错误信息只指向 copy，根因（上一个 delete 失败）无从得知。建议至少 `writeLog` 记录失败路径。

### 7. `executePreLaunchCommand` 超时不终止进程

```java
p.waitFor(30, TimeUnit.SECONDS);
```
返回值丢弃。命令挂起时，30 秒后继续启动游戏，但**启动前命令进程残留**，且"启动前命令没跑完就启动游戏"违背语义。建议超时后 `destroyForcibly()` 并记 WARN。

### 8. 内存参数无校验

`buildJvmBase` 直接 `-Xms{min}M -Xmx{max}M`。若用户把 min 配得比 max 大，JVM 启动即报 `Initial heap size set to a larger value than the maximum heap size`，错误信息对普通用户不友好。建议在 `buildJvmBase` 或 `LaunchInfo.setMaxMemoryMB` 里校验并纠正/记日志。

### 9. `stdoutBuffer` / `stderrBuffer` 无上限增长

`BaseLauncher` 里两个 `StringBuilder` 只 append 不裁剪。长时间挂机（几小时）后缓冲区可达几十 MB，`getGameStdout()` 还要 `toString()` 复制一份。HMCL/PCL2 都是环形或截断的。建议加容量上限（如保留最后 1MB）。

### 10. ForgeLegacy 的 `-Dfml.modFolders` 可能造成 mod 重复加载

```java
argList.add("-Dfml.modFolders=" + modsDir);
```
`--gameDir` 已经指向版本目录（隔离时），FML 默认就会扫 `--gameDir/mods`。再额外指定 `modFolders` 指向同一目录，部分 FML 版本会重复注册 mod 或产生 "duplicate mod" 警告。HMCL 对 Legacy Forge 通常不注入这个参数。建议确认目标 FML 版本行为，或去掉。

### 11. `buildModulePath` 内层循环提前 break

找到 `group:artifact:` 匹配的 library 后，若 `downloads.artifact.path` 文件不存在，会尝试降级路径；降级路径也不存在时 `break` 无条件执行，**不会继续尝试下一个同名 library 条目**。同一 artifact 多版本并存在 libraries 里罕见，但一旦发生（如 Forge 合并了不同版本的 asm），模块路径会缺条目。建议只有 `found=true` 才 break。

## 低优先级（边界 / 观察）

### 12. `PlatformUtils.getJavaVersion()` 对 `1.x`（x>9）解析错

```java
if (version.startsWith("1.")) return Integer.parseInt(version.substring(2, 3));
```
"1.10.0" → `"1"` → 1。实际 Java 没有 1.10+（Java 10 是 "10.0"），所以无实际影响，但逻辑不严谨。可用 `indexOf('.', 2)` 取完整次版本号。

### 13. `buildGameArgsFromJson` 的 `lastFilteredOption` 不覆盖 RuledArgument

黑名单值跳过逻辑（`--quickPlayPath` 等的后继值）只在顶层 primitive 分支生效；RuledArgument 的 `value` 里遇到黑名单选项不会连带跳过其值。实际 RuledArgument 里出现这些参数的组合极罕见，影响很小。

### 14. `resolveLibraryPath` / `resolveNativeLibraryPath` 每次调用重新 `split` 且无缓存

`getLibraries` 对每个 library 调一次，规模不大，可忽略。若追求性能可缓存，但不是问题。

### 15. `buildDefaultEnv` 中 `javaPath` 为 null 时 `env.put("INST_JAVA", null)`

`HashMap` 允许 null 值，但 `ProcessBuilder.environment().putAll(env)` 遇到 null 值会 NPE。不过 `javaPath` 为 null 时 `new ProcessBuilder(fullCommand)`（`fullCommand[0]=null`）本身就会先抛 NPE，所以是"前置校验缺失"的连带，非独立 bug。
