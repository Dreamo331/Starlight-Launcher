# 版本选择改为「游戏目录内配置文件」

- 日期：2026-10-25
- 状态：**已实现并通过验证**（落地细节与验证证据见第十二节）
- 性质：技术文档（非法律文本，不触发 `tools/legal-witness` 重新存证）

---

## 一、改动初衷

多游戏目录（`GameFolders`）已支持切换，但「选中的版本」是全局单值，不随目录走。
结果是：在 A 目录选了 1.20.1，切到只装了 1.19.4 的 B 目录后，启动仍然指向 1.20.1 ——
**轻则弹"该目录未找到版本，请重新选择"，重则用错版本或指向不存在的目录**。

目标：**切换到某个目录时，用这个目录自己上次配置的版本，而不是别处留下的版本。**

## 二、现状盘点（改造前的事实）

### 2.1 唯一持久化点

`starlight.ini` 的 `[Launcher] Version=<版本目录名>`（全局单值）。key 登记在三处：

| 登记处 | 位置 |
|---|---|
| `StarlightConfig.LAUNCHER_KEYS` | `src/main/java/com/example/starlight/config/StarlightConfig.java:24` |
| `UIGeneralControlClass.saveConfig` 的 `launcherKeys` | `src/main/java/com/example/starlight/gui/UIGeneralControlClass.java:439` |
| `ConfigManager` 的 `launcherKeys` | `src/main/java/com/example/starlight/main/ConfigManager.java:101` |

### 2.2 真正决定启动哪个版本的路径（**最容易踩的坑**）

```
LauncherView.launchGame()                     只用 configCache 做空值校验 + 动画文案
  └── UIGeneralControlClass.getLaunchConfig()  ← 真正构造启动配置
        └── readConfig()                      ← 每次都从磁盘重新读 starlight.ini
```

`UIGeneralControlClass.getLaunchConfig()`（`UIGeneralControlClass.java:404`）不读 UI 的
`configCache`，而是调 `readConfig()`（同文件 `:382`）**从磁盘读 ini**。

因此：任何"只改内存 / 只改 UI 缓存、不改 ini"的做法，都会出现
**界面显示 A、实际启动 B** 的错位。本次改造必须把这条路径一并收口。

### 2.3 `saveConfig` 的两个陷阱

1. `StarlightConfig.saveConfig` 对"不在传入 Map 里的键"**原样保留原行**（`:100-111`）。
   所以只是把 `"Version"` 从 `LAUNCHER_KEYS` 里删掉，**并不能把 ini 里的旧行删掉**，必须显式删行。
2. `UIGeneralControlClass.saveConfig`（`:476`）写的是
   `config.getOrDefault(key, config.get(key))`。若 Map 里没有该键且 `config.get()` 返回 null，
   会写出字面量 **`Version=null`**，随后被 `readConfig()` 读成字符串 `"null"`。
   —— 删 key 的同时必须显式删除该行，否则升级用户的 ini 会被写脏。

## 三、目标语义

1. 每个游戏目录自己持有"我要启动哪个版本"，存在该目录内的配置文件里。
2. 切换游戏目录 → 读目标目录的配置文件 → 当前版本随之切换；目录之间互不干扰。
3. 在某个目录里选择版本 → 写该目录的配置文件。
4. 文件缺失 / 损坏 / 记录了一个已不存在的版本 → 视为「该目录尚未选择版本」，
   走现有的"请先选择游戏版本"分支，不崩溃、不误启动别的版本。
5. `starlight.ini` **不再保存 `Version`**：配置文件是唯一真源。

---

## 四、配置文件设计

**位置：`{游戏目录}/starlight.json`**（与 `launcher_profiles.json` 同级，一眼可见，
便于用户备份或复制整合包时一起带走）

```json
{
  "schemaVersion": 1,
  "selectedVersion": "1.20.1-forge_47.2.0",
  "updatedAt": "2026-10-25T16:03:00+08:00",
  "updateBy": "Starlight Launcher 1.2.3"
}
```

- UTF-8 无 BOM，Gson 美化输出（沿用 `VersionConfigManager` 的 `PRETTY_GSON` 写法）。
- 只强依赖 `selectedVersion`；`updatedAt` / `updateBy` 仅供事后排查"谁把版本改掉了"。
- **只放版本**，不放 JavaPath / 内存 / 隔离等设置（那些仍归全局 ini；将来要扩展再加字段）。
- 路径字面量只出现在 `SelectedVersion` 一处，不散落（对齐 AGENTS.md 的"唯一真源"纪律）。
- 读取绝不对 UI 抛异常：解析失败 → 返回空串 + 一条 warn 日志。
- **不**在 `GameDirInitializer` 初始化骨架时创建空文件，只在"首次选择版本"时创建。

## 五、统一入口 `SelectedVersion`（新增）

`src/main/java/com/example/starlight/config/SelectedVersion.java`

```java
public final class SelectedVersion {
    public static final String FILENAME = "starlight.json";

    static Path fileOf(String gameDir);
    static String of(String gameDir);                    // 读文件；无/坏 → ""
    static String of(Map<String, String> config);        // = of(GameDirManager.activePath(config))
    static boolean set(String gameDir, String version);  // 写文件（空串 = 清除记录）
    static boolean isInstalled(String gameDir, String version); // 复用 ResourceScanner.versionInstalledIn
}
```

- 无 UI 依赖、不依赖 `LauncherView`，UI 与 CLI 共用。
- 写失败（目录只读 / 无权限）只记日志并返回 false，不阻断启动流程。

### 6.4 登记清理与迁移

| 位置 | 改法 |
|---|---|
| `StarlightConfig.java:24` | 从 `LAUNCHER_KEYS` 删除 `"Version"` |
| `UIGeneralControlClass.java:439` | 从 `launcherKeys` 删除 `"Version"`，**并显式删除 ini 里的旧 `Version` 行**（否则 `:476` 会写出 `Version=null`） |
| `ConfigManager.java:101` | 同上（删 key + 显式删旧行） |
| `LegacyVersionMigration` | 见下 |

**旧值迁移规则**（幂等，只在 ini 里还存在 `Version` 键时执行一次）：

1. 读旧 `Version=X`；
2. 对 `GameFolders` 里**每一个确实装有 `versions/X` 的目录**，写 `starlight.json` 的
   `selectedVersion = X`（忠实还原旧的"全局选择对所有目录生效"语义：有 X 的目录都记 X）；
3. 从 ini 删除 `Version` 行；
4. `X` 在任何目录都不存在 → 直接删行，不写文件。

**启动钩子**：`LauncherView.loadConfig()`（`:1391`）读完 ini 后，
先跑 `LegacyVersionMigration`，再把**活动目录**的版本灌进 `configCache["Version"]` 内存镜像
（另见 6.6）。

### 6.5 切目录的语义升级

`GameDirPage.doSwitchGameDir()`（`:1529-1557`）：

- 切目录后不再用"旧目录留下的版本"去校验，而是读**目标目录**的 `starlight.json`；
- 提示文案从"该目录未找到版本 X，请到「版本选择」重新选择"
  改为 **"已按该目录的记录切换到 X"** / **"该目录尚未选择版本，请到「版本选择」选择"**。

### 6.6 内存镜像（**不是真源**，是防御）

`configCache` 里的 `Version` 保留为**纯运行时镜像**，在
「启动加载 / 切换目录 / 选择版本 / 启动前」四个时机与文件同步：

- 真源始终是 `starlight.json`；`SelectedVersion.of()` 永远以文件为准；
- 保留镜像的目的是兜底：万一还有未排查到的读取点，它读到的也是**当前目录的正确值**，
  而不是空值或别的目录的值；
- 镜像永不持久化进 ini。

## 七、边界与容错

| 场景 | 处理 |
|---|---|
| 目录只读 / 无写权限 | 内存与本次启动照常生效，只记日志；下次启动退回"未选择" |
| 手动编辑 `starlight.json` 指向另一个已安装版本 | 重启或切回该目录即生效（启动前同步兜底） |
| 手动改成不存在的版本 | 视为未选择，不崩溃、不误启动 |
| 版本目录被外部删除 | 读时校验存在性，悬空记录按"未选择"处理 |
| 两个启动器实例同时开同一目录 | 后写覆盖（`updatedAt` 便于事后排查；本期不做文件锁） |
| 便携模式 `--portable` | 逻辑与路径无关，天然成立，但**必须手测** |
| 老配置升级 | 见 6.4；升级后 ini 里**不得残留 `Version` 行，也不得出现 `Version=null`** |
| 网络 / 依赖 / 合规 | 不新增网络请求、不新增依赖 → 隐私政策、第三方声明、安全与合规**均无需改动** |

### 12.2 与方案的两点细化（实施时的判断）

1. **「是否已安装」的校验收进了 `of()` 内部**。方案原写“读取点各自判定悬空记录”，实现改为
   `of()` 直接返回校验后的值、`recorded()` 才返回原始记录——
   于是所有读取点自动获得“悬空记录 = 未选择”的安全语义，不必逐点写判定；
   `GameDirPage` 用 `recorded()` 才能区分“从未选择”与“记录已失效”并给出不同提示。
2. **迁移触发点只覆盖 GUI 与 CLI 两条真实入口**（`LauncherView.loadConfig()` /
   `CliHandler.processCommandArgs()`）。若有第三种进入方式绕开两者，旧 ini 值不会被采纳，
   用户重新选一次即可——不会崩溃、不会启动错版本。
