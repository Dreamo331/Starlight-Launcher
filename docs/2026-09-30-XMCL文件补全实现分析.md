## 0. 结论摘要

XMCL 的补全体系可以概括成三层，**分层方式与本项目完全不同**：

| 层 | 职责 | 关键文件 |
|---|---|---|
| **① 规划层**（domain-agnostic） | 把「要装什么」描述成一份可执行的 **InstallManifest**（文件清单 + 任务 DAG） | `packages/installer/installManifest.ts` |
| **② 领域层** | 到底层无关的 manifest 之上，生成 Minecraft / Forge / Fabric / 资产 / 库 的文件清单 | `packages/installer/{assets,libraries,minecraft,forge,fabric,...}.ts` |
| **③ 传输层** | 单文件下载：TTFB/停滞看门狗、断点续传、Range 分片、多源轮换、熔断器、EWMA 速度学习 | `packages/file-transfer/*` + `xmcl-runtime/network/BmclDownloadController.ts` |

**对本项目最有价值的四条结论**（详见 §4、§5）：

1. **XMCL 的停滞检测是它的核心机制，不是可选优化** —— `ttfbDeadline=5s` + `stallTimeout=5s`，注释明确写「a stuck mid-stream mirror must be abandoned even in committed mode (otherwise the download hangs forever with no progress)」。本项目**完全没有这一层**，这正是「后期特别慢」的根因。
2. **XMCL 有"少发了多少字节"这一显式校验** —— `download.ts:488-508` 的 `handler.offset < target` 检查。本项目只比较 `Content-Length`，**响应不带该头时 0 字节会被当成成功**。
3. **XMCL 默认资产源是官方，不是镜像** —— `DEFAULT_RESOURCE_ROOT_URL = 'https://resources.download.minecraft.net'`；BMCLAPI 在传输层作为**保底候选**。本项目反了：BMCLAPI 是首选，于是把死镜像放到了主路径上。
4. **XMCL 用 `validatedAt` 时间戳跳过重复校验** —— 二次补全时"上次已验证且之后未被修改"的文件**完全不算哈希**。本项目每次启动都对全部文件重算 SHA-1。

## 1. 规划层：InstallManifest

### 1.1 核心抽象

`installManifest.ts:98-101`：

```ts
export interface InstallManifest {
  schemaVersion: 1
  tasks: InstallTask[]
}
```

设计意图写在 `:91-97` 的注释里，非常明确：

> A domain-agnostic executable install manifest.
> Workflows may understand Minecraft, loaders, profiles, or asset indexes;
> **manifests and executors must not.** A manifest only describes files, processes,
> and deterministic filesystem materialization.

即：**执行器不认识 Minecraft**，它只会「按清单下文件 / 跑 Java / 落盘」。三种任务类型（`:47-89`）：

| 任务类型 | 作用 |
|---|---|
| `InstallFilesTask` | 下载一批文件（`files: InstallFile[]`） |
| `InstallJavaTask` | 跑 Java 安装器（`strategies: JavaCommand[][]`，多策略依次尝试） |
| `InstallMaterializeTask` | 确定性的文件系统物化（写/复制/硬链接/解压/合并 zip） |

任务之间用 `dependsOn?: string[]` 组成 DAG，执行器（`:319-368`）用记忆化 + 环检测做拓扑执行，**同 id 只跑一次**（`:320-321`），`visiting` 集合检测循环依赖（`:324`）。

### 1.2 InstallFile：文件描述的精髓

`installManifest.ts:19-31`：

```ts
export interface InstallFile {
  path: string
  urls: string[]                      // 多源候选
  size?: number
  checksum?: InstallFileChecksum      // { algorithm, value }
  validator?: 'file' | 'zip' | 'json' // 轻量结构校验
  /** Trust an existing file with the expected size, but still checksum newly downloaded content. */
  trustExistingSize?: boolean
  /** Replace the existing file before trusting any cached validation state. */
  replace?: boolean
  /** Last timestamp at which this exact file was known to be valid. */
  validatedAt?: number
}
```

注意 `trustExistingSize` 的注释 —— 这是**专门为 0 字节/截断响应问题设计**的开关：

> 信任"尺寸正确的已存在文件"，但**对新下载的内容仍然做校验和**。

换句话说：老的、尺寸对的文件走快路径；**刚下载下来的内容一律重新校验**。这句话直接回答了本项目遇到的「BMCLAPI 返回 200 + 0 字节」问题 —— XMCL 的答案是"快路径只给老文件，新下载的必须验"。

### 1.3 有效性判定 isFileValid（`:160-181`）

```ts
async function isFileValid(file, runtime, trustCachedValidation: boolean) {
  if (trustCachedValidation && file.replace) return false          // ① 要求替换 → 不信任何缓存
  const fileStat = await runtime.stat(file.path)
  if (!fileStat) return false                                      // ② 不存在 → 无效
  if (trustCachedValidation && file.validatedAt !== undefined
      && fileStat.mtimeMs <= file.validatedAt) return true         // ③ 上次验证后没改过 → 直接信
  if (trustCachedValidation && file.trustExistingSize
      && file.size !== undefined && fileStat.size === file.size) return true  // ④ 尺寸对 → 信
  let valid: boolean
  if (file.checksum?.value) {
    valid = await runtime.checksum(file.path, file.checksum.algorithm).catch(() => '') === file.checksum.value
  } else if (file.size !== undefined && file.size >= 0) {
    valid = fileStat.size === file.size
  } else {
    valid = fileStat.size > 0                                       // ⑤ 啥都没有 → 非空即算有效
  }
  return valid && (!file.validator || await runtime.validate(file.path, file.validator))
}
```

**三级成本递减的判定链**，这是本项目最值得借鉴的一处：

| 级别 | 依据 | 成本 |
|---|---|---|
| ③ | `mtimeMs <= validatedAt` | 一次 `stat`，**不算哈希** |
| ④ | 尺寸相同（且 `trustExistingSize`） | 一次 `stat` |
| ⑤ | 完整哈希 + `validator` | 读全文件 |

`isOutputValid`（`:183-185`）故意传 `validatedAt: undefined` → **强制走完整校验**，用于校验 Java 安装器/Materialize 的产物。

### 1.4 三类 validator（`:673-693`）

| validator | 判定 |
|---|---|
| `'file'` | 只要 `stat` 成功 |
| `'json'` | `JSON.parse` 成功 |
| `'zip'` | 能被 zip 打开**且至少有一个非目录条目** |

`validator` 的价值：在**没有/不敢信 checksum** 时仍能挡掉「服务器返回 HTML 错误页」「0 字节 zip」这类结构性损坏。`libraries.ts:62-65` 就用了这个技巧：

```ts
checksum: library.download.sha1 ? { algorithm: 'sha1', value: library.download.sha1 } : undefined,
validator: library.download.sha1 ? undefined : 'zip',     // 没有 sha1 就退化为"结构校验"
```

### 1.5 重试编排 executeFiles（`:196-244`）—— 多源轮换在这里

```ts
const attempts = Math.max(1, options.attempts ?? 5)          // 默认 5 轮
// ...
for (let attempt = 0; attempt < options.attempts && pending.length > 0; attempt++) {
  await runtime.download(pending)
  // 下载后「从磁盘重读」验证，只把失败的重排
  const invalid = await Promise.all(pending.map(async (file) => ({
    file, valid: await isFileValid({ ...file, validatedAt: undefined }, runtime, false),   // 强制全校验
  }))).filter(({ valid }) => !valid).map(({ file }) => file)
  await runtime.remove(invalid.map((file) => file.path))       // 删掉坏的
  pending = invalid.map((file) => file.urls.length > 1
    ? { ...file, urls: [...file.urls.slice(1), file.urls[0]] } // ★ URL 轮换：把刚失败的源挪到末尾
    : file)
  if (pending.length > 0 && lastError && isTerminalInstallError(lastError)) throw lastError
  if (pending.length > 0 && attempt + 1 < options.attempts) {
    const ceiling = Math.min(options.retryMaxDelay, options.retryBaseDelay * 2 ** attempt)  // 指数退避
    const delay = Math.round(ceiling * (0.75 + options.random() * 0.5))                    // ±25% 抖动
    options.onRetry?.(attempt + 1, delay, pending.length, lastError)
    await options.wait(delay, options.signal)
  }
}
```

三个关键设计：

1. **失败文件才重排**，成功的文件不重下（`pending` 逐步收敛）。
2. **URL 轮换**（`:229-231`）：`[...urls.slice(1), urls[0]]` —— 每个失败文件的候选源列表整体左移一位。下一轮自然从**上一个源的下一个**开始，等价于「换源重试」，但**不需要任何全局状态**。
3. **指数退避 + 抖动**：`min(retryMaxDelay, retryBaseDelay * 2^attempt)` × `[0.75, 1.25]`，默认 500ms 起、4s 封顶。

**与 Project 的对比**：本项目的换源是「单文件内顺序遍历候选」，没有跨轮次的源轮换，也没有退避抖动。

### 1.6 终态错误判定 isTerminalInstallError（`:246-253`）


## 2. 传输层：本项目的核心对照点

### 2.1 停滞检测：两级看门狗

`controlled_handler.ts` 里有**两个独立的检测器**，这是整个体系里对本项目最有价值的部分。

**① TTFB 看门狗**（`:135-159`）—— 连上了但第一个字节迟迟不来：

```ts

  this.ttfbTimer = setTimeout(() => {
    if (this.firstByteAt === 0) {
      // Connected (or redirected) but no bytes — re-roll fast.
      this.clearTimers()
      const error = new ManagedAbortError('ttfb')
      this.abortRequest?.(error)
      this.resolvers.reject(error)
    }
  }, ttfb)
  this.ttfbTimer.unref?.()
}
```

**② 停滞看门狗**（`:289-310`）—— 已经开始收数据，但中途卡住：

```ts
// Stall watchdog: first byte arrived, then no byte for stallTimeout.
// A stuck mid-stream mirror must be abandoned even in committed mode
// (otherwise the download hangs forever with no progress). Only for
// re-assignable origins — the official source is left to finish.
const stallTimeout = this.controller.stallTimeout ?? 0
if (this.abortable && stallTimeout > 0 && this.lastByteAt > 0
    && now - this.lastByteAt > stallTimeout) {
  this.clearTimers()
  this.resolvers.reject(new ManagedAbortError('stall'))
  return
}
```

`noAbort`（已进入"必须下完"模式）只关掉**基于速度**的中止，**停滞看门狗依然生效**（`:312-315` 的注释：`In committed mode we still sample ... and keep the stall watchdog above`）。

**这四个 `ManagedAbortReason`（`controller.ts:204`）的语义划分非常清晰**：

| reason | 含义 | 应对 |
|---|---|---|
| `ttfb` | 连上/重定向完成但**没有任何字节** | **无进展** → 快速放弃，换源 |
| `stall` | 收了首字节，然后**停了** | **无进展** → 快速放弃（即使 committed） |
| `slow` | 在推进，但相对学习到的模型太慢 | 调优决策 → 可重掷，但最后一个源要忍 |
| `skip` | 排队期间该源被熔断 | 直接跳过 |

> `controller.ts:200-202` 的注释：**`ttfb` 和 `stall` 意味着"无进展"（死/卡住的镜像），应当快速放弃；`slow` 只是一个调优决策。** 这个区分是本项目目前完全没有的。

### 2.3 最优停止规则（`decide`，`:274-315`）—— 不是固定阈值

```ts
private decide(sample: DownloadSample): 'continue' | 'abort' {
  if (!this.isReassignable(sample.origin)) return 'continue'    // 官方源永不中止
  if (sample.speed < this.stallFloor) return 'abort'            // 硬停滞：一律重掷
  if (this.global.count < this.minGlobalSamples) return 'continue'  // 模型还没置信
  const eFresh = this.global.score
  if (eFresh <= 0) return 'continue'
  if (sample.total > 0) {
    const remaining = sample.total - sample.received
    if (remaining <= 0) return 'continue'
    const overhead = this.reconnectOverheadMs / 1000
    // Expected finish time as-is = remaining / speed.
    // Expected finish time if re-rolled = overhead + remaining / eFresh.
    // Solving for the break-even speed:
    const vMin = remaining / (overhead + remaining / eFresh)
    if (sample.speed < vMin * this.abortMargin) return 'abort'
  } else {
    if (sample.speed < eFresh * 0.4) return 'abort'
  }
  return 'continue'
}
```

**这是"最优停止"（optimal stopping）**：不是「低于 X KB/s 就掐」，而是比较两条路径的**期望完成时间**：

- 继续：`remaining / speed`
- 重掷：`overhead + remaining / eFresh`

解出临界速度 `vMin`，低于它才掐。特点是**剩余量越大越愿意掐**（因为省下的时间更多），剩余量小时即使慢也忍着 —— 这对本项目「最后几个文件特别慢」的场景是精准的。

### 2.4 无进展 vs 慢：两条完全不同的处置路径（`download.ts:538-573`）

```ts
if (isManagedAbortError(err)) {
  const reason = (err as ManagedAbortError).reason
  if (reason === 'skip') { advanceUrl(); continue }
  if (reason === 'slow') {
    if (slowRerolls < maxSlowRerolls && resumes < maxResumes) {

    committed = true; continue                  // 最后一个源：忍，必须下完

  // stuck. Try a couple of fresh assignments, then fall straight to
  // the next fallback URL (e.g. the official source) instead of
  // looping on dead mirrors and wasting the whole reroll budget.

```

`noProgress` 只有 **2** 次预算（对比 `slow` 的 2 次 + `maxResumes` 5 次）—— 设计意图写得很清楚：**不要在死镜像上把重掷预算耗光**。

### 2.5 短交付检测（`download.ts:488-508`）—— 直接对应 0 字节问题

```ts
if (!err) {
  // Defend against a mirror that completed "successfully" but
  // delivered FEWER bytes than requested (a short, otherwise-valid
  // 206, or a whole-file stream cut short). Without this check the
  // un-delivered tail stays as zero bytes on disk — a silent gap
  // that corrupts the file (e.g. empty zip entries). The expected
  // end is the segment's inclusive end + 1, or the whole-file total
  // discovered from the response headers.
  const target = isSeg ? segEnd! + 1 : handler.total
  if (target > 0 && handler.offset < target) {
    resumeOffset = Math.max(resumeOffset, handler.offset)
    if (resumes < maxResumes) { resumes++; continue }   // 续传缺失的尾巴
    lastError = new Error(`Incomplete download: received ${handler.offset} of ${target} bytes`)
    advanceUrl(); continue
  }
  done = true; break
}
```

**"成功但没有下够"被显式当成失败**，而且优先尝试**续传缺失部分**（不是整文件重下），续传预算用尽才换源。

`handler.total` 来自响应头（`controlled_handler.ts:184-187`）。对本项目的启发：**"声明了 N 字节却只收到 0 字节"必须算失败** —— XMCL 靠 `offset < total`，本项目靠 `contentLength > 0 && totalRead != contentLength`，但**当响应不带 `Content-Length` 时本项目会漏判**（详见 §5.1）。

### 2.7 熔断器与半开探测（`shouldSkip` `:336-351`）

```ts
shouldSkip(origin: string): boolean {
  if (!this.isReassignable(origin)) return false
  if (Date.now() >= Math.max(this.cbOpenUntil, this.slowOpenUntil)) return false
  // Half-open: occasionally let a request through to probe whether the
  // CDN has recovered. ...
  this.cbProbeTick = (this.cbProbeTick + 1) % this.cbProbeEvery
  if (this.cbProbeTick === 0) return false
  this.telemetryWin.breakerSkips++
  return true
}
```

两个独立的熔断器维度：

| 熔断器 | 触发条件 | 默认阈值/冷却 |
|---|---|---|
| **数据熔断**（CDN 完全不给数据） | 连续"几乎没数据"的尝试 | 16 次 / 30s |
| **慢源隔离**（CDN 给数据但太慢） | `slow` 中止次数 | 8 次 / 30s |

**半开探测**（`:342-348`）是关键设计：熔断期间**每 24 个请求放行 1 个**，一旦成功立即闭合熔断器（`report` 里 `:413-418`），**不等冷却期结束**。

> 这段注释直接回应了本项目当前的实现短板：
> 「A successful probe closes the breaker (in `report`) before the cooldown elapses, so we converge back to the (faster) CDN as soon as it works again — important when the official fallback is itself slow.」

本项目 `SourceHealth` 的问题正是：**冷却期内完全不试，只能等冷却结束**；且没有"官方源也不行时该重新考虑镜像"的收敛保护。

### 2.8 反向收敛保护（`report` `:427-442`）—— 很聪明的一点

```ts

```

**如果保底源也不给数据，就把熔断器关掉** —— 避免"熔断器把流量赶到一个同样死的保底源上"的死循环。这是熔断器设计的常见陷阱，XMCL 显式处理了。

### 2.9 速度模型：按镜像主机学习 + 持久化（`:200-201, :659-666`）

```ts
private readonly hosts = new Map<string, Ewma>()
private readonly global: Ewma = { score: 0, weight: 0, lastUpdate: 0, count: 0 }

private update(e: Ewma, value: number, now: number) {
  const decay = e.lastUpdate ? Math.exp(-(now - e.lastUpdate) / this.tau) : 0
  const w = e.weight * decay
  e.score = w > 0 ? (e.score * w + value) / (w + 1) : value
  e.weight = w + 1
  e.lastUpdate = now
  e.count += 1
}
```

两个模型：
- **`global.score`** = 一次重掷能达到的吞吐期望（"eFresh"，`snapshot` 里会打印）；
- **`hosts`** = 按**最终镜像主机名**（不是 API 域名，而是重定向后的真实镜像）的声誉。

**关键**：`finalHost` 来自重定向链（`controlled_handler.ts:188-194` 从 `context.history` 取最后一跳）。因为 BMCLAPI 是签名重定向到不同镜像的，**只有跟踪到最终主机才有意义**。

`report` 里两个精心设计的过滤（`:465-473`）：

```ts
if (result.received < this.minMeasureBytes) return        // 太小的文件测不出速度，不喂模型
if (!this.isReassignable(result.origin)) return           // 官方源的表现不能推断新镜像的表现
```

以及（`:478-485`）：

```ts
} else if (result.outcome === 'aborted') {
  // Remember the slow assignment, but do not let truncated samples
  // drag down the global "achievable" expectation.
  if (host) this.update(this.host(host), result.speed, now)     // 只更新该主机
} else {
  if (host) this.update(this.host(host), 0, now)                // 彻底失败 = 该主机最差证据
}
```

**被掐掉的连接更新"主机声誉"但不污染"全局可达期望"** —— 否则一个慢镜像会拉低 eFresh，导致本该被掐的正常连接也被掐。

**持久化**（`:604-640`）：`load/save` 把 `global` + `hosts` 写到 JSON，10 秒防抖保存，可跨会话 —— 注释 `:156-157`：`so repeatedly-slow hosts are abandoned sooner and the knowledge survives across sessions`。

### 2.10 Range 分片跨镜像（`download.ts:312-364`）

```ts
// 每个分片是「独立的请求」，因此在分布式 CDN 上每个分片会被独立重定向到不同镜像
```

## 5. 对「BMCLAPI 一直返回 0 字节」这个具体问题的启示

用户当前症状：BMCLAPI 服务活着、HTTP 200、正文 0 字节、日志里成片 `数据包 0 B`。用 XMCL 的机制逐条对照：

### 5.1 本项目为什么会漏判

本项目 `GameResourceCompleter.downloadFile` 的长度校验是：

```java
} else if (contentLength > 0L && totalRead != contentLength) {
```

**`contentLength == -1`（响应不带 `Content-Length`）时整个条件短路**，于是 `downloaded = true`，写下一个 0 字节文件，直到 SHA-1 校验才失败。

XMCL 的做法（`download.ts:496-508`）是拿**请求应有的终点** `target` 比：

```ts
const target = isSeg ? segEnd! + 1 : handler.total
if (target > 0 && handler.offset < target) { /* 判失败 + 续传尾巴 */ }
```

注意 `handler.total` 同样来自响应头 —— **所以 XMCL 在"连 Content-Length 都没有"的情况下也会退化为"无法判定"**。但它有第二道防线（§1.3 ⑤：没有 checksum 也没有 size 时，只要求 `size > 0`），而资产/库**永远有 size 和 sha1**，所以这道防线在真实场景中总能生效。

> **结论**：本项目已做的「`totalRead == 0` 且该文件应有内容 → 判失败」（提前于 SHA-1）方向正确，与 XMCL 的 ⑤ + `expect` 组合逻辑等价。

### 5.2 XMCL 真正的"止血"机制是什么

对照下来，XMCL 对这个问题有**四层递进**的保护，本项目此前只有第四层：

| 层 | 机制 | 本项目状态 |
|---|---|---|
| ① **默认不走坏源** | 资产默认官方源（`assets.ts:24`） | ❌ 默认 BMCLAPI |
| ② **无进展快速放弃** | TTFB/stall 双看门狗 5s | ❌ 无 |
| ③ **源级熔断 + 半开探测** | 16 次无数据 / 30s，期间每 24 次探 1 次 | ⚠️ 已加计数，但**冷却期内完全不试** |
| ④ **下载后内容校验** | 新下载内容一律校验和（`trustExistingSize` 语义） | ✅ 已有 SHA-1 |

**本项目缺的是 ② —— 而 ② 恰好是唯一不依赖"源是否返回错误码"的机制。** 这也解释了为什么用户观察到"没挂但是 0 B"：健康表按状态码/字节数分类，而真正需要的是一条**独立于源响应**的时间维度看门狗。

### 5.3 一条重要的设计边界

XMCL 对 `abortable` 的判定（`BmclDownloadController.ts:330-334`）：

```ts
isAbortable(origin: string): boolean {
  // Only abort (TTFB/stall) re-assignable CDN origins; the official
  // source is slow-but-reliable and must be allowed to finish.
  return this.isReassignable(origin)
}
```

**只对"可重掷"的源做无进展中止**。理由：官方源是**固定**的，掐掉它再请求还是同一个主机，掐了没意义，反而把慢但能用的源搞死。

**这对本项目很重要**：如果给 `GameResourceCompleter` 加停滞看门狗，必须**区分"可换源的镜像"和"最后的保底官方源"**。否则官方源慢的时候会被反复掐断、永远下不完 —— 这正是 XMCL 用 `committed = true`（`:558-561`）保护最后候选源的原因：

> `The re-roll budget is spent. A slow-but-working connection is never a hard failure on the last source — commit to finishing.`

## 8. 一句话总结

**XMCL 把"补全"拆成了「描述要什么（manifest）+ 怎么把这个文件弄到手（传输层看门狗/续传/多源/熔断/速度模型）」两件互不知情的事；而它的传输层核心信念是——「没有进展」和「进展慢」是两种完全不同的病，前者要立刻换源，后者才值得权衡。**

本项目目前把两者混在一个固定超时里，所以既治不了卡死（无进展占满线程），也调不准慢速（固定 25.6 万 B/s 触发线）。这是最值得借鉴的一条。
