# 离线皮肤改造：PCL2 风格（UUID 定制 + 资源包）

> 日期：2026-10-01 ｜ 范围：离线账号皮肤机制 ｜ 状态：已完成并验证

## 背景与目标

原实现用 **authlib-injector + 本地 Yggdrasil 皮肤服务器** 为离线玩家注入皮肤数据：
启动时起一个本地 HTTP 服务、下载 authlib-injector、向 JVM 追加注入参数。该方案依赖
外部 jar 下载、占用端口、链路长。

本次按 PCL2 的实现思路重构为两层机制：

1. **UUID 定制**：离线模式下游戏不给玩家提供皮肤数据，玩家默认皮肤模型（Steve/Alex）
   由 UUID 决定。因此只微调传给游戏的 `auth_uuid`，让游戏把玩家判定为期望模型；
2. **资源包覆盖**：自定义皮肤（本地文件 / CSL API / 非 Steve-Alex 内置皮肤）打包成
   `Starlight Skin.zip` 放进 `resourcepacks/`，并写入 `options.txt` 的 `resourcePacks`，
   覆盖游戏内置默认贴图。多人游戏仅自己可见，且替换所有默认角色（与 PCL2 一致）。

不再需要本地服务器、authlib-injector 下载与 JVM 注入。

## 机制细节

### 1) UUID 解析（`OfflineSkinUuid`，对应 PCL2 `McLoginLegacyUuidWithCustomSkin`）

- 起点：账号离线 UUID（`Account.id`，无连字符 32 位 hex），幂等，不改账号本身；
- `DEFAULT`（随机）：UUID 不动，模型由玩家名哈希决定；
- `STEVE` / `ALEX`：末 5 位 hex 循环 +1 直到 `skinSex` 命中（每次 +1 末位奇偶必翻转，
  实际 1 次命中，带 10 万次上限保护）；
- 内置皮肤 ARI/EFE/KAI/MAKENA/NOOR/SUNNY/ZURI：按官方模型调 UUID（贴图由资源包注入）；
- `LOCAL_FILE` / `LITTLE_SKIN` / `CUSTOM_SKIN_LOADER_API`：按用户选择的 slim/wide 调 UUID。

### 2) 资源包（`OfflineSkinPack`，对应 PCL2「离线皮肤资源包」）

- 文件名 `Starlight Skin.zip`，位置：
  - 无版本隔离：`<gameDir>/resourcepacks/Starlight Skin.zip`；
  - 版本隔离：`<gameDir>/versions/<version>/resourcepacks/Starlight Skin.zip`（游戏目录随隔离切换）；
- `pack.mcmeta`：`pack_format` 按原版版本映射（1.6~1.8→1 … 1.21.6→63，1.21.7+/快照/未知→64，
  旧式单整数格式 <65 仍被 1.21.9+ 接受）；
- 贴图路径：
  - 1.19.3+：覆盖 `assets/minecraft/textures/entity/player/{slim|wide}/` 下全部 9 个内置皮肤
    （alex/ari/efe/kai/makena/noor/steve/sunny/zuri）；
  - 1.6~1.19.2：覆盖 `assets/minecraft/textures/entity/{alex|steve}.png`；
  - 1.6/1.7 不支持双层皮肤：64×64 自动裁剪为 64×32；
  - 1.5.x 及更早：无资源包机制，跳过并清理（记录 warning）；
- `options.txt` 的 `resourcePacks`：
  - 1.13+：追加 `"file/Starlight Skin.zip"`，为空时补 `"vanilla"`；
  - 1.6~1.12：追加 `"Starlight Skin.zip"`（无 `file/` 前缀）；
  - 每次启动都先做去重/清理：未启用自定义皮肤、贴图缺失或版本过老时删除 zip 并移除条目；
- 贴图来源：`LOCAL_FILE` 读原文件字节；CSL API 走现有 `Skin.load(username)` → `toPngBytes`
  无损重编码；内置皮肤读打包资源 `/Skins/<NAME>.png`。

## 已知边界

- 资源包方式**替换游戏中所有默认角色皮肤**，多人游戏中仅自己可见（与 PCL2 一致，面板文案已注明）；
- 1.2~1.7 版本不支持 Alex（纤细）模型，选择纤细模型时游戏仍显示 Steve 模型外观；
- 1.5.x 及更早不支持自定义皮肤（无资源包机制）；
- 与旧方案不同，CSL API（LittleSkin 等）皮肤不再对其他玩家可见（旧方案经会话服务器注入
  可被他人看到）；本地预览功能不受影响；
- `正版皮肤`（按正版用户名取 Mojang 皮肤）未纳入本次改造——当前皮肤模型无此类型，如需可按
  PCL2 方式补充（Mojang API 查 UUID + 版本 <1.20 限制）。

## 披风支持（第三轮，2026-10-01；修订）

现象：离线账号的披风无法加载。

原因（两次排查结论）：

1. 旧方案由本地 Yggdrasil 皮肤服务器（`OfflineSkinServer`）经会话档案下发披风；
   改为 PCL2 风格时删除了它，离线账号失去披风注入通道。
2. 曾尝试把披风写进资源包（OptiFine 自定义披风格式 `optifine/cape/<玩家名>.png`），
   实际**不可行**：OptiFine 1.17.1（H1）没有资源包披风通道（其 `optifine/` 目录只有
   cit/cem/ctm/random/sky/colormap），原版客户端更不读——披风只来自会话档案的
   textures.cape 字段，客户端内不存在可覆盖的"默认披风"贴图。已移除该通道。

方案：**恢复本地 Yggdrasil 档案服务器 + authlib-injector**，但仅当离线账号配置了披风
才启用；无披风时保持纯 PCL2（UUID + 资源包）机制，不注入任何参数。

实现：

- 新增 `auth/offline/LocalYggdrasilServer.java`：`127.0.0.1` 随机端口的极简 Yggdrasil
  session 端点（JDK 内置 HttpServer，无新依赖）：
  - `/sessionserver/session/minecraft/profile/<uuid>` 与 `/session/minecraft/profile/<uuid>`
    返回带 textures 属性的档案 JSON（SKIN/CAPE 的 URL + slim 模型元数据，base64）；
  - `/skin.png`、`/cape.png` 提供贴图字节；
  - **未知 UUID 透传 Mojang sessionserver**（超时/失败回退 204），多人游戏中他人皮肤不受影响；
  - `startRaw(byte[], byte[], ...)` 支持原始 PNG 字节（不依赖 JavaFX，便于测试）。
- `auth/offline/OfflineSkinManager.java`：新增 `loadForLaunch`（启动前统一加载皮肤+披风）。
- 启动路径接入（三条全部）：`UIGeneralControlClass.launchMinecraftAsync`、
  `MenuHandler`（quickLaunch/launchMinecraft）、`GameLauncherService.launchMinecraftAsync`：
  应用资源包后加载皮肤，检测到披风则启动服务器并通过
  `AuthlibInjectorSupport.buildLaunchJvmArgs(apiBase)` 追加
  `-javaagent:authlib-injector.jar=http://127.0.0.1:<port>/`（无 jar 时回退
  `-Dminecraft.api.*` 参数）；游戏退出/启动失败时停止服务器。
- `OfflineSkinPack` 保留皮肤+披风合并加载与仅披风包构建（资源包内不再写披风条目，
  披风走会话档案通道；资源包仍负责默认角色贴图覆盖）。

验证：`mvn test` BUILD SUCCESS；冒烟测试 45 项全过（新增服务器断言：
档案 JSON 含 SKIN/CAPE 与 slim 模型、`/cape.png` 正常返回 PNG、未知 UUID 返回 204、
仅披风档案无 SKIN 字段、无披风不启动）。

使用条件与边界：

- 需联网下载/复用 authlib-injector.jar（`AuthlibInjectorSupport` 自带官方源 + GitHub 回退）；
- 披风跟随当前账号：皮肤设置选「本地文件」→ 浏览皮肤 + 浏览披风（`localCapePath`）；
  LittleSkin / CSL API 账号的披风同样生效（CSL API 一次请求同时取皮肤与披风）；
- 仅在**自己客户端**可见（原版机制如此）；第三方登录（`THIRD_PARTY`）账号披风不受影响；
- 披风 PNG 建议 64×32（过大图片会被整个映射到披风模型上，显示为压扁的图）。

## 披风注入链修复（2026-10-01 再追加）

现象：17:13 日志已含 `-javaagent:...=http://127.0.0.1:8191/`，游戏仍不显示披风；
游戏日志（latest.log / 启动 stdout 归档）中 authlib 的
`Environment: sessionHost='https://sessionserver.mojang.com', name='PROD'` 仍是 Mojang 地址，
且无任何 authlib-injector 痕迹 → agent 实际未加载。

根因（两处）：

1. **注入参数没同步进 LaunchInfo**（`gui/UIGeneralControlClass.java`）：
   `buildLaunchInfo(config)`（启动流程中较早）把 `config.jvmArgs` 快照进
   `info.jvmArgs`；披风服务器启动后注入的 `-javaagent`/`-Dauthlibinjector.side`
   只改了 `config.jvmArgs`（日志区打印的就是它，看着"已注入"），
   启动器实际读取的 `info.getJvmArgs()` 仍是旧列表 → 命令行没有 agent。
2. **本地服务器缺 authlib-injector 元数据端点**：authlib-injector 1.2.8 启动时
   请求 apiBase **根路径 `/`** 获取元数据；返回 404/连接失败 → agent 打印
   `Failed to fetch metadata` 并**拒绝注入**（实测 `java -version` 直接 exit=1）。

修复：

- `UIGeneralControlClass`：披风注入段追加 `info.setJvmArgs(Arrays.asList(config.jvmArgs.split("\s+")))`，
  把注入参数同步回 info（GameLauncherService / MenuHandler 两条路径顺序本就正确，未改）。
- `LocalYggdrasilServer`：`/` 根路径注册元数据端点（HttpServer 最长前缀匹配，不影响
  `/sessionserver/...` 等具体路径），返回：
  ```json
  {"meta":{"serverName":"Starlight Local","implementationName":"Starlight Launcher",
   "implementationVersion":"2.0.0","feature.non_email_login":true,
   "feature.authlib_injector_actions":false,"feature.skins":true,
   "feature.no_mojang_account":true}}
  ```
  （无签名公钥：客户端 getTextures 走 unsigned=true，不校验签名。）

验证（`temp/smoke/AgentCompatTest.java`，真实 1.2.8 jar + 游戏 JVM 17.0.19）：

- 修复前：`GET /` 404 → agent `Failed to fetch metadata` → exit=1；
- 修复后：`GET /` 200 → agent 打印 Version 1.2.8 / Authentication server 后正常执行 → exit=0。

回归：`mvn test` BUILD SUCCESS；冒烟 45 项 ALL PASS。

## authlib-injector 下载修复（2026-10-01 追加）

现象：启动日志显示官方源（latest.json）"缺少 downloadUrl 字段"、GitHub 直链 HTTP 404，
注入回退到 `-Dminecraft.api.*`，披风不生效。

根因：

- 官方源 `https://authlib-injector.yushi.moe/artifact/latest.json` 实际返回的字段是
  `download_url`（蛇形命名），代码按 `downloadUrl`（驼峰）解析 → 误判"缺少字段"；
- GitHub `releases/latest/download/authlib-injector.jar` 直链 404：最新 release 的资产名
  带版本号（`authlib-injector-1.2.8.jar`），不带版本号的直链不存在。

修复（`auth/AuthlibInjectorSupport.java`）：

- 官方源解析兼容 `download_url`（优先）/ `downloadUrl`，仍做 SHA-256 校验；
- 下载回退链：官方源 → **GitHub API**（`api.github.com/.../releases/latest`，解析
  `assets[].browser_download_url`，资产名带版本号可下）→ GitHub 直链（最后兜底）。

验证：临时 `-Duser.home` 强制走完整下载路径实测通过——latest.json 解析成功、
下载 349681 字节、SHA256 与官方一致、`buildLaunchJvmArgs` 返回
`-javaagent:<jar>=http://127.0.0.1:7306/` + `-Dauthlibinjector.side=client`。
已把校验通过的 jar 直接放到 `%USERPROFILE%\.starlight-launcher\authlib-injector.jar`，
下次启动直接复用，无需再下载。

## 披风最终卡点：纹理域名白名单（2026-10-01 再追加）

现象（17:32 现场日志）：agent 已正常注入并 transform（authlib-injector.log 无 ERROR），
本地档案服务器也启动，但服务器**收不到任何档案请求**，游戏 52 秒后异常收尾
（starlight.log 尾部 `[ERROR] 错误：null`）。游戏日志
`logs\minecraft_launch_20261001_173243.log` 给出决定性证据：

```
[17:33:19] Environment: authHost='http://127.0.0.1:10437/authserver', accountsHost='http://127.0.0.1:10439/https/api.mojang.com', sessionHost='http://127.0.0.1:10439/https/sessionserver.mojang.com', ...
[17:33:24] [Worker-Main-14/ERROR]: Textures payload contains blocked domain: http://127.0.0.1:10437/skin.png
```

链路其实**已通到最后一厘米**：客户端确实请求了本地档案服务器并拿到了 textures
（SKIN/CAPE URL），但 1.17.1 的 authlib 在 `YggdrasilMinecraftSessionService.getTextures`
里有**纹理 URL 域名白名单**检查（默认只允许 `.minecraft.net` / `.mojang.com`），
`127.0.0.1` 不在白名单 → 报 `Textures payload contains blocked domain` → 皮肤/披风
拒绝加载。Environment 里 sessionHost 显示为 agent 内部 httpd（10439）的代理路径是
agent 的展示机制，真实请求仍会经 URLProcessor 落到 apiRoot（10437）——已由报错里的
URL 证明。

根因（反编译 `authlib-injector-1.2.8.jar` 确认）：

- `AuthlibInjector.bootstrap` 在创建 transform 单元后执行
  `SkinWhitelistTransformUnit.getWhitelistedDomains().addAll(apiMetadata.getSkinDomains())`
  ——agent 把**元数据顶层的 `skinDomains` 列表**并入纹理白名单
  （`SkinWhitelistTransformUnit` 默认白名单只有 `.minecraft.net` / `.mojang.com`）；
- 我们的元数据端点（`LocalYggdrasilServer.handleMetadata`）此前**未提供 `skinDomains`**，
  白名单为空 → `127.0.0.1` 被拒。

## 9. 签名格式修复（authlib-injector 1.2.8 "Bad signature public key" 崩溃）

**现象**：加 RSA 签名后，agent 1.2.8 启动即报 `Unable to parse metadata: java.io.IOException: Bad signature public key`，游戏 0 秒退出。

**根因（反编译 KeyUtils 确认）**：agent 1.2.8 的 `KeyUtils.decodePEMPublicKey` 只接受带 PEM 头尾的格式：
- 输入必须以 `-----BEGIN PUBLIC KEY-----` 开头、以 `-----END PUBLIC KEY-----` 结尾，否则直接抛 `IllegalArgumentException("Bad key format")`（被包装为 "Bad signature public key"）。
- 之前的实现返回裸 X.509 DER Base64（`getEncoded()` 直接 Base64），不被接受。

**修复（LocalYggdrasilServer.java）**：`signaturePublickey` 改为 PEM 格式：
```
-----BEGIN PUBLIC KEY-----
<X.509 DER Base64>
-----END PUBLIC KEY-----
```

**探针发现的另一个事实**：agent 的 `APIMetadata.parse(String apiRoot, String metadata)` 签名顺序是 (apiRoot, metadata)，第二个参数才是被 `JsonUtils.parseJson` 解析的元数据 JSON。

**验证（temp\smoke\APIMetadataProbe.java / AgentCompatTest.java）**：
- `PARSE OK order=(apiRoot, meta)` —— PEM 元数据被 agent 解析成功；
- `AGENT PARSE OK` —— 真实服务器元数据解析成功；
- `AGENT VERIFY: PASS` —— 用 agent 解析出的公钥验证服务器 textures 签名通过（SHA256withRSA）。


## 10. 签名算法与签名对象修复（客户端"查了档案但不下载贴图"根因）

**现象**：签名修复后游戏正常启动、agent 正常注入、客户端查到档案（URI 无 `?unsigned=` 参数），但**始终没有皮肤/披风贴图下载请求**，且游戏内 `latest.log` 无任何 authlib 报错。

**根因（反编译 authlib 2.3.31 Property 确认，两处）**：

1. **签名算法不匹配**：authlib 2.3.31 的 `Property.isSignatureValid` 固定用 `SHA1withRSA` 验签；之前的实现用 `SHA256withRSA` 签名 → 客户端验签必然失败（`InsecureTextureException: Textures payload has been tampered with`，错误被 log4j 吞掉不显示在启动器日志）。
2. **签名对象错误**：`Property.isSignatureValid` 是对 **value 字段的字节（base64 字符串本身）** 做 `update(value.getBytes())` 验签；之前的实现对**原始 JSON payload** 签名 → 验签对象不匹配。

**修复（LocalYggdrasilServer.java）**：
- 签名算法改为 `SHA1withRSA`；
- 签名对象改为 base64 编码后的 value 字符串（`signTextures(value)`）。

**验证（temp\smoke\AgentCompatTest.java，决定性）**：真实服务器 → agent 1.2.8 解析元数据公钥 → **authlib 2.3.31 `Property.isSignatureValid` 直接验签 → PASS**（这是客户端完全相同的代码路径）。

### 16.8 实机第四轮：全链路接通但 OptiFine 下载端 NPE（22:14）
- 22:14:23 启动（IDEA Stop→Build→Run 后）：启动命令含两个 -javaagent（authlib-injector 13512 + cape-url-patch-agent 13513），
  游戏输出 [CapeUrlPatchAgent] 已重写披风 URL 常量（两次），本地披风服务器 22:15:00 / 22:15:31 两次收到
  OptiFine 披风下载请求并返回 590 字节（15 周年披风，PNG 头校验有效），
  **但游戏侧每次报错**：Couldn't download http texture: java.lang.NullPointerException: Cannot read the array length because "buf" is null。
- 反编译定位（%TEMP%\of_full、httpx\）：
  - OptiFine HttpTexture.loadTexture（pipeline=true 分支）走 HttpPipeline.makeRequest + executeRequest，
    status 2xx 后取 response.getBody() 构造 ByteArrayInputStream —— body 为 null 即触发该 NPE。
  - HttpPipelineReceiver.readResponse：仅当响应头含 Content-Length 且 parseInt>0 才分配 body 字节数组；
    Transfer-Encoding: chunked 走 chunked 解析；两者都没有则 body=null。
  - 结论：JDK com.sun.net.httpserver 的响应与 OptiFine HttpPipeline 简单解析器不兼容
    （status 2xx 但 body 读取为 null），即“请求到达、服务器返回、客户端解析失败”。
- 修复：LocalCapeProxy 弃用 JDK HttpServer，改 ServerSocket 手写 HTTP/1.1 响应：
  HTTP/1.1 200 OK / Content-Type: image/png / Content-Length: N / Connection: close + 空行 + body。
  每次请求独立连接（Connection: close），避开 keep-alive 复用歧义；404 同理。
- 验证：CapeProxyHttpCompatTest 模拟 HttpPipeline 客户端协议（HTTP/1.1 + keep-alive 头、
  按 Content-Length 完整读 body）9/9 PASS（200 OK / Content-Length 590 / body 590 字节一致 / 404 / agentJvmArg 绝对路径含端口）。
- 待实机：IDEA Stop→Build→Run→启动游戏→进世界→F5 看背后 3 秒，确认不再出现
  Couldn't download http texture，且披风显示为【官方版】15周年披风.png。
