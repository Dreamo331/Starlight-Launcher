# 2026-09-30 下载等待池方案（0B/停滞响应的批内延迟重试）

> 项目：Starlight Launcher（Maven，Java 17，Windows）
> 触发背景：补全游戏资源（assets / libraries）时出现大量 `[网络 发送] GET ... | 数据包 0 B` 日志；
> 经实测确认 **0B 并非资源不存在，而是镜像连接偏慢**——连接一旦建立，数据仍可正常下载（如日志中
> `200 | 数据包 31.8 KB` 的成功项）。
> 本文为**已确定的设计方案**，可直接落地。

---

## 1. 现状（已核实代码）

补全链路：`downloadConcurrently`（固定线程池，线程数 = `DownloadSettings.getDownloadThreads()`，默认 8）
→ `downloadSingleAsset`（候选源循环）→ `downloadFile`（`HttpURLConnection`：connectTimeout 15s + 停滞看门狗
readTimeout 15s；最后一条可用候选放宽）。

| 现象 | 当前处置 | 健康表（SourceHealth） |
|---|---|---|
| HTTP 200 但正文 0 字节 | 判失败，换下一候选源 | `recordEmpty`：连续 5 次拉黑该地址段 90s |
| 单次 read 停滞超时（15s 无字节） | 判失败，换下一候选源 | `recordTimeout`：连续 3 次拉黑 60s |
| 长度不完整（Content-Length 不符） | 判失败，换下一候选源 | 不计数 |
| SHA-1 校验不符 | 判失败，换下一候选源 | 不计数 |
| 404 / 410 | 判失败，换下一候选源 | `record404`：连续 8 次拉黑 120s |

**关键缺口（本方案要解决的核心）**：

1. 所有候选源都失败 → 该文件**本批判失败，批内不再重试**，只能等用户再次手动点「补全」；
2. 每次停滞都白等满一个完整读超时周期（15s），慢源占住线程槽位；
3. 「慢但能下」的源会被一批 0B/超时**误伤拉黑**（90s/60s），形成「越补越慢、一批失败一堆」的体验。

---

## 2. 方案总览：批内「下载等待池」（延迟重试队列）

**一句话语义变化**：0B / 停滞等「疑似慢源」的失败不再立即判死，而是先进入等待池；
主波次结束后按退避窗口重试，**重试仍失败才计为最终失败**。

### 2.1 失败分类

| 类别 | 判定 | 处置 |
|---|---|---|
| **可重试（入池）** | 200-0B 空正文 / 停滞读超时 / 长度不完整 / 5xx / 连接异常 / SHA-1 不符（仅一次） | 入等待池，退避后重试 |
| **不可重试（直接计失败）** | 404 / 410（资源确实不存在）/ 重定向异常 | 不入池，本批结束即计失败 |

SHA-1 不符只允许重试一次，且**重试时必须强制更换候选源**（若存在其他可用源），防止同一坏源循环重试；重试后仍不符即判死。

### 2.2 等待池运行流程（伪代码）

```
wave1：全部任务提交线程池 → 等待全部结束
waiting = 收集 wave1 中「可重试失败」的任务

for round in 1..MAX_RETRY_ROUNDS(=2):
    if waiting.isEmpty(): break
    // 检查批级剩余时间，不足则跳过本轮重试，直接计最终失败
    if (remainingTime < WAIT_BASE_MS(round) + MIN_EXECUTE_MS) break
    sleep(backoff(round))            // 主线程退避等待，不占线程池槽位：1s → 8s，上限 30s，含 ±20% 随机抖动
    提交 waiting 全部任务 → 等待全部结束（仍计入批级总时限）
    // 重试时按最新源评分重新排序候选源，优先尝试快速源
    waiting = 本轮仍「可重试失败」的任务集合

waiting 剩余 → 计最终失败
```

关键设计点：

- **等待不占线程**：任务在重试之间回到池中（退出工作线程），等待发生在批主线程；
- **错峰重试**：退避窗口加入 **±20% 随机抖动**，避免所有重试任务在同一时刻再次集中请求；
- **复用线程池**：主波次结束后池线程空闲，重试波次复用同一 executor；
- **源评分动态排序**：每次选择候选源时，根据 `SourceHealth` 和**历史连接时间**动态排序，重试波次天然优先尝试当前最优源；
- **总时限保护**：重试前检查批级剩余时间，若不足以完成一轮退避 + 最小执行时间，则跳过重试直接计失败。

### 2.3 与 SourceHealth 健康表解耦（关键调整）

- **首见 0B / 停滞：只入池，暂不计入 `recordEmpty` / `recordTimeout`**；
- **引入“软计数” `slowCount`**：首见失败时累加该源在本次批中的 `slowCount`，但不触发拉黑；
- **重试仍失败：才调用 `recordEmpty` / `recordTimeout`**，维持现有「坏源快速熔断」语义；
- **连续多批慢源拉黑**：若同一源在连续 3 批补全中都进入等待池且重试仍失败，则额外触发一次拉黑（冷却时间可设为 120s），防止长期慢源永远不被熔断；
- **重试时仍尊重 `isBlocked`**：被拉黑的候选跳过，冷却结束自动放行；
- 代价：真坏源要多付一次请求成本（重试一次），可接受。

### 2.4 源评分与动态排序

在 `downloadSingleAsset` 选择候选源时，不再仅按静态顺序，而是根据以下信息动态排序：

1. **`SourceHealth` 状态**：被拉黑的源降权或跳过；健康源优先。
2. **历史连接时间**：维护 `Map<源地址, 最近成功连接时间>`，每次成功下载后更新。选择候选源时，优先选最近连接时间短的源。
3. **软计数 `slowCount`**：本批中进入等待池次数越多的源，排序权重越低。
4. **重试波次重新排序**：每轮重试开始前，根据最新评分重新排序候选源，确保优先尝试快速源。

此机制不需额外网络请求，仅利用已有下载结果与健康表数据。

### 2.5 批级保护

- **总时限**：沿用现有 `CompletableFuture.allOf().get(30, MINUTES)`，覆盖全部重试轮；
- **取消**：等待与重试全程检查 `cancel`，取消立即退出，已入池任务不残留；
- **参数先内联常量**：`MAX_RETRY_ROUNDS = 2`、`WAIT_BASE_MS = 1000`、`WAIT_MAX_MS = 30000`、`JITTER = 0.2`；
  二期再接 `DownloadSettings` + `starlight-client.ini`（需同步登记 `ConfigManager.CLIENT_KEYS`）。

## 4. 确定的设计决策

1. **入池范围**：0B + 停滞超时 + 长度不完整 + 5xx + 连接异常 + SHA-1 不符（仅一次）。404/410 不入池。
2. **首见 0B/停滞不计入健康表拉黑**：只累加 `slowCount` 软计数；重试仍失败才调用 `recordEmpty` / `recordTimeout`；同一源连续 3 批补全均进入等待池且重试失败，则额外拉黑 120s。
3. **重试参数默认值**：轮次 2，退避 1s → 8s（上限 30s），含 ±20% 随机抖动，批级总时限仍 30 分钟；重试前检查剩余时间，不足则跳过。
4. **源动态排序**：候选源按 `SourceHealth` 状态、历史连接时间、`slowCount` 动态排序；重试波次重新排序。
5. **SHA-1 重试强制更换源**：若存在其他可用候选源，重试时必须切换，防止同一坏源循环。
6. **RetryQueue 容量上限**：设置池容量上限（如 2000 个文件），超出部分直接计失败，防止内存膨胀。

## 5. 验证方式

- `mvn -DskipTests compile` 编译通过；
- 单元测试：
  - 使用 `MockWebServer` 模拟首次 0B、重试成功，验证等待池入池、退避、重试、最终成功；
  - 模拟连续多批慢源，验证 `slowCount` 累加与拉黑逻辑；
  - 验证 `RetryQueue` 的保序去重、容量上限、取消检查；
  - 验证源动态排序：模拟多个源，历史连接时间不同，确认优先选择快速源。
- 手工验证：把 `DownloadStallTimeoutSec` 调小（3s）并指向慢镜像，观察「入池 → 退避（含抖动） → 重试 → 完成/失败」日志与进度文案；
- 回归验证：正常快源下等待池应为空，行为与现状完全一致（无新增请求、无额外等待）；
- 抽查日志：DebugLog 保留 0B/停滞明细，新增「x 个文件进入等待池 / 第 k 轮重试开始，共 y 个文件 / 第 k 轮重试结束，剩余 z 个」可观测行。
