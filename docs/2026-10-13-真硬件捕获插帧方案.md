# 真·硬件捕获插帧方案（Frame Interpolation）

> 状态：方案设计，未落地。本文只描述"应该怎么做"，不改动现有代码。
> 前提结论：现有的"帧生成器"是 `maxFps` 改写器，不是帧生成。本方案是把它替换成真正的帧插值管线。

---

## 0. 先厘清三件事，避免重蹈覆辙

上一轮排查发现现有实现把三件事混为一谈，本方案必须先把边界钉死：

| 概念 | 含义 | 谁做 |
|---|---|---|
| **帧率上限**（cap） | 限制每秒最多渲染多少帧，省电降温 | 游戏自己（`options.txt` / `maxFps`），**与本方案无关** |
| **帧生成 / 帧插值**（FI） | 在已有帧之间合成新帧，提升感知帧数 | 本方案（独立进程合成） |
| **超分 / 缩放**（upscale） | 低分辨率渲染再放大 | 不在本方案范围，可选后接 FSR1/LS 缩放 |

**关键点：帧插值是"外部合成"，必须拿到游戏画面。** 拿画面的方式决定整个架构，这是本方案的第一决策点。

---

## 1. 架构选型：两条路线，强烈建议 A

### 路线 A · 窗口捕获 + 独立合成进程（推荐）

```
Minecraft (OpenGL) ──渲染──> 窗口 (HWND)
                                │
                                │ Windows.Graphics.Capture / DXGI DD
                                ▼
                    ┌───────────────────────┐
                    │  FrameGen Host 进程    │
                    │  捕获 → 插值 → 呈现    │
                    │  独立 DX11/DX12 窗口   │
                    └───────────────────────┘
                                │
                                ▼
                          用户看到的画面
```

**做法**：启动器拉起一个伴生进程 `framegen-host.exe`，它用 Windows Graphics Capture (WGC, Win10 1903+) 或 DXGI Desktop Duplication 捕获 MC 窗口，跑插帧算法，全屏呈现。

| 优点 | 缺点 |
|---|---|
| 游戏侧**零侵入**，不注入、不改 jar、不依赖游戏版本 | 多一次 GPU 复制 + 呈现开销 |
| 与 MC 版本/加载器/Mod 完全解耦 | 全屏游戏时需处理焦点/输入穿透（WGC 可捕获全屏独占外的窗口化） |
| 崩溃隔离：host 挂了不影响游戏 | 独占全屏会截不到（必须让 MC 用窗口化/无边框） |
| 可用 CUDA/DX12/Compute Shader 做插值 | 引入约 1 帧的额外延迟 |

> **必须接受的产品约束**：这条路要求玩家用"窗口化全屏"。现有 MC 默认就是窗口化，代价可接受。要写进 UI 说明。

### 路线 B · 游戏内注入 + GL 钩子（不推荐）

通过 javaagent 注入，Hook LWJGL 的 `glfwSwapBuffers`，在 swap 前抓 framebuffer，插帧后多 swap 几次。

| 优点 | 缺点 |
|---|---|
| 零复制、零额外延迟 | 需针对每个 MC 版本/加载器适配（1.12/1.16/1.20/Forge/Fabric/OptiFine/Iris） |
| 可与渲染管线深度集成 | 注入即崩溃风险，用户排障成本极高 |
| | 无法处理"游戏没在渲染"的画面（如加载中） |
| | 与 OptiFine/Sodium/Iris 的 swap 逻辑冲突史很长 |

**结论：走 A。** 路线 B 是 Lossless Scaling 这类商业软件都不敢全押的做法（它们同样用桌面捕获）。本项目连 `maxFps` 的 `options.txt` 重写都出过"吃注释、吃末尾换行"的问题，不适合承担注入式图形 Hook 的复杂度。

## 2. 插帧算法选型

### 2.1 分级策略（按硬件能力自动降级）

| 档位 | 算法 | 硬件要求 | 预期收益 | 延迟代价 |
|---|---|---|---|---|
| **L0 兜底** | 帧复制 / 混合（`lerp(prev, cur, 0.5)`） | 任何 GPU | 帧数翻倍但**无运动信息，快速平移会明显拖影** | ≈0 |
| **L1 基础** | 块匹配光流 (Block Matching, 8×8 块 + 双向搜索) | 任何 GPU，Compute Shader | 中等质量 | 低 |
| **L2 主流** | **RIFE / IFRNet 类轻量神经插帧**（onnx → DirectML / TensorRT） | 独显 / 强核显 | 接近商业水平 | 中 |
| **L3 最佳** | NVIDIA Optical Flow SDK（Ada/Ampere 硬件光流单元） | RTX 20 系+ | 最高质量、最低延迟 | 低 |

**推荐首发做 L1 + L2**：L1 保证"任何机器都能开"，L2 给独显用户真实收益。L3 作为后续增量（且仅 NVIDIA，覆盖窄）。

> 你之前的判断"顶多算插了几帧空白帧"完全正确——那正是 L0。**要避免的就是只做出 L0。** L0 单独上线比不做更伤口碑。

### 2.2 神经网络路线的现实约束

- **模型体积**：RIFE 类模型 INT8 量化后约 5~15 MB，可随启动器分发。
- **推理后端**：优先 **DirectML**（DX12，A/N/I 通吃，Windows 原生）；NVIDIA 用户可另走 TensorRT 提速。**不要绑 CUDA**，否则 A 卡/核显用户直接出局。
- **分辨率**：1080p 插值在 RTX 3060 上约 3~5 ms/帧（FRUC 类），2K/4K 需按需降级或只用 L1。
- **1080p@60→120** 是主战场；**4K@144** 现阶段不现实，UI 上要诚实标注。

### 2.3 明确的"不做"

- ❌ **不做 8x**。物理上 60fps 插到 480fps，单帧预算 2ms 内，任何算法都会糊成一片，且感知收益趋零。**上限 2x（60→120）**，4x 仅在 30fps 起插时开放且需警告。
- ❌ **不做"空白帧"**。宁可不出这个功能，也不要 L0 冒充。
- ❌ **不承诺"零延迟"**。插值必然引入 ≥1 帧延迟，必须 UI 明示。

## 3. 进程与部署架构

### 3.1 组件划分

```
Starlight Launcher (Java/JavaFX)
  └─ org.framegen.host.FrameGenHostManager     ← 生命周期、配置、健康检查
       │ 启动/停止子进程、传参、收遥测
       ▼
framegen-host.exe  (C++ / DX11 或 DX12，独立可执行)
  ├─ CaptureBackend   (WGC 优先，DXGI DD 兜底)
  ├─ Interpolator     (L1 块匹配 或 L2 DirectML)
  ├─ Presenter        (全屏无边框窗口 / 交换链)
  ├─ InputForwarder   (把输入事件转发回游戏窗口，保持可操作)
  └─ Telemetry        (通过命名管道/Named Pipe 上报 fps、GPU 占用、丢帧)
```

**为什么独立进程而不是 native 库**：
1. 崩溃隔离——插帧 host 崩了，游戏和启动器都不受影响，只是画面回到直通。
2. 崩溃隔离之外还有**分辨率/刷新率切换**（独占全屏、显示器模式切换）风险，独立进程更容易恢复。
3. 本项目已用 Gluon substrate 把 Java 打成单 exe，**再塞 DX12 捕获+推理到同一进程会显著增加打包复杂度**（`native/management_stub.c` 那种 JNI stub 模式适合小工具，不适合图形栈）。独立 exe 反而是更低风险的路径。

### 3.2 与现有启动器集成点

| 集成点 | 现有机制 | 改造方式 |
|---|---|---|
| 拉起游戏 | `GameLauncherService` | 游戏进程起来后，取 `HWND`/PID 交给 host |
| HWND 获取 | 现有 `GameMonitor` 已在扫 `java.exe/javaw.exe` 的 WMI 命令行，能拿到 PID | 增加 `EnumWindows` + `GetWindowThreadProcessId` 按 PID 找主窗口 |
| 生命周期 | 现有 `notifyGameStarted/notifyGameStopped`（`LauncherView#L1522`/`#L1478`）已是权威信号 | 直接复用，**不再需要 2s 一次 PowerShell 轮询** |
| 配置 | 现有 `AppConfig`（`~/.starlight/framegen/config.properties`） | 保留文件位置，废弃 `frameMultiplier`/`baseFps` 键，新增 `interpolation.enabled/quality/engine` |
| UI 页面 | `FrameGenCoordinator.buildPage()` | 整页重做（见 §5） |

> **顺带解决上一轮的两个遗留问题**：`AppConfig.load()` 里的 `mkdirs()` 移到 `save()`；`GameMonitor` 的 PowerShell 轮询降级为可选兜底。

## 4. 技术要点与风险

### 4.1 输入转发（最容易低估的部分）

插帧 host 全屏盖在游戏上时，**鼠标/键盘必须转发回游戏窗口**，否则玩家无法操作。

- 方案：host 窗口设置 `WS_EX_TRANSPARENT | WS_EX_LAYERED` 直接穿透（画面可见但不接收输入）——**优先用这个，最省事**。
- 但穿透后游戏窗口在下面，玩家点击落在游戏窗口上，需要保证游戏窗口仍有焦点。
- 更稳的做法：host 用 `WS_EX_NOACTIVATE` 无焦点窗口，`SetWindowPos` 置顶，游戏窗口保持 `SetForegroundWindow`。
- **这一块必须早做 POC**，它比插值算法更容易翻车。

### 4.2 全屏模式限制

- 独占全屏（`F11` 真全屏）→ DXGI DD 可捕获，WGC 不可（Win10 早期）；且捕获后呈现会与游戏争抢显示模式。
- **产品决策：检测到独占全屏时禁用插帧并提示"请切换为窗口化全屏"**，不要试图硬支持。

### 4.3 延迟与"手感"

- 插帧引入的延迟 = 捕获延迟 + 插值耗时 + 呈现延迟，典型 8~20ms。
- 对 PVP/速通类玩家是**负收益**。UI 必须提供清晰的"竞技模式：关闭插帧"开关。
- 建议实现**动态开关**：检测到玩家在战斗/高频输入时自动关闭插帧（需游戏内状态，较难；退而求其次用"按住某键直通"）。

### 4.4 与现有工具的冲突

| 冲突对象 | 表现 | 处理 |
|---|---|---|
| Lossless Scaling | 同为桌面捕获，叠加会双倍延迟/黑屏 | 检测到 LS 进程存在则拒绝启动，UI 提示 |
| OptiFine/Sodium 全屏优化 | 会改变窗口/交换链行为 | 依赖路线 A 的"外部捕获"天然规避 |
| OBS/录制软件 | 争抢捕获资源 | WGC 支持多消费者，一般共存；DXGI DD 会冲突 |
| 启动器自己的截图功能 | `HomePage` 有截图磁贴 | 截的是 host 窗口内容，需注意合成层级 |

### 4.5 反作弊与公平性

- 纯外部捕获不读写游戏内存，**不构成作弊**。
- 但**插帧带来输入延迟优势的可能性为负**，不存在公平性问题。
- 部分服务器/比赛规则可能禁止任何画面修改，UI 应有免责说明。

## 5. UI / 产品设计要点

替换现有"帧生成器"页面（当前是 0/2x/4x/6x/8x 五个按钮 + Lossless Scaling 路径框 + 托盘开关）：

```
┌─ 帧插值 ──────────────────────────────────┐
│  状态：● 运行中   引擎：DirectML (L2)      │
│  捕获：Windows Graphics Capture            │
│  目标：60 → 120 fps（实测输出 118 fps）    │
│                                             │
│  质量档位   [关闭] [基础] [标准] [高质量]  │
│             └ L1      └ L2      └ L3(仅N卡)│
│                                             │
│  竞技模式（关闭插值，直通画面）  [ 开 ]   │
│  快捷键：按住 Ctrl+Alt 临时直通             │
│                                             │
│  ⚠ 需要游戏使用"窗口化全屏"，独占全屏不可用 │
│  ⚠ 插值会引入约 1 帧延迟                    │
└─────────────────────────────────────────────┘
```

**必删项**：
- `Lossless Scaling 路径`输入框（LS 与本方案冲突，不再支持外挂 LS）
- `×2/×4/×6/×8` 倍率按钮（改为质量档位，倍率固定 2x）
- 首页磁贴文案"帧生成" → "帧插值"

## 6. 分期落地

| 阶段 | 内容 | 周期 | 可交付判定 |
|---|---|---|---|
| **P0 可行性验证** | C++ 单文件 POC：WGC 捕获记事本窗口 → L0 帧复制 → 全屏呈现；验证输入穿透、多显示器、刷新率 | 1~2 周 | 能稳定 60→120 呈现 5 分钟不崩 |
| **P1 算法接入** | 接 L1 块匹配光流（Compute Shader），替换 L0 | 2~3 周 | 平移场景无明显拖影，主观可接受 |
| **P2 神经网络** | 接 DirectML + RIFE 量化模型；自动按 GPU 选档 | 3~4 周 | RTX3060 上 1080p@60→120 插值 <5ms/帧 |
| **P3 启动器集成** | 复用 `notifyGameStarted/Stopped`，自动找 HWND，健康检查，崩溃自恢复 | 1~2 周 | 游戏启动即自动开启，退出即自动关闭 |
| **P4 打磨** | 竞技模式、快捷键直通、多显示器、遥测、冲突检测 | 2 周 | — |

**总计约 9~14 周**（单人全职）。P1 之后才有对外宣称"帧插值"的资格。

## 7. 关键风险与决策建议

### 7.1 这个功能值得做吗？

坦白讲，**投入产出比很低**：

1. **Minecraft 的瓶颈几乎从不在 GPU 出帧**。它是 Java 单线程游戏，卡在 tick 逻辑、GC、区块加载、实体渲染批处理。GPU 明明能出 200 帧，CPU 只喂得出 60 帧——插值能补到 120，但**插的是"CPU 没算出来的那一帧"，运动信息来自前后两帧，中间的逻辑状态根本不存在**。对 MC 这种有方块交互、准星、粒子、UI 的游戏，插值的伪影（准星重影、粒子拖尾、快捷栏重影）比 3A 游戏明显得多。
2. **`HUD/准星重影是硬伤**。插值无法区分"应该在每帧都清晰"的 UI 元素和"应该平滑过渡"的世界。商业软件靠 UI 检测算法缓解，本项目没有这个积累。
3. **已有的 `maxFps` 功能其实更实用**：限制帧率对 MC 省电降温稳帧是确定收益，而插值收益高度依赖场景。
4. **竞品参照**：Lossless Scaling 卖 30 元，积累多年，仍被大量用户抱怨"MC 上不好用"。

### 7.2 如果仍要做，务实的替代路径

**建议优先级**：

1. **先做诚实版帧率上限**（上一轮方案 A）——1~2 天，立即消除"名不副实"问题。
2. **再评估是否接 Lossless Scaling 的 lsfg**（但要走它真实的调用方式：不是命令行参数，而是它的 `LSFG` 配置文件 + 全局热键模拟，或干脆引导用户手动开，启动器只负责拉起游戏和检测）。
3. **最后才考虑自研插帧**，且先做 P0/P1 给内部验证，**不要先做 UI**。

### 7.3 一句话结论

> 真做硬件捕获插帧技术上可行（WGC + DirectML + RIFE 是成熟路径），但**对 Minecraft 这个特定游戏收益有限、伪影明显、投入 9~14 周**。若目标是"让用户觉得帧数高了"，先修好 `maxFps` 的语义错误性价比高 100 倍；若目标是真的做技术积累，本文的 P0→P4 路线是可执行的，但请把"2x 上限""窗口化全屏""1 帧延迟"三条约束写进产品文档，否则必然重演"开 8x 更卡"的口碑灾难。
