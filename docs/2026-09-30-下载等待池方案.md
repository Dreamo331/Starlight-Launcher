# 2026-09-30 下载等待池方案（0B/停滞响应的批内延迟重试）

> 项目：Starlight Launcher（Maven，Java 17，Windows）
> 触发背景：补全游戏资源（assets / libraries）时出现大量 `[网络 发送] GET ... | 数据包 0 B` 日志；
> 经实测确认 **0B 并非资源不存在，而是镜像连接偏慢**——连接一旦建立，数据仍可正常下载（如日志中
> `200 | 数据包 31.8 KB` 的成功项）。
> 本文为**方案稿（未实现）**，待确认后落地。

---

## 1. 现状（已核实代码）

补全链路：`downloadConcurrently`（固定线程池，线程数 = `DownloadSettings.getDownloadThreads()`，默认 8）
→ `downloadSingleAsset`（候选源循环）→ `downloadFile`（`HttpURLConnection`：connectTimeout 15s + 停滞看门狗
readTimeout 15s；最后一条可用候选放宽）。

| 现象 | 当前处置 | 健康表（SourceHealth） |
|---|---|---|
| HTTP 200 但正文 0 字节 | 判失败，换下一候选源 | `recordEmpty`：连续 5 次拉黑该地址段 90s |
| 单次 read 停滞超时（15s 无字节） | 判失败，换下一候选源 | `recordTimeout`：连续 3 次拉黑 60s |
| 长度不完整（Content-Length 不符） | 判失败，换下一候选源 | 不计数 |
| SHA-1 校验不符 | 判失败，换下一候选源 | 不计数 |
| 404 / 410 | 判失败，换下一候选源 | `record404`：连续 8 次拉黑 120s |

**关键缺口（本方案要解决的核心）**：

1. 所有候选源都失败 → 该文件**本批判失败，批内不再重试**，只能等用户再次手动点「补全」；
2. 每次停滞都白等满一个完整读超时周期（15s），慢源占住线程槽位；
3. 「慢但能下」的源会被一批 0B/超时**误伤拉黑**（90s/60s），形成「越补越慢、一批失败一堆」的体验。

---

## 2. 方案总览：批内「下载等待池」（延迟重试队列）

**一句话语义变化**：0B / 停滞等「疑似慢源」的失败不再立即判死，而是先进入等待池；
主波次结束后按退避窗口重试，**重试仍失败才计为最终失败**。

### 2.1 失败分类

| 类别 | 判定 | 处置 |
|---|---|---|
| **可重试（入池）** | 200-0B 空正文 / 停滞读超时 / 长度不完整 / 5xx / 连接异常 / SHA-1 不符 | 入等待池，退避后重试 |
| **不可重试（直接计失败）** | 404 / 410（资源确实不存在）/ 重定向异常 | 不入池，本批结束即计失败 |

SHA-1 不符只允许重试一次：重试后仍不符即判死（防损坏文件无限循环）。

### 2.2 等待池运行流程（伪代码）

```
wave1：全部任务提交线程池 → 等待全部结束
waiting = 收集 wave1 中「可重试失败」的任务

for round in 1..MAX_RETRY_ROUNDS(=2):
    if waiting.isEmpty(): break
    sleep(backoff(round))            // 主线程退避等待，不占线程池槽位：2s → 8s，上限 30s
    提交 waiting 全部任务 → 等待全部结束（仍计入批级总时限）
    waiting = 本轮仍「可重试失败」的任务集合

waiting 剩余 → 计最终失败
```

关键设计点：

- **等待不占线程**：任务在重试之间回到池中（退出工作线程），等待发生在批主线程，
  与「线程内 sleep 原地重试」有本质区别——这正是「池」的意义；
- **错峰重试**：0B/停滞往往是同一时刻所有并发请求同时打向同一个慢镜像，退避窗口让重试错开撞墙时间；
- **复用线程池**：主波次结束后池线程空闲，重试波次复用同一 executor，不再新建。

### 2.3 与 SourceHealth 健康表解耦（关键调整）

- **首见 0B / 停滞：只入池，暂不计入 `recordEmpty` / `recordTimeout`**——
  「慢源」不会因为一批 0B 被误拉黑 90s；
- **重试仍失败：才调用 `recordEmpty` / `recordTimeout`**——维持现有「坏源快速熔断」语义不变；
- **重试时仍尊重 `isBlocked`**：被拉黑的候选跳过，冷却结束自动放行——重试波次天然享受「源恢复即复用」红利；
- 代价：真坏源要多付一次请求成本（重试一次），可接受。

### 2.4 批级保护

- **总时限**：沿用现有 `CompletableFuture.allOf().get(30, MINUTES)`，覆盖全部重试轮，批不会无限拖；
- **取消**：等待与重试全程检查 `cancel`，取消立即退出，已入池任务不残留；
- **参数先内联常量**：`MAX_RETRY_ROUNDS = 2`、`WAIT_BASE_MS = 2000`、`WAIT_MAX_MS = 30000`；
  二期再接 `DownloadSettings` + `starlight-client.ini`（需同步登记 `ConfigManager.CLIENT_KEYS`）。

## 3. 改动文件清单（预估）

| 文件 | 改动 |
|---|---|
| `download/task/GameResourceCompleter.java` | `downloadFile` 失败出口改为枚举结果（OK / RETRY / FAIL）；`downloadSingleAsset` 传播分类；`downloadConcurrently` 增加等待池循环与退避等待 |
| `download/mod/RetryQueue.java`（新增） | 批内等待池容器：保序去重、重试轮次、退避参数、取消检查（独立小类，便于单测） |
| `download/mod/SourceHealth.java`（可选，约 2 行移动） | `recordEmpty` / `recordTimeout` 调用点从「首见失败」移到「重试仍失败」处 |
| `docs/2026-09-30-下载等待池方案.md`（本文） | 方案文档 |

**明确不动**：`HttpDownloadEngine` / `DownloadCoordinator`——资产补全路径保持
`HttpURLConnection` 停滞看门狗（`HttpClient` 无 socket read timeout，见 `downloadFile` 内注释），
不迁移到 mod 协调器；本文只给现有路径加「批内延迟重试」能力。

## 4. 待确认（3 个决策点）

1. **入池范围**：只 0B，还是 0B + 停滞超时 + 长度不完整 + 5xx？（建议后者；404/410 不入池）
2. **首见 0B/停滞是否暂不计入健康表拉黑**？（建议是，避免慢源被误伤；真坏源多付一次请求成本）
3. **重试参数默认值**：轮次 2、退避 2s→8s（上限 30s）、批级总时限仍 30 分钟，是否接受？

## 5. 验证方式

- `mvn -DskipTests compile` 编译通过；
- 手工验证：把 `DownloadStallTimeoutSec` 调小（3s）并指向慢镜像，观察「入池 → 退避 → 重试 → 完成/失败」日志与进度文案；
- 回归验证：正常快源下等待池应为空，行为与现状完全一致（无新增请求、无额外等待）；
- 抽查日志：DebugLog 保留 0B/停滞明细，新增「x 个文件进入等待池 / 第 k 轮重试」可观测行。
